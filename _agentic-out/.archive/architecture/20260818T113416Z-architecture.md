# 架构决策文档

_本文档通过逐步协作发现构建，并在过程中持续补充各项架构决策。_

## 第一阶段激活架构：Windows RSS 最小闭环

本节是 2026-08-17 批准的阶段性交付覆盖层，不删除或改写本文后续的完整产品架构。第一阶段固定执行 Story 1.1、1.2、1.6、1.7、1.8、2.1、2.2、2.5、2.6、4.1、4.2、4.3、4.5、4.6、9.4；仅可宣称 **Windows RSS 最小闭环** 完成。

第一阶段激活的数据流为：Windows UI → DesktopApi → 精确 Tauri command → radar-core 应用用例 → 单一 SQLite owner。共享核心只激活当前设备配置、RSS/Atom 安全采集、前台手动同步、最小同步结果、规范化与溯源、确定性去重、透明规则、主情报流查询和证据详情。Windows 原文入口必须按稳定情报 ID 在核心解析已验证的 HTTPS 来源，再交由窄平台 effect 打开；不得暴露通用 URL、shell、文件或 SQL command。

2026-08-18 范围确认：Story 2.6 的当前执行面仅消费 RSS/Atom 本轮结果；GitHub Release、arXiv 和三来源聚合继续 Deferred。现有 `sync_runs`、`sync_source_results`、`sync_result_items` 与 `get_sync_result` 分组合同保持可扩展，但本阶段不得创建未实现来源的占位结果。

架构边界如下：

- 只实现一个真实来源适配器 RSS/Atom；通用 source/task 接口保持可扩展，但不得预建空的 GitHub Release、arXiv 或 GitHub discovery 模块。
- 第一阶段同步只支持前台手动执行。计划调度、后台常驻、托盘、通知和移动 ExecutionBudget 延期。
- 来源枚举和持久化模型可以保留未来兼容值，但运行时必须拒绝或明确标为未启用；UI 不展示不可用入口。
- 不激活 AI provider、通知、反馈、处理状态、全文搜索、收藏正文、移动端壳或第二数据库；不得用模拟结果冒充这些能力。
- 数据库迁移仅对当前已经存在及本阶段新增的 schema 提供升级和失败保护；未知未来 schema 必须 fail closed，不伪造未来迁移证据。
- Windows 性能和真实候选证据采用项目已批准的 30 次样本口径。系统主题/缩放矩阵只在隔离发布环境运行；所有 Rust、Node、浏览器和其他工具仍安装于项目目录，不改变全局环境。

上述裁剪只控制当前实现顺序。后文的完整跨平台、安全、可靠性和扩展性决策继续作为后续阶段约束。

## 项目上下文分析

### 需求概览

**功能需求：**

当前 PRD 包含 FR1–FR63，形成以下架构能力域：

- 首次启动、个性化配置与可恢复引导
- RSS/Atom、GitHub Release、arXiv 来源采集
- 标准化、溯源、内容生命周期与最小同步结果
- 筛选、排序、确定性去重和配置风险校验
- 可选 AI 翻译与分析，以及无 AI 降级
- 浏览、搜索、收藏与三态用户处理状态

- Windows、iOS/iPadOS、Android 生命周期与设备边界

FR59–FR63 新增的主要架构影响：

1. 同步任务必须保存来源级计数和最小规范化结果，不能只返回成功布尔值。

关键门禁包括：

- 50,000 条固定数据集下的搜索、筛选和交互性能
- 单来源失败隔离、幂等恢复和零重复通知
- 凭据安全存储、正文生命周期和诊断脱敏
- 无 AI Key、离线及受限后台环境下继续使用

- 同步结果 100% 可核验
- 三态处理状态六种收藏组合 100% 保留

## 起始模板评估

### 主要技术领域

本项目是跨平台本地优先原生应用：

- Windows：Tauri 2 + React + TypeScript + Vite + shadcn/ui
- Apple：SwiftUI 原生应用
- Android：Kotlin + Jetpack Compose Material 3 Adaptive
- 共享核心：Rust workspace，通过 UniFFI 向 Swift/Kotlin 暴露窄领域接口

### 评估过的起始方案

1. **官方平台脚手架 + 共享 Rust 核心（选择）：** 保留三套原生 UI，同时共享规范化、去重、规则、状态机和数据契约。
2. **Kotlin Multiplatform 共享逻辑 + 独立 Windows 应用：** 可共享 Android/iOS 逻辑，但 Windows/Tauri 仍形成第二套领域实现，无法完整解决三平台一致性问题。
3. **Tauri 2 统一三平台 Web UI：** 代码复用最高，但偏离已经确认的 SwiftUI、Compose 和平台原生交互要求。
4. **三个完全独立的原生实现：** 工具链简单，但高风险确定性逻辑会重复实现，长期一致性风险过高。

### 选择的起始方案

**组合式官方脚手架 + Rust 共享领域核心 + UniFFI 绑定**

**选择理由：**

- Windows 研究成果可以继续复用 Tauri/Rust 路径。
- SwiftUI 与 Compose UI 不被跨平台渲染层替代。
- 高风险确定性逻辑只实现一次。
- 平台通知、后台调度、密钥存储和生命周期仍由原生适配器承担。
- UniFFI 当前为 Swift、Kotlin 提供正式支持；采用已核验的 0.32.0 发布线并锁定版本，把生成绑定的编译验证纳入 CI；不采用尚未发布的实验性 Kotlin JNI 管线。

**2026-08-12 版本核验基线：**

- Tauri core：2.11.5
- Tauri CLI / `@tauri-apps/cli`：2.11.4
- create-tauri-app：4.7.3
- Tauri single-instance plugin：2.4.3
- UniFFI：0.32.0

上述版本进入 Cargo/pnpm 锁文件；后续升级必须通过共享契约、单实例和三平台冒烟测试，不以“latest”隐式漂移运行时依赖。

## 核心架构决策

### 数据架构

#### 数据库所有权

- 每台设备维护一个独立 SQLite 数据库，不存在服务器数据库或数据库文件同步。
- `radar-core` 是数据库、事务、迁移、查询和持久任务状态的唯一所有者。
- Windows 直接调用 Rust 核心；Swift/Kotlin 通过 `radar-ffi` 调用粗粒度用例，不直接执行 SQL。
- UI 只能接收分页 DTO、详情 DTO、状态快照和命令结果。

该边界确保三平台使用相同的唯一约束、去重、迁移和恢复语义。

#### SQLite 与 Rust 绑定

- SQLite 锁定已核验的 `3.53.4` 或更高兼容补丁版本；该版本属于包含 WAL-reset 修复后的维护发布线。
- Rust 使用 `rusqlite 0.40.1` 的 `bundled` 模式，避免依赖各操作系统内置的不同 SQLite 版本。
- 启动时执行 `SELECT sqlite_version()` 并验证最低安全版本。
- 不允许运行时加载任意 SQLite 扩展。

#### 并发与事务

- 每个应用进程只运行一个串行写入执行器。
- UI 查询使用有限只读连接；禁止平台代码额外打开数据库文件。
- 使用 WAL、`foreign_keys=ON`、有限 `busy_timeout` 和受控 checkpoint。
- 每个来源批次独立事务提交；单源失败不能回滚其他来源的成功结果。
- 规范化数据、去重结果、游标、任务和同步计数必须在同一来源事务内保持一致。
- 应用进入后台或退出前只请求安全收敛，不依赖“退出回调一定执行”。

#### 数据模型分层

主要表：

- `sources`：来源配置、游标、条件请求元数据和来源状态
- `intel_items`：稳定情报身份、标题、来源、发布时间和处理状态
- `intel_contents`：正文快照、摘录、内容 hash 和保留状态
- `item_provenance`：原始 URL、作者、版本、首次发现及关联来源
- `rule_evaluations`：规则版本、命中项、分数和解释
- `analysis_results`：AI provider、模型、输入 hash、结构化结果和置信度
- `sync_runs`、`sync_source_results`：整轮及来源级同步状态
- `jobs`：可恢复的采集后处理、AI 和通知判定任务
- `notification_log`：通知幂等键、发送状态和深链接
- `favorites`、`feedback`：用户行为与校准数据
- `settings_metadata`：非敏感配置；密钥不进入此表
- `setup_progress`：稳定步骤 ID、引导状态、已保存字段版本和更新时间；与业务配置分离
- FTS5 虚表：标题、中文摘要和可检索正文

原始事实、规则判断和 AI 结果分别存储，不允许 AI 结果覆盖来源字段。

#### 身份与去重

- 内部记录使用稳定、不带业务语义的 ID。
- 来源主键优先采用 `(source_kind, external_id)`。
- 无可靠外部 ID 时使用规范化 URL hash。
- 内容 hash 只用于变化检测和 AI 缓存，不代替情报身份。
- 跨来源仅记录关联关系；MVP 不自动语义合并。
- 数据库唯一约束是最终幂等防线，应用层预检查只用于优化。

#### 全文检索

- 使用 SQLite FTS5，不引入搜索服务器或向量数据库。
- 结构化筛选使用普通 B-tree 索引。
- 中文摘要和正文使用 FTS5 trigram 检索；标签、来源和精确字段使用普通索引。
- FTS 索引与正文变更在同一事务内显式维护，不依赖容易漂移的异步重建。
- 搜索结果使用游标分页，列表查询不加载完整正文。

#### 数据验证

- FFI 输入和第三方响应首先反序列化为版本化 Rust DTO。
- 领域构造函数执行 URL、时间、长度、枚举和状态转换验证。
- SQLite 使用 `NOT NULL`、`CHECK`、`FOREIGN KEY` 和 `UNIQUE` 作为第二道防线。
- 不持久化未经验证的 AI 结构化结果；验证失败时保留失败状态和原始事实。
- 原始第三方 payload 默认不长期保存；诊断保留需受大小和期限限制。

#### 演示数据隔离

- 演示记录具有不可伪造的 `data_origin = demo`，与真实来源使用不同 namespace。
- 演示数据不得触发真实通知、AI 外发、个人验证指标或与真实记录的去重合并。
- 首次真实同步后用户可保留或删除演示数据；删除不影响真实历史。
- 标准演示样本集中在 `contracts/fixtures/demo`，并通过契约测试证明上述副作用均为零。

#### 迁移与恢复

- SQL 迁移作为 `radar-core` 内嵌资源，使用单调递增版本。
- 启动顺序为：验证数据库 → 必要备份 → 事务化迁移 → 完整性检查 → 开放 UI 写操作。
- 不支持应用版本直接降级写入较新 schema。
- 迁移失败时保持旧数据库可恢复并进入只读诊断状态。
- 数据导出使用 SQLite backup API 或受控 checkpoint 后的一致快照，禁止直接复制活动数据库单文件。

#### 缓存策略

- SQLite 是唯一持久化事实源，不增加第二套持久缓存。
- 进程内仅缓存不可变配置、已编译规则和小型查询结果。
- 缓存按规则版本、数据提交序号或配置版本失效。
- AI 结果以规范化输入 hash 持久复用，但必须同时记录 provider、模型和分析策略版本。
- 正文、PDF、Release 二进制和模型文件不自动下载。

#### FR59–FR62 数据合同增量

**用户处理状态：**

- `intel_items.user_processing_state` 使用稳定代码 `unseen | judged | research_later`，`NOT NULL` 且新条目默认为 `unseen`。
- `favorites`、`feedback`、`analysis_results` 保持独立；列表浏览和详情查询是纯读取，不得隐式更新用户处理状态。
- 状态转换只允许通过显式领域命令，并建立 `(user_processing_state, collected_at, id)` 查询索引。
- 升级迁移保留可映射旧状态；无法映射或无旧值的记录安全映射为 `unseen`。
- Phase 1 是单用户、单设备数据域，不增加账户维度表或用户状态事件日志。

**同步结果闭环：**

- `sync_runs` 保存整轮同步身份、起止时间和最终状态。
- `sync_source_results` 保存来源级新增、更新、跳过、失败数量与错误归属。
- 新增 `sync_result_items`，保存本轮成功转换条目与 `intel_items` 的稳定关联及 `inserted | updated` 处置类型。
- 每个来源独立提交规范化条目、来源游标、计数和结果关联；来源失败只更新自己的结果，不回滚其他来源。
- 整轮状态由来源结果聚合为成功、部分成功、零结果或失败；最小结果查询不得依赖 AI、评分、搜索索引或完整正文表。
- 同步历史按保留策略清理时，只清理运行与关联记录，不删除所关联情报。

**配置验证：**

- 共享核心返回版本化 `ConfigurationValidationResult`。
- 阻断错误代码固定为 `expression_unparseable`、`value_out_of_range`、`lower_bound_above_upper_bound`、`invalid_source_or_unsupported_protocol`。
- 过窄风险代码固定为 `all_sources_disabled`、`all_high_trust_candidates_filtered`。
- 阻断错误不得写入数据库；正常配置直接保存，不进入确认分支。
- 过窄配置保存必须携带与规范化配置内容及验证版本绑定的确认令牌；保存时重新校验，配置内容变化后旧令牌失效。

**事务与迁移：**

- 新表、字段、约束和索引通过单调版本迁移加入。
- 同步计数、结果关联和来源游标必须在同一来源事务中一致。
- 三平台运行相同迁移、状态组合和固定配置验收样本。

#### 级联影响

- 后续安全决策必须确定密钥与普通数据库的分离方式，以及是否需要整库加密。
- FFI 契约必须支持分页、事务性命令和可恢复任务，而不是暴露表结构。
- 移动端后台任务只能请求核心执行“有限预算的一轮工作”，不能持有无限生命周期数据库会话。
- 测试必须在三平台运行同一迁移、去重和 golden fixture 套件。

### 认证与安全

#### 身份与授权边界

- MVP 不建立用户账户、登录、会话、角色或远程授权服务。
- 当前操作系统用户及应用沙箱构成本地身份边界。
- 所有能力默认面向当前设备，数据库、通知状态和用户反馈不跨设备共享。
- 不在 MVP 内增加自定义 PIN 或应用锁；如后续出现多人共用设备需求，再基于系统生物识别能力增加可选解锁。
- 后台任务继承应用自身权限，不能绕过用户已撤销的通知、网络或数据发送设置。

#### 密钥存储

API Key、访问令牌及未来的加密主密钥不得进入 SQLite、普通配置、日志、崩溃报告或诊断导出。

- Windows：优先使用 Windows Credential Manager；需要保护本地小型 secret blob 时使用当前用户范围的 DPAPI，禁止 `LOCAL_MACHINE` 范围。
- Apple：使用 Keychain，设置为仅当前设备可用，并选择允许系统后台任务在首次解锁后访问的保护级别。
- Android：Android Keystore 保存不可导出的 AES-GCM 密钥；API Key 作为加密 blob 保存在应用私有目录。Keystore 不直接充当任意字符串数据库。

平台客户端负责系统安全存储；共享核心只接收执行所需的短生命周期 `SecretLeaseInput`：

```text
platform.put(secret_id, bytes)
platform.delete(secret_id)
platform.status(secret_id) -> SecretStatus
core.execute_with_secret(task_id, SecretLeaseInput)
```

明文只在发起请求所需的最短生命周期内跨越一次受控调用，不能写入任务 payload、SQLite 或日志；设置页只接收“已配置”状态和掩码。移动端不向 Rust 注册长期 secret callback。

#### 本地数据库加密

- MVP 不引入 SQLCipher 或自定义整库加密。
- 核心内容主要来自公开来源，真正敏感的 API Key 已与数据库分离；整库加密会增加三平台构建、迁移、恢复和后台访问复杂度。
- Windows 数据库放在当前用户应用数据目录；Apple/Android 放在应用容器，并启用系统文件保护和备份排除策略。
- 数据导出必须明确说明会包含收藏、反馈、规则和浏览相关数据。
- 如果后续验证出明确的共享设备或高敏研究场景，再通过独立 ADR 引入整库加密；不得自研密码方案。

#### FFI 与进程边界

- `radar-ffi` 只暴露版本化用例，不暴露 SQL、文件路径、HTTP 客户端、密钥或任意命令执行能力。
- 所有 FFI 输入均视为不可信，并在 Rust 领域边界重新验证。
- FFI DTO 设置长度、分页大小、枚举和嵌套深度限制。
- Rust panic 不得跨越 FFI；必须转换为稳定错误码和可本地化错误信息。
- Windows WebView 只能调用显式 Tauri commands；使用 capability allowlist，不开放通用 shell、文件系统或前端任意 HTTP。
- 主 WebView 使用严格 CSP，仅加载打包资源；不加载远程脚本、文章 HTML 或第三方页面。
- 外部原文统一交给系统浏览器打开。

#### 网络与 SSRF 防护

所有来源请求由 Rust 共享网络层执行，并采用独立于 AI provider 的网络策略。

**公开来源策略：**

- 仅允许 HTTP/HTTPS；默认推荐 HTTPS。
- 拒绝 loopback、link-local、私有、组播、保留和未指定地址。
- DNS 解析后验证所有候选 IP；实际连接地址必须属于已验证集合。
- 每次重定向重新执行 scheme、host 和 IP 校验。
- 限制重定向次数、响应体大小、压缩展开大小、连接/首字节/总超时及每主机并发。
- 不接受无效 TLS 证书，也不提供“忽略证书错误”开关。
- Feed 返回的 URL 只能用于溯源或后续受控请求，不能自动转成本地文件或命令。

**AI provider 策略：**

- 公网 provider 使用 HTTPS 和系统信任链。
- 本地模型端点只能通过显式“本地 AI provider”模式允许 loopback。
- 本地端点授权不能复用于 RSS、自定义来源或重定向目标。
- base URL、协议类型和允许的数据范围作为独立配置保存。

#### 第三方 AI 数据边界

- 默认不发送 API Key、完整用户反馈、收藏历史、无关本地记录或诊断信息。
- 默认发送标题、必要摘要/正文片段、来源类型和分析所需元数据。
- 首次启用 provider 时展示数据接收方、发送字段和保留风险。
- 用户可以按来源关闭 AI 分析。
- 每次分析记录 provider、模型、输入 hash、策略版本和发送字段类别，但不记录完整 prompt 或 secret。
- provider 变更后，旧分析结果继续保留其原始来源标识，不伪装成新 provider 的结果。

#### 日志与诊断

- 结构化日志仅记录操作类型、来源 ID、状态码、耗时、计数和稳定错误分类。
- URL 默认移除 query 和 fragment；Authorization、Cookie、API Key、正文和 prompt 必须脱敏。
- 诊断导出采用明确 allowlist，禁止直接打包应用数据目录。
- 生产日志采用大小和期限轮转；详细网络 payload 只允许在显式、临时的开发诊断模式使用。
- 用户删除 secret、来源或正文后，相关缓存、索引和诊断引用必须按生命周期规则清理。

#### 供应链与发布安全

- Cargo、pnpm、Swift Package Manager 和 Gradle 均提交锁文件。
- CI 执行依赖漏洞、许可证和 secret 扫描。
- 正式包禁止调试 capability、测试 API Key、开发服务器地址和宽松 CSP。
- Windows、Apple、Android 分别使用平台签名；签名密钥只存在于受控发布环境。
- 自动更新不进入首个实现闭环；启用时必须验证签名并保留迁移回滚策略。

#### FR59–FR63 安全增量

**配置风险确认凭证：**

- `ConfigurationValidationReceipt` 是共享核心生成的高熵、不透明、单次使用句柄，不是授权令牌，不能绕过核心校验。
- 核心只在内存中保存 receipt 对应的规范化配置 hash、验证器版本和风险代码；receipt 不进入 SQLite、日志、诊断或遥测。
- 保存时重新规范化并重新校验配置；配置 hash、验证器版本或风险集合不一致时拒绝 receipt。
- receipt 使用后立即失效，进程重启后全部失效并要求重新验证；阻断错误无论是否携带 receipt 都不得保存。

**Windows 单实例入口：**

- Windows 使用锁定版本的 `tauri-plugin-single-instance 2.4.3`，并按官方要求作为首个插件注册。
- 重复启动回调收到的参数和工作目录全部视为不可信；默认忽略工作目录。
- 只接受“激活现有窗口”或符合 allowlist 的应用深链，并限制参数数量、单项长度和总长度。
- 深链只允许稳定情报 ID 和固定目的地，不接受文件路径、脚本、任意 URL、shell 参数或 secret。
- 参数必须在 Rust 平台适配层解析和验证，不得直接转发给 WebView；无效参数只激活现有窗口，不执行附加动作。
- 回调只允许显示、恢复、聚焦现有主窗口或请求任务栏注意；单实例插件不向 JavaScript 暴露 capability。

**同步结果与用户状态隐私：**

- 普通诊断只记录来源 ID、同步计数、状态码、耗时和稳定错误分类。
- 最小结果中的标题、原文链接、发布方不得进入默认诊断导出。
- 用户处理状态、收藏和价值反馈不得进入网络日志或第三方 AI 请求。
- 用户主动数据导出可以包含这些状态，但必须明确数据范围。
- 同步结果查询继续使用分页和长度限制，防止 WebView/FFI 超量请求。

**安全验收：**

- 伪造、过期、重复使用和配置已变化的确认 receipt 均被拒绝。
- 第二次启动携带超长参数、文件路径、私网 URL、未知协议或畸形深链时，只激活现有窗口。
- 同步摘要、诊断导出和日志中不出现标题、完整 URL、处理状态、API Key 或正文。
- 窗口可见、最小化和托盘隐藏时重复启动均不创建第二个可交互实例。

#### 级联影响

- API/通信设计必须定义统一错误模型、取消、超时和任务进度事件。
- 平台层通过 Application Command 与持久 `PlatformEffect` outbox 完成密钥会话、通知、后台调度、外链和系统权限握手，不向 Rust 注册长期回调。
- 测试必须覆盖 DNS 重绑定、重定向到私网、超大响应、日志脱敏和 secret 删除。
- 整库加密被明确列为延后决策，不能在实现中被某个平台自行加入。

### API 与通信模式

#### 总体通信模型

MVP 不引入本地 Web Server、REST、GraphQL、gRPC 或云 API。内部通信分为平台 UI、平台类型安全包装、Application API（Commands / Queries / Tasks）、`radar-core` 领域与持久化、平台 Ports 五层。

- UI 只能调用应用用例，不能绕过应用层调用数据库或来源适配器。
- 写操作使用 Command，读操作使用 Query，长任务使用持久化 Task。
- 所有平台使用同一用例名称、输入语义、错误码和结果模型。
- 平台包装层负责把共享 DTO 转成 Swift、Kotlin、TypeScript 的展示模型。

#### 应用 API 形态

```text
query_items(QueryItemsInput) -> Page<IntelSummary>
get_item(ItemId) -> IntelDetail
save_source(SaveSourceInput) -> SourceView
save_rule(SaveRuleInput) -> RuleView
preview_rule(PreviewRuleInput) -> RulePreview
start_sync(StartSyncInput) -> TaskRef
start_analysis(StartAnalysisInput) -> TaskRef
get_task(TaskId) -> TaskSnapshot
cancel_task(TaskId) -> CancelResult
get_app_status() -> AppStatus
export_diagnostics(ExportOptions) -> ExportResult
```

- 禁止 `execute_sql`、`fetch_url`、`read_file` 等通用高权限接口。
- Command 返回提交后的版本号或稳定 ID。
- Query 使用不透明 cursor 分页，不暴露数据库 offset 或 rowid。
- 列表 DTO 不包含正文、大型 payload 或完整分析输入。
- 所有 DTO 包含 `contract_version`；变更优先采用向后兼容的新增字段。
- 不使用跨语言继承、泛型回调图或可变共享对象。

#### 长任务和进度

- MVP 不跨 FFI 暴露 Rust Future、Stream 或长生命周期异步回调。
- `start_*` 立即返回 `TaskRef`，`radar-core` 在自己的 Tokio runtime 中执行网络与任务编排。
- 任务状态持久化为 `queued/running/retry_wait/succeeded/partially_succeeded/failed/cancelled`。
- 前台界面只在任务活跃时轮询 `get_task()`；后台运行不维持 UI 订阅。
- 所有状态快照包含单调递增 `revision`，相同 revision 不触发 UI 重绘。
- Windows 可发送轻量 Tauri invalidation event 提醒 UI 立即查询，但事件不作为事实源。
- 取消采用 cooperative cancellation；已提交的来源事务不回滚，未开始的步骤停止。
- 每个任务接收明确 `ExecutionBudget`，包括截止时间、最大来源数、网络与 AI 并发上限。

#### 平台绑定

**Windows：**

- TypeScript `DesktopApi` 封装全部 `invoke()`。
- React 组件和状态层不得直接调用 Tauri API。
- Tauri commands 均为异步命令，阻塞数据库工作进入专用执行器。
- event payload 只包含 `{ entity, id, revision }` 或任务 ID。

**Apple：**

- `RadarCoreClient` Swift actor 包装 UniFFI 生成接口。
- SwiftUI 只与 `@MainActor` ViewModel 交互。
- FFI 调用放入受控后台执行器，不在主线程执行数据库或网络工作。

**Android：**

- `RadarCoreClient` 作为 repository 实现，使用 Kotlin coroutine dispatcher 包装调用。
- Compose ViewModel 暴露不可变 `StateFlow`。
- FFI 阻塞调用不在 Main dispatcher 运行。

三平台包装层必须通过共享契约 fixtures；平台 UI 不重新实现领域规则。

#### 平台效果握手

移动端不向 Rust 注册长期 callback。三平台统一使用“平台触发 + 持久 outbox + 结果回报”：

```text
平台调度器触发 Application Command
  → core 执行并持久化任务
  → core 写入 PlatformEffect outbox
  → 平台读取并执行效果
  → 平台通过 Application Command 回报结果
```

- `PlatformEffect` 至少包含稳定 effect ID、幂等键、类型、payload version、过期时间和执行状态。
- 通知由 core 生成确定性 `NotificationEffect`；平台提交系统通知后回报 delivered、denied、expired 或 failed。
- 调度器只触发 `start_sync(reason)`，不承担同步规则；深链接由平台解析后转换为 `AppDestination`。
- AI 密钥从平台安全存储临时取出，以非持久 `SecretLeaseInput` 提供给一次执行会话；排队任务不得保存明文密钥。
- Windows 即使能直接实现 Rust Port，也遵循同一握手语义，避免三端副作用行为分叉。

#### 错误模型

```text
AppError {
  code
  category
  message_key
  retryability
  source_id?
  task_id?
  details_allowlisted
  correlation_id
}
```

稳定类别为 `validation`、`not_found`、`conflict`、`permission`、`network`、`rate_limited`、`source_format`、`provider`、`storage`、`migration`、`cancelled`、`internal`。

- `message_key` 由平台本地化，Rust 不返回面向用户的拼接长文。
- 原始底层错误只进入脱敏日志。
- `retryability` 明确为 `never/manual/automatic/after`。
- 部分成功返回成功结果和来源级问题列表，不伪装成整体失败。
- 未知错误统一映射为 `internal`，同时生成 correlation ID。

#### 来源与 AI 适配器协议

```text
SourceAdapter
  validate_config()
  fetch_page(cursor, conditional_headers, budget)
  normalize(raw_item)
  classify_error()

AiProvider
  probe_capabilities()
  analyze(input, schema, budget)
  classify_error()
```

- 来源适配器不直接写数据库或发送通知。
- 适配器返回版本化领域候选和新的游标；应用服务负责事务提交。
- GitHub、arXiv、RSS/Atom 使用各自 adapter，共享 HTTP policy。
- AI provider 必须先执行能力探测，再选择严格结构化输出或本地 schema 校验。
- 第三方响应 fixture 是适配器契约测试的标准输入。

#### HTTP 与异步运行时

锁定已核验候选版本 `reqwest 0.13.4`、`tokio 1.53.1`、`serde 1.0.229`，并提交 Cargo lockfile。

- 来源与 AI provider 使用不同的 `reqwest::Client` 和网络策略。
- 禁用 cookie store。
- 禁用隐式系统/环境代理；代理支持若进入后续版本，必须显式配置并重新评估 SSRF 边界。
- 使用自定义 redirect policy，不接受默认自动重定向行为。
- 全局、每主机和 AI 分别设置并发 semaphore。
- 保存 `ETag`、`Last-Modified`、分页游标和 rate-limit 状态。
- GET 可按错误类别自动重试；429 尊重 `Retry-After`，5xx 使用带抖动退避。
- AI POST 不在 HTTP 层盲目重放；由持久分析任务根据输入 hash、尝试次数和失败阶段决定是否重试。
- HTTP/3 等不稳定功能不进入 MVP。

#### 契约与版本治理

- Rust DTO 是运行时契约的权威来源。
- `contracts/schemas` 保存对外 fixture、枚举和错误码的可读镜像。
- UniFFI 绑定、TypeScript DTO 和契约文档由同一版本生成或校验。
- CI 检查生成产物是否与 Rust 定义同步。
- 删除字段、改变枚举含义或改变错误语义必须创建显式迁移 ADR。
- 应用与核心随同一安装包发布，不承担任意版本远程兼容；持久任务和数据库中的 payload 必须支持升级恢复。

#### FR59–FR63 Application API 增量

```text
get_sync_result(SyncRunId, Cursor?) -> SyncResultPage
set_user_processing_state(SetProcessingStateInput) -> ProcessingStateView
validate_configuration(ValidateConfigurationInput) -> ConfigurationValidationResult
save_configuration(SaveConfigurationInput, ValidationReceipt?) -> ConfigurationView
get_setup_progress() -> SetupProgress
save_setup_step(SaveSetupStepInput) -> SetupProgress
take_pending_activation() -> AppDestination?
```

**同步结果合同：**

- `SyncResultPage` 包含同步运行 ID、起止时间、成功/部分成功/零结果/失败状态、三类来源计数、来源级问题和分页最小规范化结果。
- 最小结果字段固定为来源类型、发布方、原始标题、可用时的发布时间、采集时间和原文链接；查询不得连接 AI、评分、FTS 或完整正文。
- `TaskSnapshot` 成功或部分成功后携带 `result_ref = SyncRunId`；`partially_succeeded` 是正常终态，不通过异常通道返回。
- UI 收到任务 revision 变化后查询结果；事件只负责失效通知，重复查询无副作用。

**处理状态命令：**

- `SetProcessingStateInput` 包含情报稳定 ID、`unseen | judged | research_later` 目标状态、客户端已知 revision 和幂等请求 ID。
- 核心拒绝未知状态和过期 revision；查询、打开详情、收藏、取消收藏、正文删除和 AI 操作均不得调用该命令。

**配置验证协议：**

- `ConfigurationValidationResult` 明确返回 `blocking_errors`、`narrowing_risks`、可选 `validation_receipt`、`validator_version` 和 `normalized_config_hash`。
- 阻断错误包含字段路径、稳定错误代码和修正提示键。
- 仅存在过窄风险时返回 receipt；无风险配置不要求确认。
- 保存时 receipt 不匹配映射为 `validation/stale_validation_receipt`，不得映射为 `internal`。

**配置引导：**

- `SetupProgress` 包含稳定步骤 ID、完成状态、已保存字段版本和下一建议步骤。
- 保存步骤与保存业务配置复用同一核心校验；跳过只改变引导进度，不删除已保存配置。
- 设置根页固定入口和两次导航限制属于平台路由验收，不进入领域 API。

**Windows 激活通信：**

1. Rust 平台适配器验证重复启动参数。
2. 合法 `AppDestination` 写入有界进程内 `PlatformActivationQueue`；相同目的地合并。
3. 平台显示并聚焦现有窗口，只发送 `{ entity: "activation", revision }` 失效事件。
4. UI 调用 `take_pending_activation()` 获取已验证目的地；无合法目的地时仅恢复当前窗口上下文。

激活队列不是持久业务事件源，不得向 WebView 直接发送原始参数。

**契约测试增量：**

- 三端共用 fixtures 验证同步完整成功/部分成功/零结果/失败、三态处理状态与过期 revision、四类阻断错误、两类过窄风险、receipt 失效/重复使用、配置引导中断恢复，以及合法/畸形/超长 Windows 激活参数。

- 测试需要覆盖取消、超时、部分成功、重复调用、旧任务恢复和未知枚举。

### 前端架构

#### 总体原则

- 三个平台共享领域语义、DTO、错误码、深链接和验收行为，不共享 UI 代码。
- UI 层只负责展示、输入、导航和平台交互；筛选规则、去重、任务恢复和权限判定不在 UI 重写。
- 持久数据以 `radar-core` 为事实源；平台缓存只是可丢弃投影，不能变成第二个事实源。
- 后台事件只触发按 revision 重新查询，不直接拼接或修改领域对象。

单向数据流为 `View → Intent → ViewModel/Hook → RadarCoreClient → DTO/AppError → Query/State → Render State → View`。

#### Windows React 架构

采用 feature-first 目录：

```text
src/
  app/
    providers/
    router/
    shell/
  features/
    intel-feed/
    intel-detail/
    search/
    sources/
    rules/
    sync/
    settings/
    diagnostics/
  components/
    ui/
    domain/
  stores/
    ui-store.ts
    workspace-store.ts
  lib/
    desktop-api/
    errors/
    query-keys/
    deep-links/
```

**状态职责：**

- TanStack Query `5.101.4` 管理情报列表和详情、搜索与筛选结果、来源、规则、设置、同步任务、诊断和应用状态，以及所有通过 `DesktopApi` 异步获得的数据。
- Zustand `5.0.14` 只管理侧栏折叠、工作区布局、非路由型弹窗、临时筛选面板、命令面板和纯展示偏好。
- 组件本地状态管理输入焦点、未提交表单、单组件 tab、popover、dropdown 和临时确认状态。

禁止把领域 DTO 放入 Zustand、使用 `useEffect` 调用 `DesktopApi`、组件直接调用 Tauri `invoke`、创建数据与 UI 混合的巨型 store，或将数据库设置复制到 localStorage。

**Query 与 Mutation：**

- Query key 使用层次结构，例如 `['intel', 'list', normalizedFilters]`、`['intel', 'detail', id]`。
- 保存来源、规则或设置成功后，按领域根 key 失效相关查询。
- mutation 返回的 revision 用于避免重复刷新。
- 收藏等可逆、低风险操作可以乐观更新并提供 rollback。
- 删除、规则生效、来源配置、数据清理和 AI 发送设置不得乐观提交。
- 后台任务活跃时使用自适应轮询；进入终态立即停止。
- 窗口重新聚焦不默认触发联网，只重新查询本地核心状态。

**Windows 路由：**

- 使用 React Router `8.3.0` Declarative Mode。
- 不使用 loader/action 作为第二套数据层，数据读取统一由 TanStack Query 完成。
- 路由包括 `/intel`、`/intel/:id`、`/search`、`/favorites`、`/sources`、`/rules`、`/sync`、`/settings`、`/diagnostics`。
- 过滤条件可进入 URL search params；纯布局状态不进入 URL。

#### Apple 前端架构

- 使用 SwiftUI、`@MainActor` ViewModel 和 Observation。
- `RadarCoreClient` actor 是共享核心的唯一入口。
- ViewModel 发布不可变 `ViewState`，View 发送明确 intent。
- iPhone 使用 `NavigationStack` 和底部 Tab；iPad 使用 `NavigationSplitView`，按 size class 在多栏和单栈间折叠。
- 选中情报 ID 属于导航状态；情报详情始终通过核心查询。
- 长任务采用 Swift Task 管理轮询生命周期，页面离开时取消 UI 观察，不取消后台核心任务。
- Dynamic Type、可见标签、焦点顺序和 Reduce Motion 是组件验收条件；当前产品不承诺盲人屏幕阅读器支持。

#### Android 前端架构

- 使用 ViewModel、不可变 `UiState`、`StateFlow` 和单向 intent。
- `RadarCoreClient` repository 是共享核心唯一入口。
- 使用 Navigation 3 `1.1.4` 稳定版管理显式 back stack。
- 使用 Material 3 Adaptive `1.2.0` 稳定版构建手机单栈、平板和折叠屏列表—详情布局。
- 不在 Composable 内直接调用 FFI、数据库或网络。
- `SavedStateHandle` 只保存轻量导航 key 和未提交 UI 状态，不保存情报 DTO。
- 系统返回、预测返回、window insets、旋转、多窗口和进程重建必须有测试。

#### 共享导航与深链接

定义平台无关的 `AppDestination`：`feed(filters?)`、`intel_detail(item_id)`、`search(query?)`、`favorites`、`sources(source_id?)`、`rules(rule_id?)`、`sync_result(sync_run_id)`、`settings(section?)`、`diagnostics(correlation_id?)`。

- 通知只携带稳定 destination 和领域 ID。
- 各平台负责将 `radar://...` 解析为本地导航状态。
- 找不到目标记录时显示可恢复错误，不自动导航到任意网页。
- 深链接不得携带 API Key、正文、prompt 或敏感查询参数。

#### 组件边界

三平台分别实现 `IntelSummaryRow`、`EvidenceDetail`、`ProvenanceSection`、`ConfidenceIndicator`、`RuleEditor`、`RuleImpactPreview`、`SourceStatus`、`TaskProgress`、`PartialSuccessBanner`、`EmptyState`、`DiagnosticExport`。这些名称表示共享语义，不要求像素或代码一致；组件只能接收展示 DTO 和 intent closure。

#### 表单与验证

- 平台端提供即时格式提示和无障碍错误关联。
- 保存前统一调用核心验证；核心返回字段级稳定错误码。
- 表单 draft 保留在页面或 ViewModel，只有保存成功后才更新查询缓存。
- 离开脏表单时提示用户；不得默默保存部分配置。
- 规则编辑器的“预览影响”和“保存生效”是两个独立 command。

#### 加载、错误与恢复状态

所有核心页面必须显式覆盖首次加载、保留旧数据的刷新、空结果、离线缓存、来源部分失败、AI 等待或失败、权限拒绝或撤销、迁移只读诊断、任务取消、成功及可撤销反馈。列表刷新时保留已有内容；错误状态不得覆盖仍然可用的数据。

#### 性能策略

- 所有列表采用惰性/虚拟化渲染和 cursor 分页。
- 详情按 ID 查询；列表 DTO 不携带正文。
- Windows 在 hover/键盘选中稳定后预取详情；iOS/Android 在即将导航或选中稳定后预取。
- 搜索输入防抖，取消旧查询并以 query key 隔离结果。
- 设置、诊断等低频页面延迟加载。
- Windows 不启用 SSR、PWA 或 Service Worker。
- 避免把大型正文送入全局响应式状态。

#### 设计系统与无障碍

- 共享语义 token：颜色角色、间距等级、重要度、来源可信度、AI 状态和错误严重度。
- Windows 使用 shadcn/ui 组件组合；Apple 和 Android 使用平台原生组件。
- 状态不能只靠颜色表达。
- 触控目标、键盘操作、焦点可见性、稳定自动化语义和动态字体分别通过平台门禁验证；稳定名称、角色和状态继续服务 UI Automation 与一致交互，但不构成盲人屏幕阅读器支持声明。
- 动画只用于导航关系和状态变化，并尊重 Reduce Motion/系统动画设置。

#### FR59–FR63 前端增量

**新增功能边界：**

三端建立一致的 `sync-results`、`processing-state`、`setup-guide`、`configuration-validation` feature；分别实现 `SyncResultSummary`、`SyncResultItem`、`ProcessingStateControl`、`SetupGuideEntry`、`ConfigurationValidationSummary`。组件只接收展示模型和 intent，不计算来源计数、风险类别或状态转换。

**Windows Query 与路由：**

- 新增 query keys：`['sync', 'result', syncRunId, cursor]`、`['intel', 'processing-state', itemId]`、`['setup', 'progress']`、`['configuration', 'validation', normalizedDraftHash]`。
- 新增或细化 `/sync/:syncRunId`、`/settings`、`/settings/setup`；设置根页直接显示“配置引导”入口，从主情报流到该入口最多两次用户导航操作。
- 激活队列提供合法目的地时才触发路由导航；无目的地时保持当前路由、筛选、滚动、选择和未提交表单。
- 重复启动不得重新创建 Router、QueryClient 或 Zustand stores。

**三态处理状态：**

- UI 固定显示“未查看 / 已判断 / 待研究”，只有显式 mutation 能改变状态；打开列表或详情不得触发 mutation。
- 收藏 mutation 只更新/失效收藏投影，不修改处理状态；处理状态 mutation 不修改收藏、价值反馈或 AI 查询。
- revision 冲突时重新查询并提示用户，不静默覆盖。

**同步结果页面：**

- 任务进入成功或部分成功终态后，根据 `result_ref` 打开结果；先展示同步摘要和来源级计数，再分页加载最小结果。
- 零结果是成功终态，不进入错误组件；部分成功同时保留成功条目和失败来源恢复动作。
- AI 状态只附着于分析区域，不控制同步结果的加载和可见性。

**配置验证 UI：**

1. 将当前 draft 提交给 `validate_configuration`。
2. 有阻断错误时关联字段、聚焦首错并禁止保存。
3. 只有过窄风险时展示风险摘要，允许返回修改或明确确认。
4. 无风险时直接保存。
5. receipt 过期时保留 draft 并重新校验，不显示为系统故障。

平台 ViewModel/Hook 只按稳定代码选择文案和焦点目标，不自行重算风险。

**配置引导恢复：**

- `SetupProgress` 是核心事实源；未提交字段留在页面状态，已保存字段来自核心查询。
- 跳过、关闭或生命周期中断不清除已保存内容；入口显示当前进度，但不得把完整业务配置复制到 UI store 或平台偏好存储。

**Windows 单实例激活：**

- 单实例回调不直接操作 React；UI 只响应 activation revision 并调用 `take_pending_activation()`。
- 相同目的地保持草稿和焦点；不同目的地遵循现有离开脏表单确认；无目的地只恢复窗口。
- 无法获得系统焦点时使用平台任务栏注意反馈，不创建应用内伪窗口。

**前端验收：**

- 三端共同验证同步成功/部分成功/零结果/AI 失败、三态与收藏组合、设置入口两次导航内可达、四类阻断错误/两类风险/无风险保存，以及中断后引导恢复。
- Windows 另验证窗口可见、最小化、托盘隐藏时重复启动，Router、QueryClient、stores 和未提交表单均不重置。

#### 级联影响

- 实现模式必须定义 Query key、ViewState、Intent、DTO 映射和错误展示规范。
- 工程结构需要为三平台建立相同领域 feature 名称。
- UX spine 必须把完整 UX 规格压缩成可实施的共享语义与平台差异合同。
- 测试需覆盖导航恢复、query invalidation、错误保留旧数据，以及稳定名称、角色、状态和焦点顺序的自动化语义。
- 不允许某个平台把本地数据库 DTO 直接当作长期 UI 可变状态。

### 基础设施与部署

#### 运行基础设施

- MVP 不部署业务后端、云数据库、容器集群或常驻远程服务。
- 数据库、规则执行、迁移与 AI 编排均在设备端完成；网络仅用于用户配置的数据源和 AI 服务。
- MVP 不接入远程遥测、远程配置或云端崩溃收集。
- 系统规模通过本地索引、分页、限并发和任务预算纵向治理，不设计水平扩展。

#### 工具链与版本治理

- Node.js 使用 24 LTS；根目录 `packageManager` 字段锁定精确 pnpm 版本。
- `rust-toolchain.toml` 锁定 Rust stable 工具链；提交 `Cargo.lock`、pnpm lockfile 和 Gradle Wrapper。
- Apple CI 锁定 Xcode 26.x 镜像，但最低运行目标仍为 iOS/iPadOS 17+。
- Android 使用 JDK 21；AGP、Kotlin 与 Compose 版本由验证通过的工程模板和版本目录固定。
- 依赖升级只能通过显式 PR 完成，不允许 CI 自动漂移工具链或锁文件。

#### 持续集成

GitHub Actions 分为相互独立、可定位失败责任的质量通道：

- `core`：Rust format、Clippy、单元测试、SQLite 迁移、golden fixtures 和确定性测试。
- `bindings`：生成 UniFFI Swift/Kotlin 绑定，检查生成结果无未提交差异，并执行编译冒烟测试。
- `windows`：冻结锁文件安装、类型检查、lint、测试、Tauri 构建和 NSIS 安装包验证。
- `apple`：Swift 测试、模拟器构建；只有受保护发布任务可生成签名归档。
- `android`：Gradle test、lint、assemble 和关键设备测试；发布任务生成签名 AAB。
- `security`：依赖审计、secret 扫描、许可证清单和 SBOM。
- `performance`：核心基准与约定数据规模门禁，不把不稳定端到端计时作为唯一判定。

PR 构建不读取签名密钥。分支保护至少要求核心、绑定契约和受影响平台通过。Action 固定到受支持主版本。

#### 配置、秘密与诊断

- 仅定义 `development`、`test`、`release` 三类构建配置，它们不对应云端环境。
- 非敏感来源预设、JSON Schema 和能力清单随应用打包。
- 用户 AI 密钥只进入平台安全存储，不进入 SQLite、日志、环境文件或安装包。
- 代码签名凭据只存在于 CI 的受保护发布环境中，PR 和 fork 构建不可访问。
- 本地日志采用结构化、滚动、限额与默认脱敏策略；采集、AI 调用和规则执行携带 correlation ID。
- 设置页展示来源健康度、最后成功时间、失败原因和重试状态；诊断包仅由用户主动导出并再次脱敏。

#### 打包与受控分发

- 三平台共享语义版本，平台构建号独立单调递增。
- Windows Phase 1 生成 x64 NSIS 当前用户安装包；受控手动安装验收可使用尚未取得 Windows 生产代码签名的候选构建，首版不同时维护 MSI。WebView2 使用系统运行时或 Tauri 推荐的 bootstrapper 策略。
- Apple 生成签名归档并通过 TestFlight 受控分发；首版不进入公开 App Store 发布。
- Android 生成签名 AAB 并通过 Google Play Internal Testing 分发；debug APK 只供开发使用。
- MVP 不实现应用内自动更新，升级通过新的受控构建完成。
- 每个发布版本附带应用版本、平台构建号、数据库 schema 版本、core commit、校验和、SBOM 和迁移说明。

**Windows 签名与分发边界：**

- Apple 与 Android 候选构建的受控测试签名、安装资格和隐私披露要求保持不变。

#### FR59–FR63 CI 质量通道

- `state-consistency`：验证三态处理状态与收藏/未收藏六种组合，以及浏览、详情、收藏、正文删除、重启、离线恢复和升级后 AI、价值反馈与处理状态互不覆盖。

- `windows-lifecycle`：验证正常窗口、最小化、托盘隐藏时重复启动、单可交互实例、路由/筛选/选择/草稿保持，以及畸形、超长和禁止类型启动参数。
- `sync-consumption`：使用三类来源的新增、更新、跳过、失败和零结果固定响应集，验证计数 100% 一致、部分失败不隐藏或回滚成功结果，并在无 AI Key 时访问最小结果。

### 决策优先级分析

**阻塞实现的关键决策：**

1. 共享 Rust 核心是数据库、确定性领域规则、任务状态和跨平台契约的唯一权威。
2. SQLite 采用单写执行器、WAL、显式迁移与恢复点，平台层不得直接访问数据库。
3. UniFFI 只暴露窄 DTO、Command、Query 和持久 Task，不跨边界暴露数据库连接、Future、Stream 或复杂回调。
4. 原始事实、规则判定与 AI 结果分层存储，AI 失败不得阻断采集和本地浏览。
5. 网络、密钥、通知和后台调度通过平台 Port 隔离，并执行 SSRF、重定向、大小、超时和脱敏策略。

**塑造架构的高优先级决策：**

- 三套平台原生 UI 共享领域语义而不共享 UI 代码。
- Windows 使用 TanStack Query 管理异步核心数据，Zustand 仅管理纯 UI 状态。
- Apple 与 Android 分别使用 `@MainActor` ViewModel/Observation 和 ViewModel/StateFlow 的单向数据流。
- 所有发布均通过跨平台 CI、契约 fixtures、迁移门禁和受控测试通道。

**实现后可继续优化的决策：**

- 具体预取阈值、查询缓存时长、日志轮转上限和并发预算。
- 公开商店分发、自动更新、数据库整库加密和远程诊断。
- 更高级的语义合并、代理支持和公共插件机制。

### 决策影响分析

**推荐实现顺序：**

1. 建立 monorepo、三平台壳工程、Rust workspace、锁文件和基础 CI。
2. 完成最小 UniFFI 往返、统一 DTO/AppError 和三端编译冒烟测试。
3. 实现 SQLite schema、迁移、单写执行器、任务恢复与 fixtures。
4. 实现 HTTP policy 和 RSS/Atom、GitHub Releases、arXiv 适配器。
5. 实现规则、搜索、AI provider 与通知判定。
6. 按共享 destination、ViewState 与验收语义构建三端 UI。
7. 完成安全、性能、无障碍、升级恢复和受控分发门禁。

**跨组件依赖：**

- UI 查询、后台任务和通知均依赖稳定的 Application API、revision 和错误分类。
- AI、来源适配器和诊断依赖统一 HTTP policy、ExecutionBudget 与 correlation ID。
- 三平台构建依赖同一 Rust core 版本、生成绑定和契约 fixtures。
- 分发签名前必须先证明数据库迁移、任务恢复和隐私边界在三端一致。

## 实现模式与一致性规则

### 模式类别与冲突点

已识别的主要冲突集中在数据库与代码命名、跨语言字段转换、feature 边界、测试位置、DTO 与时间格式、事件语义、状态所有权、加载与错误恢复、重试、验证和日志脱敏。以下规则对所有平台和实现代理具有约束力。

### 命名模式

#### 数据库命名

- SQLite 表、列和索引统一使用 `snake_case`。
- 表名使用复数，例如 `intel_items`、`sync_runs`。
- 主键统一为 `id`，外键统一为 `<entity>_id`。
- 索引使用 `idx_<table>_<columns>`；唯一约束使用 `uq_<table>_<columns>`。

#### API 与路由命名

- Rust Application API、DTO 字段和 JSON fixtures 使用 `snake_case`。
- Swift、Kotlin、TypeScript 包装层转换为语言惯用的 `camelCase`，不得改变字段语义。
- Windows 路由使用小写复数路径，例如 `/sources/:sourceId`。
- 深链接统一为 `radar://intel/<id>`、`radar://sync/<sync-run-id>`；`TaskId` 只查询任务进度，任务终态通过 `result_ref` 返回 `SyncRunId`。
- Command 使用动词命名，如 `save_source`；Query 使用读取语义，如 `query_items`；Intent 使用用户行为语义，如 `RetrySync`、`OpenIntelDetail`。

#### 代码命名

- Rust 类型、Swift/Kotlin 类型和 React 组件使用 `PascalCase`。
- React 文件使用 `kebab-case.tsx`；Swift/Kotlin 类型文件使用 `PascalCase`。
- 三端共享相同 feature 语义：`intel-feed`、`intel-detail`、`search`、`sources`、`rules`、`sync`、`settings`、`diagnostics`。
- 禁止使用 `SetEverything`、`CommonManager`、`MiscService` 等隐藏职责的泛化名称。

### 结构模式

- 业务代码按 feature 组织，不按 controller/service/model 类型建立全局大目录。
- Rust 单元测试与模块共置；跨模块测试放在 crate 的 `tests/`。
- React 测试与实现共置为 `*.test.ts(x)`。
- Apple 和 Android 测试保持平台标准 target/source-set，但路径镜像生产 feature。
- 跨平台契约样本只放在 `contracts/fixtures/`，不得复制进各端。
- 通用代码只有被两个以上 feature 使用且语义稳定后才能进入 `shared`、`lib` 或 `common`。
- 禁止建立无边界的 `utils`、`helpers`、`services` 杂物目录。
- 架构变化记录放入 `docs/adr/`；生成代码放入明确的 generated 目录并标记不可手工修改。

### 格式模式

#### Application API 返回格式

- 本地 Application API 返回类型化 DTO，不额外包装 `{data, error}`。
- 成功与失败通过语言结果类型表达；跨 FFI 错误统一映射为 `AppError`。
- 列表接口始终返回 `Page<T>`；单项接口不得返回单元素数组。
- 长任务启动接口返回 `TaskRef`，后续状态通过 `TaskSnapshot` 查询。

#### 数据交换格式

- JSON 字段使用 `snake_case`，枚举值使用小写 `snake_case`。
- ID 在边界上作为不透明字符串传递，UI 不得推断其格式。
- 时间统一传递带时区的 RFC 3339 UTC 字符串，展示层负责本地化。
- 布尔值只能使用 `true/false`。
- 可选值使用显式 optional/null；禁止以空字符串、零或 `unknown` 充当缺失值。
- 未识别的新枚举值映射到受控 `unknown` 展示状态并记录兼容性诊断。

### 通信模式

事件统一命名为 `core.<entity>.<action>.v1`，例如 `core.intel.changed.v1`、`core.task.progressed.v1` 和 `core.source.health_changed.v1`。

事件载荷统一包含 `event_version`、`entity`、`id`、`revision`、`occurred_at` 和 `correlation_id`。

- 事件仅表示“需要重新查询”，不携带完整领域对象，也不作为事实来源。
- 处理方必须容忍重复、乱序和晚到事件，并以 `revision` 判断是否刷新。
- 事件版本发生不兼容变化时创建新事件名，不在相同版本中改变载荷语义。

### 状态管理模式

- 所有 Render State 视为不可变快照。
- Rust core 是持久事实来源；平台缓存只保存可丢弃投影。
- Windows 的异步核心数据只进入 TanStack Query；Zustand 只保存纯 UI 状态。
- SwiftUI View 只与 `@MainActor` ViewModel 交互。
- Compose 只收集 ViewModel 暴露的不可变 `StateFlow<UiState>`。
- DTO 必须先映射为展示模型，不得成为长期可变 UI 状态。
- Query key 由集中式工厂生成，禁止组件手写字符串数组。
- 后台任务结束后按领域根 key 失效查询；事件不得直接修改缓存中的领域对象。

### 过程模式

#### 错误与加载状态

核心页面统一区分 `initial_loading`、`refreshing_with_data`、`empty`、`ready`、`partial_failure`、`blocking_failure` 和 `read_only_migration_failure`。

- 刷新失败时保留旧数据，不用全屏错误覆盖可用内容。
- 用户消息由 `message_key` 本地化；底层错误仅进入脱敏日志。
- 自动重试只服从 `AppError.retryability` 和 `ExecutionBudget`。
- UI 不自行实现无限重试或固定间隔轮询。
- validation 错误在保存时由 core 最终裁决，并稳定关联到字段键。
- Error Boundary 只处理程序缺陷，不代替预期业务错误状态。
- 部分成功必须同时展示成功结果和来源级问题，不折叠成整体失败。

#### 日志模式

结构化日志至少包含 `timestamp`、`level`、`component`、`operation`、`correlation_id`，并按需包含 `task_id`、`source_id` 和 `error_code`。

- 禁止记录 API Key、Authorization header、完整 prompt、完整正文或未脱敏 URL 查询参数。
- `error` 表示操作失败，`warn` 表示降级或可恢复异常，正常重试使用 `info` 或 `debug`。
- 用户可见错误必须能通过 correlation ID 对应到诊断记录。

### 强制执行指南

所有实现代理必须：

- 先复用既有类型、错误码、Query key、fixture 和 feature 名称。
- 修改跨平台契约时同步更新 schema、生成绑定和三端契约测试。
- 新增命名或模式前先搜索仓库中的既有约定。
- 不得绕过 Application API、直接访问 SQLite、Tauri `invoke` 或 UniFFI。
- 为每个新状态至少验证成功、空、加载、失败和恢复路径。
- 若必须偏离规则，先创建 ADR，说明原因、影响范围和迁移方案。

CI 通过 formatter、lint、契约生成差异、schema fixtures、架构边界测试和平台编译检查执行这些规则。

### FR59–FR63 一致性增量

#### 稳定命名

- 数据库固定使用 `intel_items.user_processing_state`、`sync_result_items.sync_run_id`、`sync_result_items.intel_item_id`、`sync_result_items.disposition`、`idx_intel_items_user_processing_state_collected_at` 和 `uq_sync_result_items_sync_run_id_intel_item_id`。
- `UserProcessingState` 枚举只允许 `unseen`、`judged`、`research_later`。
- `SyncRunOutcome` 枚举只允许 `succeeded`、`partially_succeeded`、`zero_results`、`failed`。
- 配置代码固定为 `expression_unparseable`、`value_out_of_range`、`lower_bound_above_upper_bound`、`invalid_source_or_unsupported_protocol`、`all_sources_disabled`、`all_high_trust_candidates_filtered`、`stale_validation_receipt`，平台不得定义别名。

#### 命令与查询

- Query 固定为 `get_sync_result`、`get_setup_progress`；Command 固定为 `set_user_processing_state`、`validate_configuration`、`save_configuration`、`save_setup_step`；Windows 平台命令固定为 `take_pending_activation`。
- 禁止创建 `mark_as_read`、`toggle_research`、`save_config_force`、`confirm_warning`、`get_latest_sync_items`、`open_second_instance` 等隐藏三态、确认凭证或指定同步运行语义的替代接口。

#### 状态正交规则

| 状态 | 唯一写入入口 | 禁止的隐式写入 |
|---|---|---|
| 用户处理状态 | `set_user_processing_state` | 浏览、详情、收藏、反馈、AI |
| 收藏 | 收藏命令 | 处理状态、正文删除 |
| 价值反馈 | 反馈命令 | 处理状态、收藏 |
| AI 状态 | 分析任务 | 用户处理状态 |
| 配置引导进度 | `save_setup_step` | 保存业务配置、导航 |
| 同步结果 | 同步任务事务 | UI 查询、AI 分析 |

任何跨列副作用必须先修改 PRD 与架构，不得由 Story 自行加入。

#### 同步结果格式

- `SyncResultPage` 使用 cursor 分页；来源计数逐项返回，不以单一 `success` 布尔值替代。
- `zero_results` 是明确成功结果，不使用空数组推断；部分成功同时包含 `items` 与 `source_problems`。
- 最小结果 DTO 不得复用 `IntelDetail`。
- 失效事件固定为 `core.sync.result_changed.v1`，只携带同步运行 ID 与 revision。

#### 配置验证过程

- 状态固定为 `pristine`、`dirty`、`validating`、`blocking_invalid`、`narrowing_risk`、`saving`、`saved`、`save_error`。
- `blocking_errors` 非空时清除任何 receipt；`narrowing_risks` 非空且无阻断错误时才显示确认操作。
- draft 改变后立即丢弃旧 receipt；过期 receipt 返回表单级 `stale_validation_receipt`，保留输入并重新验证。
- 禁止以 `forceSave`、`force: true` 或平台布尔值绕过共享验证。

#### Windows 激活

- 失效事件固定为 `platform.activation.changed.v1`，载荷只含通用事件元数据和 activation revision，原始进程参数永不进入事件。
- `take_pending_activation()` 只返回已验证 `AppDestination`；无合法目的地时不产生导航 intent。
- 激活不得重建应用根容器、打开第二窗口或清空页面状态。

#### Fixture 组织

```text
contracts/fixtures/
  sync-results/{succeeded,partially-succeeded,zero-results,failed}.json
  processing-state/
    six-state-favorite-combinations.json
    lifecycle-restoration.json
  configuration-validation/
    blocking/
    narrowing/
    valid/
    receipts/
  windows-activation/
    valid/
    malformed/
    oversized/
```

平台测试只能引用这些权威样本，不得复制并修改成本地版本。

#### 增量反模式

- 打开详情自动把 `unseen` 改成 `judged`。
- 使用收藏星标表达 `research_later`。
- 用空结果数组推断同步成功。
- 使用 `force: true` 保存风险配置。
- 将第二次启动原始参数直接发送给 React。
- 三个平台分别计算“过窄配置风险”。

### 正例

- `idx_intel_items_published_at`、`source_id`、`query_items`。
- React 通过集中式 `intelKeys.detail(id)` 查询详情。
- `core.task.progressed.v1` 只发送 task ID 与 revision，界面随后查询 `TaskSnapshot`。
- 刷新失败时展示已有情报和非阻塞错误横幅。

### 反模式

- React 组件在 `useEffect` 中直接调用 Tauri。
- SwiftUI View 或 Composable 直接调用 UniFFI。
- 三个平台分别定义含义不同的 `SyncError`。
- 事件携带完整 `IntelDetail` 并直接覆盖缓存。
- 在 Zustand、`SavedStateHandle` 或 SwiftUI 状态中长期保存数据库 DTO。
- 使用本地时间、整数布尔值或空字符串哨兵跨边界传输。
- 将新逻辑随手放入 `utils`，或复制 fixtures 到平台工程。

### 架构边界

#### API 边界

- `src-tauri/commands`、Apple `CoreBridge` 和 Android `corebridge` 是三个 UI 的唯一核心入口。
- 平台客户端只暴露已批准的 Application Command、Query 和 Task。
- `radar-ffi` 只转换稳定用例、DTO 和 `AppError`，不得承载业务判断。
- 禁止提供通用 SQL、任意 URL 请求、任意文件访问或反射式 command 接口。

#### 组件边界

- UI feature 只能通过平台 client 访问核心。
- feature 间通过导航、Intent 和共享查询失效协作，不直接修改彼此内部状态。
- `components/ui` 或 `DesignSystem` 只包含无领域判断的基础组件；领域组件进入明确 feature 或 `components/domain`。
- 各平台使用相同 feature 语义，但不要求目录大小写或像素实现相同。

#### 服务边界

- `radar-core` 可以依赖领域、Application API 和基础设施实现，但不得依赖 React、SwiftUI、Compose 或平台 SDK。
- 平台密钥、通知、调度和外链通过 Application Command、临时 secret 会话与 `PlatformEffect` outbox 握手；领域层不得导入平台类型或持有跨 FFI callback。
- 来源与 AI adapter 可以访问受控 HTTP client，但不能写数据库或发送通知。
- Application 层编排 adapter、事务、任务与 Port，是副作用顺序的唯一决策者。

#### 数据边界

- 只有 `radar-core/infrastructure/database` 可以执行 SQL。
- 领域模块不接收数据库连接；repository/transaction 能力通过明确内部接口提供。
- TanStack Query、Swift ViewModel 和 Android ViewModel 缓存均为可丢弃投影。
- `contracts/` 是跨平台 fixtures 与可读契约镜像的唯一位置；Rust 类型是运行时权威来源。
- `Generated/` 和 `generated/` 只能由 `cargo xtask bindings` 更新。

### 集成点与数据流

```text
Platform View
  → ViewModel / Hook
  → Platform Core Client
  → Tauri command or UniFFI
  → Application Command / Query / Task
  → Domain service
  → Database / Source / AI / Platform Port
  → DTO or AppError
  → Platform presentation model
  → Render State
```

- 外部输入只能从三个来源 adapter 或 AI provider adapter 进入。
- 所有响应先经过大小、重定向、SSRF、格式和 schema 验证。
- 通知、后台调度和密钥操作只能通过已定义 Command、临时会话和 `PlatformEffect` 离开核心。
- 核心事件只通知平台重新查询，不通过事件绕过 Application API 传递事实。

### 文件组织规则

- 根配置负责跨仓库工具链和一致性；平台配置留在各自工程。
- 配置文件不得包含真实 secret；测试 secret 使用进程内 fake provider。
- 测试与 feature 镜像组织；跨平台输入只引用 `contracts/fixtures`。
- 构建产物、签名文件、用户数据、真实密钥和本地数据库全部忽略。
- 生成绑定必须带生成器版本和不可手改声明。
- 静态品牌资源分别进入平台资源目录；共享语义 token 以可生成/校验的契约保存，不共享渲染资产。

### 开发工作流集成

- 根 Cargo workspace 构建核心、FFI 和 `xtask`。
- pnpm workspace 只管理 Windows Web 依赖，不承载 Apple/Android 业务代码。
- `cargo xtask bindings` 生成并验证移动端绑定。
- 平台开发可独立启动，但必须使用同一个锁定的 core commit。
- Release workflow 只消费已通过验证的源码与锁文件，不在发布阶段重新生成未审查的业务代码。
- PR 按变更路径触发相关平台构建，但修改 core、contracts、bindings 或 migrations 时强制触发全部平台契约门禁。

## 2026-08-12 FR64/NFR54 核心架构决策增补

本节同步已验证的 GitHub 项目条件化自动发现合同。若与正文中仅覆盖 FR1–FR63、NFR1–NFR53 或只描述固定 GitHub Release 关注的旧计数和概括性条款冲突，以本节为准；既有本地优先、共享 Rust 核心、三端原生 UI、单数据库所有者和平台副作用边界保持不变。

### 决策优先级

**阻塞实现的关键决策：**

1. GitHub 项目发现与 GitHub Release 同步是两个独立的 Application Task、Adapter、运行状态和故障边界。
2. GitHub 返回的稳定仓库数字 ID 是规范身份的首选；`owner/name` 是可变别名和无法取得稳定 ID 时的降级键。
3. 发现订阅、发现运行、项目身份、条件命中、带时间戳观测、关注优先级和订阅级忽略均由共享核心统一持久化和判定。
4. 同一规范仓库身份在当前设备最多形成一个项目对象和一个有效 Release 监控对象；数据库唯一约束是最终幂等防线。
5. 发现运行必须区分完整成功、成功零结果、部分完成、限流等待和失败；执行预算耗尽或分页未完成不得伪装成零结果。

**塑造架构的重要决策：**

- 订阅条件先规范化为跨维度 AND、同维度 OR 的稳定表达，再由 GitHub 查询约束与本地确定性 predicate 共同执行；远端查询结果不是最终领域判定。
- Star/Fork 增长只使用同一仓库至少两个成功、带时间戳的有效观测；请求失败、限流、缺失字段和首次观测均不产生增长命中。
- 关注优先级固定为 `fixed > active_auto > inactive_auto`；订阅级 ignore 只抑制该订阅，不覆盖固定关注或其他有效自动关注。
- 发现历史、Release、收藏、反馈和其他合法数据的保留独立于订阅启停和条件失配。

**明确延后：**

- 自动关注项目的产品容量上限、超限队列或淘汰策略尚未由 PRD 决定；实现不得声明无限容量、静默淘汰或自行添加上限。
- GitHub 私有仓库、组织授权、GitHub App、OAuth 登录、贡献者/Issue 活跃度和复杂趋势模型不进入 Phase 1。

### 数据架构

新增或扩展以下领域记录：

- `github_projects`：本地项目 ID、稳定 GitHub 仓库 ID、当前 `owner/name`、可选 `node_id`、公开状态、当前元数据及 revision。
- `github_repository_aliases`：历史 `owner/name` 与项目的映射，用于重命名、转移及旧链接回收；别名不能创建第二项目。
- `github_discovery_subscriptions`：名称、启用状态、规范化条件、条件版本、创建/更新时间及最近完成运行。
- `github_discovery_runs`：订阅、开始/结束时间、执行预算、最终 outcome、分页完成度、结果计数、错误与退避信息。
- `github_discovery_matches`：订阅、项目、首次命中时间、最近命中时间、分类、条件版本及命中依据版本。
- `github_discovery_evidence`：命中维度、预期条件、实际观测值和观测时间；多个订阅的依据分别保留。
- `github_metric_observations`：项目、观测时间、Star/Fork 值、采集状态和来源运行；只有成功且字段有效的观测可进入增长计算。
- `github_subscription_ignores`：订阅与项目的可撤销忽略关系；不得建成项目级全局删除标志。
- `github_monitoring_state`：固定关注和自动关注投影，最终有效监控状态由固定关注、有效订阅命中及用户控制共同计算。

核心约束：

- `github_projects.github_repository_id` 在可获得时唯一；降级身份使用规范化、不区分大小写的 `owner/name` 唯一键，并在取得稳定 ID 后事务性合并。
- Release 监控唯一键引用本地项目 ID，不引用可变仓库名称。
- 同一运行、订阅和项目只保留一条有效 match；依据可包含多个维度，但不能制造第二监控对象。
- 仓库身份合并必须在一个事务中重定向订阅命中、观测、Release 监控和历史关联；禁止删除合法历史。
- 增长窗口只选择窗口内首个与末个有效观测；不足两个有效值或比例增长首值为零时返回 `insufficient_baseline`，不是命中或零增长。

### API 与通信模式

共享 Application API 新增：

```text
create_github_discovery_subscription(input) -> GitHubDiscoverySubscriptionView
update_github_discovery_subscription(input) -> GitHubDiscoverySubscriptionView
set_github_discovery_subscription_enabled(input) -> GitHubDiscoverySubscriptionView
start_github_discovery(input) -> TaskRef
get_github_discovery_run(run_id, cursor?) -> GitHubDiscoveryRunPage
query_github_discovery_results(input) -> Page<GitHubDiscoveryResultSummary>
get_github_discovery_result(project_id, subscription_id?) -> GitHubDiscoveryResultDetail
ignore_github_discovery_result(input) -> GitHubMonitoringStateView
undo_github_discovery_ignore(input) -> GitHubMonitoringStateView
set_github_auto_monitoring_enabled(input) -> GitHubMonitoringStateView
convert_github_monitoring_to_fixed(input) -> GitHubMonitoringStateView
```

合同要求：

- 所有写命令携带客户端已知 revision 和幂等请求 ID；revision 冲突返回 `conflict`，不得静默覆盖。
- `GitHubDiscoveryRunOutcome` 只允许 `succeeded_with_results`、`succeeded_zero_results`、`partially_succeeded`、`rate_limited`、`failed`、`cancelled`。
- `GitHubDiscoveryResultClassification` 只允许 `new_discovery`、`newly_qualified`、`known_match`、`baseline_only`。
- 发现任务和 Release 同步分别返回自己的 TaskRef、result reference、revision 和错误列表；任一任务不得等待另一任务成功才公开自己的结果。
- 失效事件 `core.github_discovery.changed.v1` 只携带实体 ID 和 revision；不携带完整仓库响应或查询条件。

### 来源集成与执行预算

- 新增 `GitHubDiscoveryAdapter`，与 `GitHubReleaseAdapter` 分离，共享受控 HTTP policy、退避和诊断分类，但不共享运行状态或事务。
- 发现 Adapter 使用 GitHub 官方仓库搜索和仓库元数据响应，只返回分页候选、分页元数据和限流信息；不能写数据库、建立关注或计算最终用户状态。
- GitHub 搜索具有独立限流资源类别；执行器读取 `Retry-After`、`X-RateLimit-Remaining` 和 `X-RateLimit-Reset`，遵守 NFR24，禁止并发突发和退避期内重复请求。
- 分页依据官方 `Link` header 继续；每页、最大页数、截止时间和网络请求数进入 `ExecutionBudget`。预算用尽但仍存在下一页时，运行结果必须是 `partially_succeeded`。
- 远端搜索条件只用于缩小候选集；共享核心以规范化 subscription predicate 对候选元数据再次确定性验算，只有通过本地判定的项目才能进入自动关注。
- 任一页成功提交后可以保留已确认结果；后续页失败不得回滚已确认结果，也不得将运行标为成功零结果。

### 关注状态与历史保留

有效 Release 监控由共享核心计算：

```text
effective_release_monitoring = fixed_follow
  OR any(active_subscription_match AND auto_monitoring_enabled AND NOT ignored_for_that_subscription)
```

- `fixed_follow = true` 时，订阅停用、条件失配、订阅级忽略和自动关注停用均不得停止 Release 同步。
- 同一项目由多个订阅维持自动关注时，停用或忽略其中一个订阅不得停止其他有效订阅提供的监控。
- “停用自动关注”保留项目、依据和历史；没有固定或其他有效自动关注时才暂停后续 Release 同步。
- “转为固定关注”在事务中设置固定状态并保持同一 Release 监控身份，不新建任务或复制历史。

### 安全与隐私

- Phase 1 只发现公开仓库，不新增 GitHub 登录、OAuth、GitHub App 或长期 GitHub 凭据。
- 搜索文本、Topic、语言和阈值属于普通本地配置；不得包含 API Key、AI secret 或任意 URL 抓取能力。
- Adapter 只允许 GitHub 官方 API 主机和 HTTPS；不接受用户提供的发现 API base URL 或重定向到其他主机。
- 默认诊断只记录订阅 ID、运行 ID、页码、计数、状态码、限流信息和稳定错误分类，不记录完整搜索文本、项目描述或仓库响应。
- 忽略、停用和转固定属于本地用户行为，不发送给第三方 AI，也不写入网络日志。

### 前端架构

- 三端新增一致的 `github-discovery` feature，分别实现订阅列表/表单、运行摘要、发现结果、命中依据和监控控制；平台 ViewModel/Hook 不重新实现条件组合、增长判定或关注优先级。
- Windows 路由增加 `/sources/github/discovery`、`/sources/github/discovery/:subscriptionId` 和项目详情目的地；Apple/Android 使用对应原生导航状态。
- Query keys 按 subscription、run、result 和 project identity 分层；发现 revision 只失效发现投影，Release revision 只失效 Release 投影。
- 发现成功零结果、部分完成、限流和失败使用独立 Render State；已有结果刷新时保留内容。
- 忽略、停用和转固定不是乐观修改：核心返回合并后的 `GitHubMonitoringStateView` 后再更新投影，避免多订阅优先级在 UI 侧算错。
- UX Spine 的分类、关注、发现运行和 Release 同步四个独立维度是三端展示合同。

### 基础设施与质量门禁

新增质量通道：

## 2026-08-12 FR64/NFR54 实现模式与一致性规则增补

### 稳定命名

- SQLite 表、列、索引、Rust DTO 和 JSON fixtures 使用 `snake_case`；平台包装层仅在边界映射为语言惯用 `camelCase`。
- 数据表固定使用 `github_projects`、`github_repository_aliases`、`github_discovery_subscriptions`、`github_discovery_runs`、`github_discovery_matches`、`github_discovery_evidence`、`github_metric_observations`、`github_subscription_ignores` 和 `github_monitoring_state`。
- 项目稳定外键统一为 `github_project_id`；订阅外键统一为 `github_discovery_subscription_id`；发现运行外键统一为 `github_discovery_run_id`。
- 三端 feature 语义统一为 Windows `github-discovery`、Apple `GitHubDiscovery`、Android `githubdiscovery`；不得使用 `repo-radar`、`trending-projects`、`auto-watch` 等含义不同的别名。

稳定枚举：

```text
GitHubDiscoveryRunOutcome:
  succeeded_with_results | succeeded_zero_results | partially_succeeded |
  rate_limited | failed | cancelled

GitHubDiscoveryResultClassification:
  new_discovery | newly_qualified | known_match | baseline_only

GitHubMonitoringMode:
  fixed | automatic | automatic_disabled | none

GitHubGrowthEvaluation:
  matched | not_matched | insufficient_baseline | zero_ratio_baseline
```

平台只本地化显示文本，不得改变枚举含义或将未知值映射为成功。

### 条件与判定模式

- `GitHubDiscoveryConditionSet` 是发现条件的唯一权威合同；不同维度固定 AND，同维度多个值固定 OR。
- 远端 GitHub 查询仅缩小候选集；共享核心必须使用规范化 condition set 对返回候选再次执行确定性 predicate。
- 平台 UI 只展示核心返回的 `condition_summary`、字段级验证结果和命中依据，不拼接第二套查询语义。
- 条件保存沿用 `validate_configuration` 的阻断错误、过窄风险和 receipt 模式；不得创建 `force_discovery_save` 或平台布尔绕过。

### 观测与增长模式

- 只有响应成功、字段存在、时间有效且仓库身份已解析的观测才能写入 `github_metric_observations`。
- 首次有效观测返回 `baseline_only`；不足两个有效值返回 `insufficient_baseline`。
- 失败、超时、限流、字段缺失和部分页面未获取不得写入 Star/Fork 零值或合成观测。
- 比例增长首值为零时返回 `zero_ratio_baseline`，不得除零、改用 1 或静默降级为绝对增长。
- 时间统一使用 RFC 3339 UTC；增长窗口边界由共享时钟和固定 fixtures 决定，平台本地时区只用于展示。

### 身份与合并模式

- 规范身份优先使用 GitHub 数字仓库 ID；`node_id` 可保留作互操作字段，但不建立第二套主键；`owner/name` 是可变别名。
- 所有项目取得或更新必须经过单一 `resolve_github_repository_identity` 领域用例；Adapter、UI 和 Release 同步不得自行 upsert 项目。
- 身份合并在事务中迁移别名、订阅命中、观测、监控和 Release 外键，并保持历史 ID 可追溯。
- 手动固定关注、多个订阅、大小写差异、重命名和转移命中同一身份时，只追加依据和别名，不创建第二项目。

### 状态正交规则

| 状态 | 唯一写入入口 | 禁止的隐式写入 |
|---|---|---|
| 发现订阅配置 | 订阅创建、修改与启停命令 | 发现执行、结果查询、Release 同步 |
| 发现运行状态 | 发现 Application Task | UI 空数组、Release 任务、AI |
| 条件命中与依据 | 成功发现事务 | UI 展开、用户浏览、Release 查询 |
| Star/Fork 观测 | 成功元数据采集事务 | 请求失败、限流、增长计算 |
| 订阅级忽略 | ignore/undo 命令 | 停用订阅、删除历史 |
| 固定关注 | 手动固定或转固定命令 | 发现命中、订阅启停 |
| 自动关注启用 | auto-monitoring 命令及有效订阅投影 | UI toggle 乐观推算 |
| Release 同步状态 | Release Application Task | 发现失败或发现零结果 |

任何跨状态副作用必须先修改 PRD、UX、Architecture 和 fixtures，不得由单个 Story 自行增加。

### 命令、查询与事件

- 命令与查询只能使用核心决策中已批准的名称；禁止 `watch_repo`、`unwatch_repo`、`mark_trending`、`force_monitor`、`get_discovery_items` 等模糊接口。
- 写命令必须携带 revision 和幂等请求 ID；结果查询使用不透明 cursor，不暴露 GitHub page number 为持久 API 合同。
- 事件固定为 `core.github_discovery.changed.v1`、`core.github_project.changed.v1` 和既有 Release 事件；载荷只包含通用事件元数据、实体 ID 与 revision。
- 事件是查询失效提示，不携带完整 GitHub 响应、订阅条件、项目描述或命中依据，也不直接修改 UI 缓存。

### 错误、加载与结果模式

- GitHub 发现错误映射到既有 `validation`、`conflict`、`network`、`rate_limited`、`source_format`、`storage`、`cancelled` 或 `internal` 分类，不建立第二个错误体系。
- `succeeded_zero_results` 是显式成功终态；禁止从 `items.length == 0` 推断运行成功。
- 下一页存在但因预算、超时、限流或无效响应未完成时，结果必须为 `partially_succeeded` 或 `rate_limited`，并保留已确认结果与来源级问题。
- 加载和刷新保留旧结果；发现错误只能覆盖当前发现运行区域，不覆盖 Release 结果、主情报流或固定关注项目。
- UI 不自行重试；重试服从 `AppError.retryability`、`Retry-After`、rate-limit reset 和 `ExecutionBudget`。

### 用户控制模式

- 忽略、撤销忽略、停用自动关注和转固定关注均调用共享核心命令；三端不得直接切换本地布尔值。
- 这些控制不做乐观领域更新。平台可以显示 submitting，但必须以核心返回的合并 `GitHubMonitoringStateView` 作为成功结果。
- 项目由其他订阅或固定关注维持监控时，返回值必须包含 `effective_monitoring = true` 及原因集合，UI 不自行遍历订阅推算。
- 忽略和停用只失效相关发现/监控投影，不失效或删除 Release、收藏、反馈和历史情报查询。

- 每个新枚举、错误码或 schema 字段必须同步 Rust 权威类型、可读 schema、生成绑定及三端契约测试。

### 架构边界

**领域边界：**

- `domain/github` 是发现条件、增长计算、仓库规范身份、结果分类和关注优先级的唯一权威位置。
- `domain/sources` 保留通用来源抽象；GitHub 发现领域不得依赖 React、SwiftUI、Compose、GitHub HTTP DTO 或 SQLite 类型。
- GitHub Release 继续位于既有 Release 来源 Adapter；发现领域只通过本地项目 ID 和有效监控投影与 Release Application Task 协作。

**Adapter 边界：**

- `infrastructure/sources/github_discovery` 负责 GitHub 官方 API 请求、查询参数、分页、响应解析和错误分类。
- Adapter 只返回分页候选、限流与分页元数据；不得写数据库、保存观测、判定最终命中、修改关注状态或触发 Release 同步。
- 发现 Adapter 与 Release Adapter 可以共享 HTTP policy，但不得共享游标、Task、运行结果或错误状态实例。

**Application 边界：**

- `application/tasks/github_discovery.rs` 是发现执行顺序、预算、事务提交、部分完成和恢复的唯一编排者。
- Commands 负责订阅创建、修改与启停以及用户控制；Queries 负责运行与结果投影。查询不得产生观测、关注或监控副作用。
- 仓库身份解析和合并必须通过领域用例及数据库事务，不得由 Adapter 或平台 Feature 直接完成。
- 有效 Release 监控投影由 Application 层根据固定关注、有效自动关注和订阅级忽略计算并持久化。

**平台边界：**

- 三端 `github-discovery` feature 只接收展示 DTO、Render State 和 intent；不得引用 GitHub 原始响应或复制 Rust predicate。
- Windows query keys、Apple ViewState 和 Android UiState 分别按订阅、运行、项目和结果组织，但共享稳定 ID 与 revision 语义。
- 订阅表单 draft 属于页面/ViewModel 临时状态；保存后的订阅、结果和监控状态只来自核心查询。

**数据边界：**

- 只有 `infrastructure/database/github_discovery` 可以访问新增表。
- Release 表只引用规范本地项目 ID；不得保存订阅 ID 作为 Release 身份。
- 订阅停用和项目忽略不得级联删除项目、Release、收藏、反馈或观测审计。
- fixtures 只存在于 `contracts/fixtures/github-discovery`；平台测试通过相对路径或打包测试资源引用同一权威文件。
