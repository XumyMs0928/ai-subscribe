# AI 大模型开发行业情报雷达产品需求文档

**Author:** xmy
**Date:** 2026-08-06

## 执行摘要

AI 大模型开发者与技术负责人需要持续跟踪论文、模型、开源项目、厂商博客和技术社区，但信息分散于多个平台，且充斥重复搬运、营销内容与低价值更新。用户每天需要投入 1–2 小时手动收集、去重、翻译和判断，仍可能错过会影响技术选型或项目决策的重要动态。

本产品是一套面向 Windows、iPhone、iPad、Android 手机和平板的原生 AI 开发行业情报雷达。各客户端均以设备本地数据为主，在操作系统允许的生命周期内采集公开信息源，根据用户关注赛道、来源可信度、新鲜度、重复度、技术影响和可操作性进行筛选，再通过可配置的 AI 服务生成中文摘要、主题标签、重要度评分及评分依据。无 AI Key、AI 服务失败、网络离线或后台执行受限时，用户仍可浏览和检索该设备已缓存的内容。

除用户手动指定的 GitHub 项目外，产品还可按关注赛道、主要语言、GitHub Topic、Star/Fork 门槛及增长条件发现符合订阅规则的公开项目，并自动纳入设备本地 Release 监控。发现依据必须可解释，用户可以忽略、停用或转为固定关注；发现任务失败不得影响既有项目的 Release 同步。

首要用户是个人 AI 开发者与技术负责人。产品的核心目标不是聚合尽可能多的资讯，而是让用户每天只需浏览少量高价值情报，即可掌握真正影响其关注方向和项目决策的变化。

性能、可靠性、安全与外部服务约束均服务于这一核心目标：首启时间来自“无需配置即可立即体验”的首启旅程，50,000 条数据下的查询目标来自连续积累历史情报后仍需在 15 分钟内完成日常浏览的要求，单源隔离与离线访问来自外部服务失败旅程，密钥隔离来自本地优先与可配置第三方 AI 的信任边界，响应大小、超时、重定向、目标地址和限流约束来自公开来源采集及本地数据保护要求。具体条件、测量方法和通过阈值以非功能需求为准。

### 产品差异化

产品的第一优先级是智能筛选准确度。规则筛选先于 AI 分析，结合用户自定义赛道、关键词、来源信誉、发布时间、重复关系和技术影响，降低水文、营销软文与重复搬运进入主情报流的概率。

所有情报必须可溯源，至少保留发布方、作者（若可获得）、原始标题、原文链接、原始发布时间、采集时间和来源类型。AI 生成的翻译、摘要、评分与判断必须明确标识，并与原文事实分离。无法可靠溯源的内容不得被评为高优先级，也不得触发重大动态通知。

相较通用 RSS 阅读器，产品提供 AI 开发领域筛选、跨来源去重、中文提炼和重要度判断；相较仅能订阅已知仓库的 Release 工具，产品可从用户关注方向发现此前未知但达到明确活跃度或增长条件的公开项目，并保留忽略、停用和固定关注控制；相较云端简报服务，产品本地优先、无强制云同步；相较手动刷站，产品通过平台允许的后台同步与系统通知缩短重大动态的发现时间。

## 项目分类

- **项目类型：** Windows、iOS/iPadOS 与 Android 原生多平台应用
- **业务领域：** AI/ML 技术研究与开发者工具
- **领域复杂度：** 高
- **项目背景：** Greenfield 新产品
- **核心约束：** 本地优先、设备本地数据独立、筛选准确、信息可溯源、单源故障隔离、无 AI Key 可用、适配平台生命周期与权限边界
- **MVP 非目标：** 云同步、跨设备数据同步、多租户、团队权限、付费订阅、登录内容抓取、绕过反爬、自动操作第三方账户

## 成功标准

### 用户成功

- 用户每天在 ≤15 分钟内浏览按新鲜度排序且达到主情报流阈值的 AI 技术动态，并能识别其对当前关注方向或项目决策的影响。
- 主情报流以“有价值”反馈占比衡量筛选效果，验证期目标 ≥70%，不以资讯数量作为成功指标。
- 用户能够在单条情报卡片中判断“发生了什么、为什么重要、是否值得进一步阅读”，并可一键回到原文核验。
- 高优先级通知以“值得立即知道”反馈占比衡量提醒准确度，验证期目标 ≥80%；同时每周复盘关键动态，防止依靠减少提醒制造表面准确率。
- 用户无需 AI Key 也能完成采集、去重、筛选、搜索、阅读和溯源。
- 用户可以在 Windows、iPhone、iPad、Android 手机和平板任一受支持设备上完成相同核心旅程；平台特有能力可以不同，但不得阻断首启、浏览、检索、溯源、配置与反馈。
- 用户拒绝通知权限或操作系统限制后台执行时，仍可前台同步和使用设备本地缓存，且界面明确显示最后成功同步时间与当前限制。
- 用户能够通过可解释的发现条件找到此前未手动指定的相关 GitHub 项目，查看每个项目命中的赛道、语言、Topic、Star/Fork 门槛或增长条件，并可忽略、停用或转为固定关注。

### 产品验证成功

首阶段仅供个人使用，不以用户增长或收入衡量。验证周期内满足以下条件即可证明方向有效：

- 连续使用 4 周，每周至少 5 天通过该工具获取 AI 技术动态。
- 在上述有效使用日内，用户完成日常情报掌握的时间 ≤15 分钟，不再需要逐一浏览全部已配置来源。
- 每周以主要来源的已知重大事件为人工基准复盘，因系统未采集或误过滤造成的已确认关键漏报为 0。
- 高优先级通知中，“值得立即知道”的反馈占比 ≥80%；无价值提醒可被标记并用于手动调整规则。
- 验证期内至少发生一次用户主动调整赛道、关键词或来源，且下一轮同步按新配置生效；该项作为自定义监控被实际使用的证据，不替代提醒与情报流准确率指标。
- 验证期内至少完成一次 GitHub 自动发现结果审查，并对至少一个结果执行忽略、停用或转为固定关注，以证明发现与用户控制闭环可实际使用。
- 至少在 Windows、iPhone、iPad、Android 手机和 Android 平板各完成一轮连续 7 天核心旅程验证；核心任务完成率均为 100%，不要求设备间共享配置、收藏或历史数据。

### 技术成功

- 首次启动至可浏览情报不超过 5 秒。
- 50,000 条缓存数据下，常用筛选与首屏查询 P95 小于 200ms。
- 同一情报跨轮询重复入库率为 0，重复通知率为 0。
- 单一来源失败不阻断其他来源同步，错误可定位到具体来源。
- 离线、无 AI Key、AI 超时三种状态下均可浏览和检索缓存。
- 每条高优先级情报具有有效原文链接、来源、发布时间和采集时间；无可靠来源的内容不得进入高优先级。
- API Key 不出现在前端状态、日志、诊断导出和测试数据中。
- 默认刷新策略遵守来源限制，遇到 429 后按服务端信息退避。
- 各平台在应用被挂起、终止、系统回收或网络切换后均不损坏已完成数据，并能在下次可执行时继续处理可恢复任务，或将无法继续的任务明确标记为可重试。
- GitHub 项目发现任务发生限流、超时或无效响应时，既有固定关注和自动关注项目的 Release 同步结果不得被隐藏、回滚或等待发现任务恢复后才可用。

### 可测量结果

- **每日使用时长：** ≤15 分钟。
- **提醒有效率：** 验证期内，用户标记为“值得立即知道”的高优先级通知占比目标 ≥80%。
- **主情报流有效率：** 用户标记为“有价值”的主流条目占比目标 ≥70%。
- **关键动态漏报：** 每周复盘已知重大事件，目标为 0 次因系统未采集或误过滤造成的关键漏报。
- **溯源完整率：** 高优先级情报 100% 具备有效来源信息。
- **可靠性：** 单源错误不扩散；已缓存内容在外部服务不可用时 100% 可访问。
- **GitHub 项目发现：** 固定仓库样本中的规则匹配、首次发现与首次跨门槛分类、项目身份去重和用户控制行为满足 NFR54，发现故障导致既有 Release 同步中断次数为 0。

提醒有效率和情报流有效率采用“有价值 / 无价值”反馈记录。前 4 周是校准期，指标用于调整规则，不用于制造虚假的模型精度结论。

## 用户旅程

### 旅程一：个人 AI 开发者完成首次启动并建立每日情报习惯

林舟是一名独立 AI 开发者，正在研究 Agent 与本地大模型。他每天打开多个网站，却很难判断哪些更新真正影响项目。首次启动情报雷达时，应用无需注册或配置 AI Key，直接展示带有明确“演示数据”标识的情报流，并预置 Agent、多模态和本地模型等默认赛道。

林舟可以立即体验筛选、详情、来源溯源和重要度解释。应用随后以非阻塞方式引导他调整关注赛道、关键词、默认来源和刷新周期。他关闭不相关赛道，手动添加正在使用的开源项目，同时创建按“推理框架”赛道、Python 语言、GitHub Topic 及 Star/Fork 条件发现公开项目的订阅，并选择暂不配置 AI 服务；自动发现配置可跳过，不阻断主情报流。

几天后，林舟决定配置第三方 AI 服务。应用先说明将发送标题、必要正文片段和分析所需元数据，不会发送 API Key、反馈历史或无关本地数据；获得确认后，他仍可按来源禁止发送正文，仅允许使用标题和摘要。未获确认或被禁止发送的来源继续使用本地规则处理，不阻断采集与阅读。

第二天，雷达已在操作系统允许的时机完成同步。林舟可在同步状态中分别查看 RSS/Atom、GitHub Release 与 arXiv 本次新增、更新、跳过和失败数量，并打开成功转换的最小结果列表，无需先配置 AI 或等待完整评分。在 Windows 上，林舟关闭主窗口后可让应用继续在托盘运行，并从托盘显示窗口、立即同步或显式退出；在手机和平板上，应用被切到后台或被系统终止后保留已完成数据与待处理状态，下次前台启动时显示最后成功同步时间，并继续处理可恢复任务或将无法继续的任务明确标记为可重试。若他拒绝通知权限，应用仍可正常使用，并从设置中说明如何重新授权。林舟每天用十几分钟浏览少量高价值情报，把条目显式设为“未查看”“已判断”或“待研究”，并对有帮助和无意义的内容分别反馈；收藏与处理状态相互独立。依据反馈统计逐步校准规则后，主情报流更贴合他的项目方向，他不再逐个平台刷站。

**揭示的能力：** 无注册首启、明确标识的演示数据、默认赛道、渐进式引导、无 Key 可用、首次 AI 数据发送说明与确认、按来源控制 AI 内容发送、手动 GitHub 项目关注、GitHub 项目发现订阅、来源配置、同步结果摘要与最小预览、用户处理状态、反馈、平台生命周期恢复、Windows 托盘与开机启动控制、移动端权限降级和每日高价值情报流。

### 旅程二：技术负责人收到重大提醒并完成可溯源决策

周岚负责团队的模型技术选型。工作期间，系统通知提示某个核心模型发布重大版本。通知只显示原始发布方、标题和简短的 AI 提炼，并明确标注分析生成方式；锁屏状态下遵循平台隐私设置，不额外暴露正文、凭据或敏感诊断信息。

周岚在 Windows、iPhone、iPad 或 Android 设备上点击通知后，应用直接打开该条情报详情，而不是把她带到通用列表；应用尚未运行时也能在启动后恢复该目标。详情页展示版本变化、为什么重要、可能影响、置信度、原始标题、发布方、作者、发布时间、采集时间、首次发现时间、最后更新时间和原文可用状态。她发现该信息来自项目官方 Release，而不是二次转载，于是打开原文核验。

同一版本还被另一官方博客报道。由于两条记录共享可验证的项目版本标识，应用将其确定性关联为同一事件，并保留两条独立的标题、链接、发布时间和来源记录供展开核验；不会仅凭语义相似自动合并来源。

确认后，她将情报标记为“值得立即知道”，收藏该条情报并保存当时可合法获取的正文快照，以便离线继续评估。取消收藏时，她可以删除正文快照及派生索引，仅保留元数据、必要摘录和分析结果。应用记录反馈，但不会自动替她操作 GitHub、发送消息或修改项目。

**揭示的能力：** 高优先级通知、通知深链、详情页、AI 与原文分离、完整溯源、首次发现与更新状态、基于共享标识的来源关联、关联来源展开、原文跳转、收藏正文、离线阅读、取消收藏与正文删除、价值反馈和一次性通知。

### 旅程三：用户校准雷达，降低误报并覆盖细分赛道

使用一周后，林舟发现“Agent”关键词带来过多营销文章，而一个重要的推理框架 Release 没有进入高优先级。他进入雷达设置，查看当前赛道、关键词、来源权重、排除词和提醒阈值。

他将“Agent”从宽泛关键词改为更具体的框架和能力词，降低部分二次媒体来源的信誉权重，并把官方 Release 提升为高可信来源。他发现只有预先知道仓库名称时才能手动关注项目，于是创建 GitHub 项目发现订阅：赛道选择“推理框架”，主要语言选择 Python，Topic 包含 inference，并设置 Star/Fork 当前门槛及观察窗口内的增长条件。下一次获得执行机会后，系统展示首次进入本地发现结果集或首次跨过门槛的项目，逐项标明命中的条件、实际观测值和观测时间；多个订阅命中同一仓库时只形成一个项目和一个 Release 监控对象，但保留全部命中依据。林舟可以忽略无关项目、停用自动关注，或把重要项目转为不再依赖发现条件的固定关注；已手动固定关注的仓库不会被重复建立自动关注。他还查看被过滤内容和评分依据，确认系统为什么降低某条情报的优先级，而不是只能猜测黑盒逻辑。

保存前，应用校验配置并提示可能造成漏报的过窄条件。下一轮同步使用新规则，但历史情报仍可检索。持续使用后，本地历史数据增长到 50,000 条；林舟仍能按赛道、来源、时间、重要度、用户处理状态和收藏状态组合筛选，并搜索元数据、必要摘录及可用的收藏正文，在常用操作下快速打开首屏结果。他可在“未查看”“已判断”“待研究”之间显式转换，单纯打开详情、收藏或取消收藏不会静默改变处理状态。此后提醒更少、更准确，漏掉的官方更新也被纳入监控。

**揭示的能力：** 赛道与关键词管理、排除词、来源权重、提醒阈值、GitHub 项目发现订阅、新发现与首次跨门槛口径、命中依据、忽略、停用、转固定关注、手动与自动身份去重、增长观察基线、评分解释、被过滤内容审查、配置校验、用户处理状态与收藏独立性、历史数据保留、50,000 条历史情报下的常用筛选与搜索性能，以及规则生效边界。

### 旅程四：外部服务失败时继续工作并完成自助排查

某天网络不稳定，一个厂商 RSS 来源返回限流错误，AI 服务同时超时。林舟打开应用时仍能看到本地缓存、最后成功同步时间和离线提示。GitHub Release 与 arXiv 的成功结果正常保留，没有因单源失败而回滚。

同步状态页把问题分别归因到具体 RSS 来源和 AI 处理阶段，显示失败时间、限流原因、下一次重试时间及用户可执行的处理动作；同时保留三类来源本次新增、更新、跳过和失败计数，以及已成功转换的最小结果列表，不用整体失败掩盖 GitHub Release 与 arXiv 的成功结果。若 GitHub 项目发现请求遭遇限流、部分分页失败或无效响应，状态页把问题单独归属于发现订阅并区分“成功且零结果”与“发现未完成”，此前已关注项目的 Release 同步继续执行，已有结果不被隐藏或回滚。新采集但未完成 AI 分析的内容仍显示原始标题、来源和必要摘录，同时逐项标注 AI 处理状态为“等待分析”，不会伪装成已完成的 AI 结论。

林舟可以单独重试失败来源、临时关闭 AI 分析或继续离线阅读。如果需要报告问题，他复制脱敏诊断信息，其中不包含 API Key、文章全文或完整提示词。服务恢复后，待处理任务继续执行，不重复入库或重复通知。

**揭示的能力：** 离线缓存、最后同步时间、来源级状态、同步结果摘要与最小预览、GitHub 发现任务与 Release 同步故障隔离、部分成功、待分析状态、独立重试、持久任务恢复、诊断导出和密钥脱敏。

### 旅程需求汇总

- **首次体验：** 无注册、明确标识的演示数据、默认赛道，以及主情报流先可用、可跳过且可从明确入口恢复的渐进配置（FR1–FR5、FR61；NFR33）。
- **日常核心：** 少量高价值情报、50,000 条历史情报下的常用筛选与搜索、详情阅读、用户处理状态、价值反馈和每日 15 分钟内完成（FR31–FR35、FR43、FR60；NFR2、NFR53）。
- **提醒闭环：** 可配置阈值、权限可拒绝、通知去重、冷启动深链、免打扰和频率上限（FR6、FR37–FR40、FR53、FR54）。
- **可信溯源：** 发布方、作者、原始标题、原文链接、发布时间、采集时间、来源类型、首次发现时间、最后更新时间和原文可用状态（FR14–FR16）。
- **内容生命周期：** 默认仅长期保存元数据、必要摘录和分析；收藏时保存合法正文快照，支持离线阅读、取消收藏和正文删除，且收藏与用户处理状态相互独立（FR17、FR18、FR36、FR60）。
- **来源关联：** 基于共享链接、内容标识或内容版本等可验证标识确定性关联同一事件，同时保留各自溯源记录（FR23、FR24）。
- **AI 边界：** 首次发送数据前说明并确认、按来源控制发送范围、AI 内容与处理状态明确标识、原文事实独立保存（FR26、FR28–FR30）。
- **个性化：** 赛道、关键词、排除词、来源权重、刷新周期和提醒策略（FR4–FR6）。
- **GitHub 项目发现：** 保留手动指定项目，同时按赛道、语言、Topic、Star/Fork 当前门槛及增长条件自动发现并监控公开项目；显示命中依据，支持忽略、停用和转固定关注，并保证项目身份与 Release 同步去重（FR8、FR64；NFR24、NFR54）。
- **筛选校准：** 有价值/无价值反馈、被过滤内容审查、评分解释、用户处理状态，以及保存前区分阻断性错误与可确认过窄配置风险的校验（FR19–FR22、FR43–FR46、FR60、FR62）。
- **平台生命周期：** Windows 关闭隐藏至托盘、托盘操作、开机启动控制与单实例；移动端挂起、终止、恢复、前台补偿同步及状态保留（FR41、FR42、FR51、FR52、FR63；NFR35）。
- **跨平台体验：** 手机、平板和桌面均可完成核心旅程，导航随窗口尺寸和输入方式调整；各设备数据独立，不暗示云端或跨设备同步（FR55–FR58）。
- **可靠性：** 单源故障隔离、部分成功、离线可用、失败重试和任务恢复（FR47–FR49）。
- **自助支持：** 来源级状态、最近一次同步结果、可操作错误、脱敏诊断信息和不泄露密钥（FR12、FR50、FR59；NFR52）。
- **权限边界：** 只读采集与原文跳转，不自动操作第三方账户。

## 领域专项要求

### 内容使用与合规

- 只采集无需登录即可访问的公开内容或官方开放 API，不绕过付费墙、登录限制、验证码或反爬措施。
- 每个来源适配器必须记录来源类型、发布方、作者（若可获得）、原始标题、原文链接、原始发布时间、采集时间和内容标识。
- 来源接入前应确认其 API、RSS、robots、版权和缓存条款；违反使用条款的来源不得作为默认来源。
- 默认长期保存标题、来源元数据、原文链接、必要摘录和 AI 分析，不长期保存完整正文。
- 只有用户主动收藏情报时，才保存当时可合法获取的完整正文快照；取消收藏后允许用户删除正文，仅保留元数据与分析结果。
- 完整正文只用于用户本机个人研究，不提供公开再分发、批量导出或内容镜像服务。
- 原文失效或被修改后，系统保留采集时元数据和收藏快照状态，并明确标注原链接不可用或内容可能已变化。

### AI 分析与可信边界

- AI 分析功能默认开启；未配置有效 API Key 时，界面显示待配置状态，但不阻断采集、去重、筛选、阅读和溯源。
- 用户首次配置第三方 AI 服务时，必须看到数据发送说明并确认；确认后默认对符合分析条件的新情报执行 AI 分析。
- 为生成摘要，可在内存中临时处理可获得正文；分析完成后立即丢弃未收藏的完整正文，只持久化必要摘录与分析结果。
- 发送给第三方 AI 的内容遵循数据最小化原则，只包含标题、必要正文片段和分析所需元数据，不发送 API Key、用户反馈历史或无关本地数据。
- 用户可全局关闭 AI 分析，也可按来源禁止发送正文，仅使用标题和摘要。
- AI 翻译、摘要、主题、评分、置信度和“为什么重要”必须明确标注为 AI 生成，不得与原始事实混排。
- AI 分析失败、超时或输出不符合 schema 时，保留原始情报并标记待重试，不生成伪造的兜底结论。

### 溯源与事实核验

- 高优先级情报必须具备有效原文链接、明确发布方和可解析的发布时间；条件不满足时不得触发重大动态通知。
- 官方发布、项目 Release 和论文原文的来源权重默认高于二次转载。
- 多篇文章指向同一事件时，应形成关联关系，但不得删除各自来源记录。
- 情报详情必须将原始字段、系统规则判断和 AI 分析分区显示。
- 用户可从通知和详情一键打开原文，并能看到情报首次发现时间与最后更新时间。
- 原文内容与 AI 分析发生冲突时，以原文为核验依据，并允许用户标记分析错误。

### 技术约束

- 收藏正文、普通元数据、AI 分析和密钥分别存储；API Key 不进入内容数据库、日志或诊断导出。
- 未收藏完整正文不得在数据库、临时文件、崩溃转储或日志中残留。
- 正文抓取和 AI 调用需要响应大小、超时、重定向及目标地址限制，防止恶意来源占用资源或访问本地网络。
- 用户收藏产生的正文快照应记录获取时间、内容 hash、原文 URL 和来源许可状态。
- 删除收藏正文后，应同时清理全文索引、缓存和派生临时文件。
- 外部服务不可用时，已保存内容和溯源信息必须保持可访问。
- 每台设备的配置、收藏、反馈、凭据和历史情报均属于该设备的独立本地数据集；MVP 不得暗示或静默执行跨设备同步。
- 后台同步属于受平台生命周期、网络、电量与用户设置约束的尽力执行能力；产品不得承诺移动端持续常驻或固定时刻必然完成。
- 通知、后台刷新和本地网络等操作系统权限均须按需申请；拒绝、撤销或受系统限制时必须保留前台同步与本地阅读能力。

### 主要风险及缓解

- **版权与条款风险：** 默认不保存全文，只为主动收藏保留本地快照；来源逐一核验。
- **AI 幻觉：** 原文与 AI 分区、强制溯源、schema 校验和错误反馈。
- **第三方数据使用：** 首次配置确认、最小化发送、可关闭和按来源控制。
- **原文变化或删除：** 保存采集时间、内容 hash、链接状态和收藏快照。
- **低质量转载污染：** 提升一手来源权重，关联重复事件但保留来源链。
- **本地敏感数据残留：** 未收藏全文仅内存临时处理，完成后清理。
- **移动后台执行不确定：** 展示最后成功同步时间和待处理状态，在前台启动、网络恢复或系统允许的后台时机执行补偿同步。
- **平台碎片化：** 以共享核心旅程和平台验收矩阵控制一致性，不强求托盘、窗口或通知样式跨平台完全相同。
- **设备数据预期错误：** 首次使用与设置页明确说明数据仅保存在当前设备，MVP 不提供跨设备同步或恢复服务。
- **权限与隐私：** 延迟申请非必要权限，通知权限拒绝不阻断核心使用，锁屏通知不展示正文、凭据或敏感诊断信息。

## 创新与新颖模式

### 核心创新假设

核心创新不是单独的 AI 摘要、关键词过滤或内容去重，因为这些能力在现有产品中已经存在。需要验证的创新假设是：

> 在完整溯源约束下，将用户关注赛道、来源可信度、新鲜度、事件影响、跨来源重复关系和持续反馈组合起来，可以比通用聚合器更准确地筛出少量、真正值得 AI 开发者立即关注的动态。

该假设包含四个相互依赖的创新点：

- **溯源门控：** 缺少可靠发布方、原文链接或发布时间的内容不能进入高优先级。
- **领域影响评分：** 不只判断文章与关键词是否相关，还判断它是否会影响模型能力、开发框架、部署方式、成本、安全或技术选型。
- **个性化反馈闭环：** “有价值 / 无价值 / 分析错误”反馈用于调整赛道、来源与规则权重。
- **少而准的通知目标：** 系统优化目标不是阅读量或摘要数量，而是提醒有效率与关键动态漏报率。

### 市场背景与差异化

现有工具已经具备主题优先、关键词静音、内容去重、RSS 聚合、过滤视图和 AI 摘要等单项能力，因此本产品不宣称“首个 AI RSS 工具”。可成立的差异化是：

- 面向 AI 开发决策，而非通用阅读。
- 同时接入论文、模型、项目 Release、技术社区和官方博客。
- 本地优先，允许用户自带兼容 OpenAI 接口规范的模型服务。
- 高优先级受溯源完整性约束。
- 公开展示规则评分、AI 判断和原始事实之间的区别。
- 使用用户反馈优化“少而准”，并同时评估误报与漏报。

### 验证方法

进行连续 4 周的个人验证，使用“系统输出 + 人工基准”双轨运行：

1. 每日使用系统主情报流和重大提醒。
2. 每周抽样检查被过滤内容，并手动回顾主要来源的已知重大事件。
3. 为每条高优先级通知标记“值得立即知道 / 有价值但不紧急 / 无价值”。
4. 为主情报流条目标记“有价值 / 无价值 / 重复 / 分析错误”。
5. 记录漏报原因：未采集、去重错误、赛道不匹配、来源权重过低、AI 判断错误或溯源不足。
6. 每周只调整一类主要参数，避免同时修改多个权重导致无法归因。

创新假设通过标准：

- 高优先级通知中，“值得立即知道”占比 ≥80%。
- 主情报流中，“有价值”占比 ≥70%。
- 每日使用时间 ≤15 分钟。
- 高优先级情报溯源完整率 100%。
- 验证期内没有因系统未采集或误过滤造成的已确认关键漏报。
- 第二至第四周的无价值率呈下降趋势，而不是依靠减少采集量制造表面提升。

### 风险与回退方案

- **冷启动反馈不足：** 使用透明默认赛道、来源等级和规则权重，不依赖训练个人模型才能工作。
- **过度个性化形成信息茧房：** 保留“探索”视图和被过滤内容审查，每周展示少量高可信度赛道外信号。
- **溯源门控造成漏报：** 信息可进入普通候选流，但在溯源补全前不得触发重大提醒。
- **反馈样本偏差：** 区分“不感兴趣”和“内容无价值”，避免把用户当前不需要误判为低质量。
- **重复聚类隐藏不同观点：** 聚合事件但保留全部来源，可展开查看不同报道与原始发布。
- **个性化效果不明显：** 回退为可解释的规则筛选、来源优先级和手动阈值，不阻断基础产品价值。
- **指标被过度优化：** 同时监控提醒准确度与关键漏报，禁止只靠少推送提高准确率。

## 跨平台原生应用专项要求

### 产品形态与支持矩阵

MVP 同时提供 Windows 10/11 x64、iOS/iPadOS 17 及以上和 Android 10 及以上原生客户端，覆盖桌面、手机与平板。三个客户端共享产品概念、领域规则、数据模型和核心旅程，但采用各平台惯用的导航、输入、通知、生命周期与无障碍行为。MVP 不支持 Windows 7、Windows ARM64、macOS、Linux 或 Web。

- Windows 支持当前用户级安装、窗口、托盘、系统通知、开机启动和单实例。
- iOS/iPadOS 支持 iPhone 与 iPad，覆盖紧凑和宽屏布局、横竖屏、动态字体、系统通知、深链及应用挂起与终止恢复。
- Android 支持手机和平板，并覆盖可调整窗口、横竖屏、系统通知、深链、后台限制和进程被系统回收后的恢复。
- 核心任务在键盘、鼠标、触控和平台辅助技术下均须可完成；平台特有操作不得成为跨平台核心能力的唯一入口。

### 导航与布局适配

- 信息架构在各平台保持一致，包括主情报流、搜索、收藏、同步状态与最近一次同步结果、设置。
- 手机使用适合单列和触控的层级导航；平板与宽窗口可使用双栏或多栏，但不得改变数据含义或隐藏核心操作。
- 窗口尺寸、方向、安全区、显示缩放或字体放大变化后，当前任务上下文与未保存输入不得静默丢失。
- 所有平台均提供从列表到详情、从通知到指定详情、从详情到原文的明确路径。

### 生命周期、后台执行与通知

- Windows 关闭主窗口默认隐藏到托盘；托盘至少提供显示主窗口、立即同步和显式退出，用户可控制开机启动。
- 移动端不得依赖持续常驻。挂起、终止或系统回收前应保存已完成数据和可恢复任务状态；再次获得执行机会时执行幂等续作或明确标记待重试。
- 后台同步为尽力执行。界面必须显示最后成功同步时间、当前同步状态和可能影响时效性的系统限制，并始终允许用户前台手动同步。
- MVP 不提供远程推送服务。每台设备只有在本地完成来源同步和重大动态判定后，才向操作系统提交该设备的系统通知。
- 移动操作系统未授予后台执行机会时，产品不保证重大动态即时送达。应用下次获得执行机会后处理仍有效的待处理情报；已失去提醒时效但仍有价值的内容进入主情报流，不补发误导性的“即时”提醒。
- 通知权限按需申请；拒绝或撤销权限不得阻断采集、浏览、检索、溯源或前台同步，也不得反复强迫授权。
- 点击通知必须在应用已运行、后台、未运行三种状态下定位到对应情报；目标已删除或不可用时给出明确说明和安全替代入口。
- 通知遵守免打扰时段、频率上限、同条目一次提醒与平台锁屏隐私设置。

### 设备本地数据与离线能力

- 配置、收藏、反馈、凭据和历史情报默认只保存在当前设备；卸载、清除应用数据或设备丢失可能导致数据不可恢复，产品须在相关操作前明确说明。
- MVP 不提供云端备份、跨设备同步或设备间自动迁移；同一用户在不同设备上的数据可以不同。
- 离线时可浏览缓存、查看已保存正文、搜索、筛选、查看详情与溯源、修改配置、记录反馈，并收藏已完整缓存的正文。
- 离线时暂停外部同步、原文状态检查、未缓存正文获取和第三方 AI 分析；联网且平台允许执行后恢复有效待处理任务，不重复入库、分析或通知。
- 凭据只进入平台提供的安全凭据能力；不得进入内容数据、日志、诊断导出或跨设备传输。

### 安装、升级与发布边界

- 验证阶段使用受控测试分发或手动安装，不把公开商店发布、自动更新或生产级发布运营作为 MVP 成功条件。
- Windows MVP 候选构建使用当前用户级 x64 安装包进行受控手动验证，不以 Windows 生产代码签名为候选门禁；未进行生产签名时必须向授权测试者说明发布者提示、构建来源和完整性校验方式，不得宣称该构建已经签名或适合公开发布。
- 移动候选构建必须使用平台认可且在有效期内的测试分发签名或安装凭据，只能分发给已获授权的测试账户或设备；签名缺失、失效或安装资格不满足的构建不得作为候选构建交付。
- 每个移动候选构建在分发前必须提供可访问的隐私说明，完整披露设备本地保存的数据、请求的系统权限、访问的公开来源、发送给第三方 AI 的数据、正文保留与删除规则、诊断信息范围，以及 MVP 不提供云端备份或跨设备同步。平台要求的隐私清单或等价声明必须与实际行为一致。
- 从任一受支持既有版本升级时，不得静默清空或改写该设备的配置、收藏、反馈与历史情报；无法迁移时须停止升级并说明恢复路径。
- Windows 安装和日常运行不要求管理员权限；移动端按平台标准应用权限运行，不要求越狱、Root 或设备管理权限。
- 安装、升级、卸载和清除数据前后，均须明确说明本地数据是否保留；Windows 生产代码签名、公共商店审核、公开发布和回滚运营策略由后续发布计划确定，不影响 MVP 移动受控测试构建的有效签名与隐私披露门禁。

## 产品范围与分阶段开发

### MVP 策略

**MVP 类型：** 问题验证型 MVP。

第一阶段只验证一个核心假设：在完整溯源约束下，结合用户赛道、来源可信度、内容新鲜度、技术影响、重复关系和反馈，能否筛出少量、真正值得 AI 开发者关注的动态，并能否通过明确、可解释且用户可控的条件发现此前未知但相关的 GitHub 项目。

MVP 不以来源数量、界面完整度或公开发布为目标。成功标准是个人连续使用 4 周后，每天可在 15 分钟内完成情报掌握，通知有效率达到 80%，主情报流有效率达到 70%，且没有已确认的关键漏报。

**资源要求：** 至少需要覆盖 Windows、iOS/iPadOS、Android 原生客户端，共享领域规则、本地数据、HTTP/RSS、AI API、移动生命周期、平台无障碍及真机验收的开发与测试能力。三端均属 MVP，必须按同一核心旅程的纵向切片交付，避免按平台形成互不验证的独立产品。

### Phase 1：MVP

#### 支持的核心旅程

- 首启后立即浏览演示情报和默认赛道。
- 首启后先进入主情报流，再通过可跳过且可从明确入口恢复的渐进引导配置关注赛道、关键词、排除词、来源和 AI 服务。
- 配置 GitHub 项目发现订阅，审查带命中依据的新发现或新符合条件项目，并执行忽略、停用或转固定关注；手动指定或被多个规则命中的同一仓库不得重复建立 Release 监控。
- 同步全部或单个来源后，查看 RSS/Atom、GitHub Release 与 arXiv 本次新增、更新、跳过和失败数量，并打开成功转换的最小结果列表。
- 后台采集并生成少量高价值中文情报。
- 从系统通知直接打开重大情报详情；拒绝通知权限时仍可在应用内查看重大动态。
- 查看评分依据和完整来源链，并跳转原文核验。
- 标记“值得立即知道 / 有价值 / 无价值 / 分析错误”。
- 将情报显式设为“未查看 / 已判断 / 待研究”，并独立管理收藏状态。
- 检查被过滤内容、发现并记录漏报原因，并在保存配置前区分阻断性错误与可明确确认的过窄配置风险。
- 在离线、单源失败和 AI 超时状态下继续使用缓存。
- 在 Windows 应用已运行或隐藏至托盘时再次启动，返回现有主窗口且不产生第二个可交互实例。
- 在 Windows、手机和平板上完成相同核心旅程，并在移动端挂起、终止或权限受限后继续处理可恢复任务，或将无法继续的任务明确标记为可重试。

#### 首批真实来源

- **RSS/Atom：** 厂商官方博客和中文技术媒体。
- **GitHub 项目与 Release：** 支持用户手动指定公开仓库，也支持按赛道、主要语言、Topic、Star/Fork 当前门槛及可验证增长条件发现公开仓库；两种方式统一进入 Release 增量同步能力。
- **arXiv：** 用户关注主题和分类的论文更新。

Hugging Face 与 Hacker News 不进入 Phase 1。

#### 必须具备的能力

- Windows 10/11 x64、iOS/iPadOS 与 Android 原生客户端。
- Windows 托盘、开机启动、关闭隐藏、单实例和显式退出；移动端挂起、终止、前台恢复、权限降级和通知深链。
- 各设备独立的本地存储、迁移、去重、搜索和离线缓存；不提供跨设备同步。
- 演示数据、默认赛道，以及主情报流先可用、可跳过且可从明确入口恢复的渐进式配置引导。
- 三类来源适配器、增量同步、来源游标、限流、失败隔离，以及不依赖 AI、评分、搜索或完整详情的同步结果摘要和最小只读预览。
- 当前设备的 GitHub 项目发现订阅、增长观察基线、规范仓库身份去重、命中依据与观测值展示，以及自动关注项目的忽略、停用和转固定关注；发现任务与既有 Release 同步具有独立状态、退避和故障边界。
- 统一情报模型与完整溯源字段。
- 基于规范化原文链接、来源内容标识或内容版本等共享标识的确定性去重与来源关联；关联后仍保留每条来源记录。
- 可解释的本地规则筛选、重要度排序、基础被过滤列表，以及保存前的配置校验与过窄配置漏报风险提示。
- 兼容 OpenAI 接口规范的翻译、摘要、主题、重要度、理由和置信度。
- AI 默认开启；无有效 Key 时显示配置提示并保持基础功能可用。
- 情报详情中分离原始事实、规则判断和 AI 分析。
- 高优先级通知、通知去重、免打扰和频率上限。
- 用户反馈与每周验证指标统计。
- 当前设备上的“未查看 / 已判断 / 待研究”用户处理状态；状态显式转换并与收藏、价值反馈和 AI 处理状态相互独立。
- 默认不保存完整正文；收藏时保存合法获取的本地正文快照。
- 来源级状态、独立重试、任务恢复和脱敏诊断信息。

#### 明确不做

- Hugging Face、Hacker News 或需要登录的来源。
- GitHub 私有仓库、需要登录或额外组织授权的项目发现，以及对 GitHub 全站进行实时、无遗漏或无限频率扫描。
- 在缺少至少两个带时间戳的有效 Star/Fork 观测值时推断增长；首次观测只建立基线。
- 因发现条件不再满足、发现订阅停用或项目被忽略而删除历史 Release、反馈、收藏或其他合法保留数据，或自动取消用户已转为固定关注的项目。
- 自动学习权重、本地训练或向量检索。
- 在缺少共享链接、内容标识或内容版本时，仅凭语义相似度执行跨来源事件聚类。
- 高级权重可视化编辑器。
- 云同步、账号系统、团队协作和付费订阅。
- 自动更新、公开发布渠道和 Windows 生产代码签名；本条不排除移动候选构建所需的受控测试签名或安装凭据。
- Windows ARM64、macOS、Linux 和 Web。
- 云端备份、跨设备同步或设备间自动迁移。
- 批量正文导出、内容镜像或第三方账户自动操作。

### Phase 2：验证后增强

- Hugging Face Hub 和 Hacker News 适配器。
- OPML 导入导出和来源模板。
- 周报、日报、趋势和验证指标仪表盘。
- 更细粒度的来源、赛道和通知权重。
- 基于反馈的自动权重建议，但变更需用户确认。
- GitHub 发现结果排序模型、复杂趋势曲线、组织/贡献者/Issue 活跃度条件，以及基于反馈自动修改发现规则。
- 本地 embedding、语义检索，以及在缺少共享标识时基于语义相似度执行跨来源事件聚类的实验版本。
- Windows 生产代码签名、自动更新和公开安装包。

### Phase 3：扩展愿景

- 加密多设备同步。
- 团队共享赛道、规则、收藏和情报集合。
- macOS、Linux 与其他桌面平台支持。
- 可审计的个人研究代理。
- 与项目决策、技术选型和任务系统的受控关联。
- 面向更多技术研究和行业情报场景扩展。

### 风险缓解

**技术风险**

- 三种来源的数据结构差异大：使用统一适配器契约和固定 fixture。
- GitHub 项目发现受分页、限流和元数据缺失影响：使用有限执行预算、明确的不完整状态和来源退避；发现失败不得伪装为零结果或阻塞既有 Release 同步。
- Star/Fork 增长无法由单次快照证明：保存带时间戳的有效观测，首次观测只建立基线，缺失或失败观测不得按零值参与计算。
- 仓库重命名、转移及多条发现规则重叠可能制造重复监控：优先使用稳定仓库身份合并，并保持固定关注优先于自动关注。
- 筛选规则效果未知：先实现透明规则、反馈统计和被过滤审查。
- AI provider 兼容性不一致：能力探测、schema 校验和明确降级。
- Windows 系统行为难以通过浏览器测试：托盘、通知和开机启动必须在安装态验证。
- 移动端后台执行时机不确定：使用状态可见、前台补偿同步、幂等任务与可重试状态，不承诺持续常驻。
- 三端行为与设备形态差异大：以共享验收矩阵覆盖桌面、手机、平板、横竖屏、窗口调整和系统回收。
- 移动端存储、电量与网络受限：限制后台工作量，允许用户手动同步、清理缓存并查看本地占用。

**产品风险**

- 少推送可能掩盖漏报：同步监控准确度和漏报率，每周人工基准复盘。
- 默认赛道不匹配：允许首启后立即修改，并保留探索视图。
- Star/Fork 热度可能放大主流项目偏差：命中依据必须可见，用户可忽略、停用或固定关注，发现规则不得替代情报价值与溯源判断。
- AI 总结看似准确但误导：强制溯源、原文分区和分析错误反馈。
- 单人使用造成反馈偏差：首阶段目标就是验证个人价值，不外推市场结论。

**资源风险**

- 如果开发资源不足，可以减少每类来源的默认预置数量、简化视觉表现和高级系统集成，并调整 RSS/Atom、GitHub Release、arXiv 三类来源的内部交付顺序；三类来源仍均为最终 MVP 验收门禁，任一缺失时不得宣称 Phase 1 完成。所有已承诺平台仍须保留规则筛选、溯源、基础 AI 摘要、反馈闭环、离线缓存和前台同步。
- 不以复杂设置界面阻塞验证，初期参数可使用简单表单与合理默认值。
- 不提前建设 Phase 2 数据结构，除非它是来源适配器或领域模型的自然扩展点。

## 功能需求

### 验收术语与判定口径

- **演示数据：** 不由真实来源同步产生、仅用于首次体验的示例记录；列表、详情和搜索结果中均须显示“演示数据”，不得触发真实通知或计入验证指标。
- **必要摘录：** 为列表预览、搜索、溯源和理解分析结果所需的最小原文片段，不等同于完整正文；未收藏情报不得借“摘录”名义持久化可实质还原全文的内容。
- **有效原文链接：** 可解析的 HTTP/HTTPS 公网地址，目标不属于本机、内网或受禁止的地址范围；当前可访问性通过“原文可用状态”另行表示。
- **技术影响：** 对模型能力、开发框架、部署方式、成本、安全或技术选型至少一项产生可说明的影响。
- **情报价值：** 赛道匹配、来源可信度、新鲜度、技术影响及用户规则的可解释组合结果。
- **重要程度：** 按用户当前评分规则得到的明确等级及理由。
- **高价值情报：** 满足用户当前赛道及规则条件，且重要程度达到主情报流阈值的情报；验证期以主情报流“有价值”反馈占比 ≥70% 评估总体效果。
- **普通候选：** 未达到主情报流阈值但仍合法、可溯源并保留供用户审查的内容。
- **重大动态：** 同时满足高价值条件、完整溯源门槛和用户提醒阈值的情报；验证期以通知“值得立即知道”反馈占比 ≥80% 且已确认关键漏报为 0 评估总体效果。
- **确定性重复或关联：** 可由规范化原文链接、来源内容标识、内容版本或其他可验证共享标识判定；仅有主题或语义相似不构成 Phase 1 的自动合并依据。
- **明确标识 AI 内容：** 每个 AI 生成字段或连续内容区均可与原始事实、规则判断区分，并显示 AI 生成属性及待配置、等待分析、分析中、已完成、失败或已禁用等处理状态。
- **用户处理状态：** 每条情报在当前设备上具有且仅具有“未查看”“已判断”“待研究”之一；新入库情报默认为“未查看”，仅浏览列表或打开详情不得自动改变状态。用户可显式在三种状态间转换；状态与收藏、价值反馈及 AI 处理状态是相互独立的维度。
- **过窄配置风险：** 配置格式与逻辑有效、允许保存，但会停用全部来源采集路径，或在当前设备存在可评估候选情报时将全部高可信候选过滤；该结果仅提示可能漏报，不表示未来必然漏报，也不等同于阻断性无效配置。
- **阻断性无效配置：** 配置无法形成可执行且符合字段约束的规则，包括已填写表达式无法解析、数值或日期超出界面声明范围、同一范围的下界高于上界，以及来源地址或标识格式无效或使用不受支持的协议；仅因条件组合可能过滤全部候选或停用全部来源，不得归入阻断性无效配置，而应按“过窄配置风险”处理。
- **同步结果摘要：** 某次全部来源或单个来源同步产生的来源级新增、更新、跳过和失败数量，以及本次成功转换的最小规范化结果列表；零结果、部分成功和失败必须分别表达。
- **GitHub 仓库规范身份：** 优先使用 GitHub 返回的稳定仓库标识，无法取得时使用规范化 `owner/name`；仓库重命名或转移不得因此创建第二个本地项目、第二个有效 Release 同步任务或重复通知。
- **GitHub 项目发现订阅：** 用户在当前设备保存的一组公开项目发现条件，包括关注赛道、主要语言、GitHub Topic、Star/Fork 当前门槛，以及指定观察窗口内的绝对增长或增长比例条件；不同维度之间按“同时满足”组合，同一维度的多个值按“满足任一”组合，保存前必须显示实际组合逻辑。
- **新发现项目：** 某 GitHub 仓库规范身份首次进入当前设备的发现结果集；首次成功执行发现订阅时已符合条件的仓库也属于新发现，但不表示仓库刚在 GitHub 创建。已经以固定关注、其他自动订阅关注、停用或当前订阅忽略状态存在的仓库不得再次计为新发现，后续命中新订阅时只追加命中依据。
- **新符合条件项目：** 当前设备已存在有效观测但此前未满足发现订阅，本轮首次跨过当前门槛的仓库；不得与“新发现项目”混用。
- **GitHub 增长条件：** 仅在同一仓库至少两个成功采集且带时间戳的 Star/Fork 观测值之间计算；首次观测只建立基线，失败、限流或缺失观测不得按零值计算。绝对增长为观察窗口内末值减首值；增长比例以窗口首个有效值为分母，首值为零时不得使用比例增长命中。
- **GitHub 发现命中依据：** 项目实际满足的发现订阅条件、用于判断的可获得观测值及观测时间；多个订阅命中同一项目时须保留各订阅的命中依据。
- **GitHub 固定关注：** 用户手动指定，或由自动发现项目显式转换而来的项目关注状态；固定关注不再依赖原发现订阅继续成立，且优先于自动关注。
- **GitHub 自动关注控制：** 停用保留项目、命中依据和历史数据，但暂停该项目由自动发现产生的后续 Release 同步；忽略按当前设备和当前发现订阅抑制项目再次作为新发现出现并停止该订阅建立自动关注，用户可撤销。忽略不得停止同一项目的固定关注或其他有效关注。
- **合法获取的正文：** 通过无需登录的公开页面或获准使用的官方接口取得，且保存行为符合该来源已记录的访问、版权与缓存条件。
- **可解释：** 用户可查看影响筛选、排序或反馈汇总结果的规则、来源条件、反馈关系及原因。
- **可操作错误信息：** 至少指出受影响来源或任务、失败阶段、发生时间、可识别原因，以及重试、修改配置、等待退避或继续离线使用等适用下一步；不得包含密钥、完整正文或敏感提示内容。
- **敏感提示内容：** AI 请求模板中的系统指令、受保护配置或被明确标为不得导出的提示内容。

### 首次启动与个性化配置

- FR1：用户无需注册或配置 AI 服务即可首次使用产品。
- FR2：用户首次启动时可以浏览按“演示数据”口径明确标识的示例情报，且这些记录不得触发真实通知或计入验证指标。
- FR3：用户首次启动时可以使用预置的 AI 技术赛道和默认来源。
- FR4：用户可以添加、修改、启用或停用关注赛道。
- FR5：用户可以配置关键词、排除词、关注来源和刷新周期。
- FR6：用户可以配置来源可信度、提醒阈值、免打扰时段和提醒频率上限。

### 信息来源与采集

- FR7：用户可以订阅公开的 RSS/Atom 信息源。
- FR8：用户可以监控指定 GitHub 项目的 Release 更新。
- FR9：用户可以监控指定主题、关键词或分类的 arXiv 论文。
- FR10：系统可以在每台受支持设备上按照该设备的来源配置执行增量同步；移动端在系统不允许后台执行时，可以在下次获得执行机会或用户前台触发后继续。
- FR11：用户可以在当前设备手动触发全部来源或单个来源同步。
- FR12：系统可以分别显示当前设备各来源的同步进度、最后成功时间、失败状态、待处理任务、数据新鲜度及后台受限状态，并提供最近一次同步的新增、更新、跳过与失败数量及同步结果入口。

### 情报标准化、溯源与内容生命周期

- FR13：系统可以将不同来源内容转换为统一的情报记录。
- FR14：系统必须为每条情报保留来源类型、发布方、原始标题、有效原文链接、发布时间、采集时间和内容标识；来源能够提供作者时还必须保留作者，不能提供时须明确记录为不可获得。
- FR15：用户可以查看情报首次发现时间、最后更新时间和原文可用状态。
- FR16：系统可以区分原始事实、规则判断与 AI 分析。
- FR17：对于未收藏情报，系统仅可长期保存元数据、原文链接、符合“必要摘录”口径的片段和 AI 分析，不得持久化完整正文或可实质还原全文的内容。
- FR18：用户收藏情报时，可以保存合法获取的完整正文快照；取消收藏后可以删除该正文及其派生索引。

### 高价值筛选、排序与去重

- FR19：系统可以依据赛道匹配、来源可信度、新鲜度、技术影响和用户配置规则形成“情报价值”判断，且用户能够查看影响该判断的因素。
- FR20：系统可以为情报给出“重要程度”，并展示促成该结果的赛道、来源、新鲜度、技术影响、规则命中及适用的 AI 判断依据。
- FR21：系统可以按照用户当前主情报流阈值将“高价值情报”与“普通候选”区分，阈值变化不得删除或改写原始情报记录。
- FR22：用户可以查看被过滤的内容及其过滤原因。
- FR23：Phase 1 中，系统可以依据“确定性重复或关联”口径识别重复内容；不得仅凭语义相似自动合并记录。
- FR24：Phase 1 中，系统可以依据上述确定性共享标识关联至少 2 个指向同一事件的来源记录，并保留每个来源各自的标题、链接、发布时间、发布方及其他溯源记录供用户展开核验。

### AI 翻译与分析

- FR25：用户可以在当前设备配置、更新或移除兼容 OpenAI 接口规范的第三方 AI 服务凭据；配置不得自动传播到其他设备。
- FR26：系统可以在每台设备首次向第三方 AI 服务发送内容前说明将发送的数据，并取得用户确认。
- FR27：系统可以默认对新情报执行中文翻译、摘要、主题提取、重要度判断、置信度生成和理由生成，并在情报详情中展示置信度。
- FR28：用户可以在当前设备按来源决定是否允许向第三方 AI 服务发送内容，并可随时撤销授权。
- FR29：系统必须按“明确标识 AI 内容”口径区分所有 AI 生成字段与原始事实、规则判断，并显示每条情报当前的 AI 处理状态。
- FR30：AI 服务不可用、输出无效或用户未配置有效凭据时，系统仍可以保留并展示原始情报，供稍后重试。

### 浏览、检索与收藏

- FR31：用户可以浏览经过筛选和排序的主情报流。
- FR32：用户可以按赛道、来源、时间、重要度、用户处理状态和收藏状态筛选情报；用户处理状态与 AI 处理状态必须使用不同名称和筛选语义。
- FR33：用户可以搜索已保存的情报元数据、符合“必要摘录”口径的片段和当前可用的收藏正文；搜索结果必须遵守内容生命周期边界，不得暴露已删除正文或未获准持久化的全文内容。
- FR34：用户可以查看单条情报的内容提炼、评分依据、溯源信息和关联来源。
- FR35：用户可以从情报详情打开原始内容进行核验。
- FR36：用户可以收藏、取消收藏并离线阅读已保存的正文快照；收藏变化及正文删除不得隐式改变用户处理状态。

### 重大提醒与平台驻留

- FR37：当前设备只有在本地完成情报判定，且该情报同时满足“重大动态”口径、完整溯源要求、用户提醒阈值和当前设备通知授权时，才可以向操作系统提交通知；条件不满足时不得以重大动态名义通知。MVP 不依赖远程推送生成该通知。
- FR38：用户点击通知后可以直接打开对应情报详情。
- FR39：系统可以在当前设备内防止同一情报或内容版本产生重复通知；MVP 不承诺跨设备通知去重。
- FR40：系统可以遵守用户设置的免打扰时段、通知频率上限和操作系统通知授权；权限不足时须显示提醒不可送达状态。
- FR41：在 Windows 上，用户关闭主窗口后，系统可以继续在托盘运行和同步。
- FR42：在 Windows 上，用户可以从托盘显示主窗口、立即同步或显式退出应用，并可以控制开机自动启动。

### 反馈验证、故障恢复与诊断

- FR43：用户可以将情报标记为“值得立即知道”“有价值但不紧急”“无价值”“重复”或“分析错误”。
- FR44：用户可以记录已确认的漏报及其原因。
- FR45：系统可以汇总提醒有效率、主情报流有效率、漏报和每日使用情况，支持四周个人验证。
- FR46：系统可以按赛道、来源、规则命中和筛选结果汇总用户反馈，供用户识别误报与漏报原因并手动校准“可解释”的筛选规则；Phase 1 不得据此自动修改权重或规则。
- FR47：当前设备的单个来源失败时，系统可以继续处理其他来源并保留已成功结果。
- FR48：用户可以在当前设备单独重试失败来源或待处理的 AI 分析任务；来源处于强制退避期间时须说明暂不可重试的原因和时间。
- FR49：离线、后台挂起或应用恢复后，用户仍可以浏览、搜索、筛选、收藏、配置和反馈；系统再次获得联网与执行机会后可以恢复有效待处理任务。
- FR50：用户可以查看按“可操作错误信息”口径呈现的来源级状态，并通过当前平台提供的复制或分享能力导出不含 API Key、完整正文、敏感提示内容或其他凭据的脱敏诊断信息。

### 平台生命周期、权限与设备边界

- FR51：在 iOS/iPadOS 与 Android 上，系统可以保存应用挂起、终止或进程被回收前已经完成的数据和可恢复任务状态；再次获得执行机会后，可以继续处理可恢复任务，或将无法继续的任务明确标记为可重试。
- FR52：用户可以在所有平台查看最后成功同步时间、当前同步状态和影响时效性的后台限制，并可在前台手动触发同步。
- FR53：系统只能在需要发送重大动态通知时请求通知权限；用户拒绝或撤销后，系统不得阻断采集、浏览、检索、溯源、反馈或前台同步，也不得在每次启动时重复强迫授权。
- FR54：用户从系统通知进入应用时，无论应用正在前台、后台或尚未运行，系统都可以打开对应情报详情；目标已删除或不可用时必须说明原因并提供返回主情报流的入口。
- FR55：用户可以在 Windows、iPhone、iPad、Android 手机和 Android 平板上完成首启、主情报流浏览、搜索、详情、收藏、溯源、设置、反馈和同步状态查看。
- FR56：系统可以根据桌面、手机、平板、窗口宽度、横竖屏和输入方式调整导航与布局，同时保持功能含义、筛选状态和当前任务上下文一致。
- FR57：系统必须将配置、收藏、反馈、凭据和历史情报保存在当前设备的数据边界内，并在首次使用与设置中明确说明 MVP 不提供云端备份或跨设备同步。
- FR58：用户可以在卸载、清除应用数据或执行可能删除本地数据的操作前看到数据保留后果；产品不得暗示未配置的恢复或迁移能力。

### MVP 同步结果与用户处理闭环

- FR59：用户在当前设备完成全部来源或单个来源同步后，可以分别查看 RSS/Atom、GitHub Release 和 arXiv 本次同步的新增、更新、跳过与失败数量，以及本次成功转换的最小结果列表。每项至少展示来源类型、发布方、原始标题、发布时间（来源可提供时）、采集时间和原文链接。该结果不得依赖 AI 凭据、评分、搜索或完整详情；零结果和部分失败须明确呈现，且部分失败不得隐藏已成功结果。
- FR60：用户可以在当前设备将每条情报显式设置为“未查看”“已判断”或“待研究”，并在三种状态间转换；新入库情报默认为“未查看”，仅浏览列表或打开详情不得自动改变状态。状态须在应用重启、离线、平台生命周期恢复和受支持版本升级后保留。收藏是独立维度，任一用户处理状态均可收藏或不收藏，收藏变化及正文删除不得隐式改变处理状态。

### MVP 引导、配置风险与 Windows 单实例

- FR61：系统可以在用户已能浏览主情报流后提供分步配置引导；所有可延后步骤均可跳过，跳过或退出不得阻断主情报流、同步、搜索和详情查看。用户可以从“设置”根级页面中名称为“配置引导”的固定入口继续未完成步骤；从主情报流到达该入口不得超过两次用户发起的导航操作，且已保存的配置不得丢失。
- FR62：系统在保存赛道、关键词、排除词、来源或阈值配置前，必须按照验收术语中的判定口径区分阻断性无效配置与“过窄配置风险”。阻断性无效配置不得保存，并须指出受影响字段、所属无效类别和修正方式；检测到过窄配置风险时，须指出受影响条件和可能漏报的后果，并允许用户返回修改或明确确认后保存；未检测到风险时不得要求额外确认。
- FR63：在 Windows 同一用户会话中，系统只允许一个可交互应用实例；已有实例运行时，包括主窗口已隐藏至托盘的状态，再次启动必须显示并聚焦现有主窗口，不得创建第二个可交互实例。

### MVP GitHub 项目发现

- FR64：用户可以在当前设备保留通过仓库标识手动建立的 GitHub Release 固定关注，并可以创建、修改、启用或停用 GitHub 项目发现订阅。发现订阅可以按关注赛道、主要语言、GitHub Topic、Star/Fork 当前门槛及“GitHub 增长条件”发现公开仓库；系统必须按“新发现项目”和“新符合条件项目”口径展示结果，为每个项目显示“GitHub 发现命中依据”，并将符合条件的项目自动纳入 Release 监控。用户可以忽略发现项目、停用其自动关注或将其转为固定关注。系统必须按“GitHub 仓库规范身份”合并手动关注、多个发现订阅及仓库重命名或转移产生的同一项目，固定关注优先于自动关注；同一项目在当前设备只能形成一个项目对象和一个有效 Release 监控对象，不得产生重复 Release 记录或重复通知。发现订阅停用、条件失配或项目被忽略不得删除已经保存的 Release、反馈、收藏或其他合法保留的历史数据；发现任务失败或受限不得阻断既有项目的 Release 同步。

## 非功能需求

### 统一测量基线

除单条需求另有说明外，NFR 按以下统一基线验收：

- **候选构建：** 拟进入当前阶段验收的安装版构建，使用与该阶段目标发布形态相同的默认配置和升级路径；测试结果不得以开发态或调试态构建替代。Windows MVP 候选构建可以不具备生产代码签名，但必须符合受控手动安装边界；移动候选构建必须满足 NFR51 的测试分发签名、安装资格和隐私披露门禁。
- **支持环境：** Windows 10/11 x64、iOS/iPadOS 17 及以上和 Android 10 及以上；Windows 以当前用户权限安装，移动端以普通应用权限安装。候选构建发布说明须冻结实际测试的小版本范围，验收不得临时缩小支持范围。
- **Windows 基线设备：** 4 核 x64 处理器、8 GB 内存、SSD、1920×1080 显示器。
- **移动基线设备：** 每个平台至少包含一台处于声明最低系统版本与最低支持内存档位的手机、一台当前主流手机和一台平板；Android 另含一个可调整窗口或折叠态设备配置。设备型号、系统版本、屏幕尺寸、内存与电池状态随验收记录冻结。
- **固定数据集与配置样本：** 包含 50,000 条情报、收藏、反馈、重复内容、内容更新、缺失字段和多种发布时间格式的固定可复现数据集；配置样本须为“表达式无法解析”“数值或日期越界”“范围下界高于上界”“来源地址或标识无效或协议不受支持”四类阻断性无效配置各提供至少 1 个固定样本，并分别提供“全部来源停用”和“全部高可信候选被过滤”的固定过窄配置风险样本。GitHub 固定响应集须覆盖赛道、主要语言、Topic、当前 Star/Fork 边界、至少两个带时间戳的增长观测、零基数、首次基线、仓库重命名或转移、手动与自动关注重叠、多个发现订阅重叠、忽略、停用、转固定关注、分页部分失败、限流和无效响应。涉及外部响应时使用内容与时序固定的服务响应集。
- **时延采样：** 每个平台类别、每项被测操作至少完成 100 次有效样本；Windows、iPhone、iPad、Android 手机和 Android 平板分别计算 P95，预热过程不计入样本。
- **资源采样：** 进入规定状态并稳定 2 分钟后，以不长于 1 秒的间隔连续采样 10 分钟，记录平均值、P95 和峰值。
- **固定故障场景：** 至少覆盖单一来源失败、全部来源不可达、网络中断与恢复、AI 超时、AI 限流、无效 AI 结果、应用崩溃、系统重启、系统休眠与恢复、移动端挂起与终止、进程回收、通知权限拒绝与撤销、存储空间不足、数据库完整性异常、缺少运行环境、恶意或超限外部响应。
- **全场景规则：** 条款中的“不得”“必须”和“100%”表示其适用的全部平台、固定数据、状态组合与故障场景均须通过；任一适用场景失败即判定该 NFR 未通过。
- **验收记录：** 每项测试保留候选构建版本、操作系统版本、硬件配置、数据集版本、前置条件、实际结果及通过结论，以便复现。

### 性能

- **NFR1：** 条件：在推荐硬件上首次安装并启动候选构建，且尚无用户数据。测量方法：从用户发起启动开始计时，至示例情报可见且可滚动、打开详情为止。通过判据：每个平台至少 100 次样本的 P95 ≤5 秒。保护目标：避免首次体验因等待过长而中断。
- **NFR2：** 条件：本地已加载固定 50,000 条情报数据集。测量方法：分别测量主情报流首屏、常用筛选、关键词搜索和搜索结果首屏的操作完成时间。通过判据：每类操作至少 100 次样本的 P95 均 <200 毫秒。保护目标：保证数据增长后日常浏览和检索仍然流畅。
- **NFR3：** 条件：来源同步、正文处理和 AI 分析分别单独运行及同时运行。测量方法：并发执行浏览、滚动、搜索和设置保存，各操作至少 100 次，并记录界面无响应事件。通过判据：界面无响应事件为 0，用户操作 P95 ≤500 毫秒，任何单次操作不得因后台任务持续阻塞超过 1 秒。保护目标：保证后台工作不剥夺用户对应用的控制。
- **NFR4：** 条件：当前设备已在本地完成内容采集和高优先级判定，并满足展示或提醒条件；移动端仅统计应用正在运行或系统已授予执行机会的时段。测量方法：记录本地判定完成时间以及进入主情报流或向操作系统提交通知的时间，使用至少 100 条固定样本。通过判据：每条样本均在 60 秒内进入主情报流；满足提醒条件且已获通知权限的样本也须在 60 秒内向操作系统提交通知；系统未授予后台执行机会的时段不进入产品可控时延，恢复执行后仍有效的任务须在 60 秒内处理；已失去提醒时效的任务可以进入主情报流，但补发“即时”通知的次数必须为 0。保护目标：确保设备本地重大动态及时支持决策，同时不承诺操作系统未授予的后台时段或远程推送能力。
- **NFR5：** 条件：Windows 候选构建位于后台空闲状态，当前无同步、AI 分析、用户交互或待执行任务。测量方法：按统一资源采样规则记录应用进程总 CPU 占用。通过判据：10 分钟窗口平均 CPU <2%，且不得出现持续 30 秒以上高于 5% 的占用。保护目标：减少桌面常驻对电量、散热和其他工作的影响。
- **NFR6：** 条件：Windows 候选构建已加载固定 50,000 条数据集，但当前未执行同步和 AI 分析。测量方法：依次完成主情报流、搜索、详情、收藏和设置操作，随后按统一资源采样规则记录应用进程工作集。通过判据：10 分钟窗口内存 P95 ≤250 MB，且窗口内不得持续增长超过 10%。保护目标：控制长期常驻内存压力并识别明显资源泄漏。

### 可靠性与数据完整性

- **NFR7：** 条件：多个来源同时同步，并分别向每类来源注入超时、无效响应和连接失败。测量方法：核对未故障来源的完成状态、已保存记录及失败来源的错误状态。通过判据：全部固定场景中，未故障来源均正常完成，已成功保存结果的记录数和字段值不回退，失败仅归属于对应来源。保护目标：将单点外部故障限制在最小范围。
- **NFR8：** 条件：对固定数据集中的同一内容版本跨轮次重复同步，并包含应用重启和网络恢复后的重试。测量方法：比对内容标识、入库记录和通知记录。通过判据：重复入库率为 0，重复通知率为 0。保护目标：防止重复内容污染信息流和打扰用户。
- **NFR9：** 条件：分别在保存完成后及任务处理中触发应用崩溃、系统重启、网络中断、移动端挂起、终止和低资源回收。测量方法：恢复应用后核对已完成记录的数量与字段值，并观察未完成任务的恢复或重新执行结果。通过判据：已完成数据损坏或丢失为 0；每个未完成任务均安全恢复、重新执行或明确标记为可重试，且不产生重复结果。保护目标：保护用户数据并确保意外中断后可继续工作。
- **NFR10：** 条件：分别进入离线、无有效 AI Key、AI 服务超时三种状态，并预先加载固定缓存数据。测量方法：逐项执行主情报流浏览、搜索、详情查看和收藏访问。通过判据：三种状态下缓存内容可访问率均为 100%，且外部服务失败不得阻断这些操作。保护目标：维持本地优先和弱网可用性。
- **NFR11：** 条件：使用同时包含完整溯源、缺失来源、无原始链接和来源失效内容的固定样本。测量方法：核对高优先级入库结果、溯源字段和重大提醒记录。通过判据：触发重大提醒的高优先级情报有效溯源信息完整率为 100%；任一未达到溯源门槛的样本触发提醒即失败。保护目标：避免不可核验内容驱动重要决策。
- **NFR12：** 条件：从每个受支持的既有数据版本升级至候选构建，数据中包含用户配置、收藏、反馈和历史情报。测量方法：升级前后比较记录数量、关键字段值及关联关系。通过判据：上述数据的静默丢失、清空或错误改写数量均为 0；无法迁移时必须停止升级并提供明确恢复提示。保护目标：保护升级过程中的长期用户资产。
- **NFR13：** 条件：在同步、分析和通知的不同阶段触发系统休眠、网络断开、移动端挂起、进程回收及设备重启，随后恢复并执行补偿同步。测量方法：核对任务执行记录、分析结果和通知结果。通过判据：每个逻辑任务最多产生一份有效入库结果、一份有效分析和一次通知；并发重复任务数量为 0。保护目标：防止环境恢复造成重复工作和重复打扰。
- **NFR14：** 条件：运行期间注入可检测的数据库完整性错误。测量方法：尝试对受影响数据继续写入，并检查错误提示中的影响对象、数据安全状态和恢复步骤。通过判据：相关写入成功次数为 0；所有固定错误场景均显示可操作恢复提示，且未受影响的已保存数据保持可读取。保护目标：阻止错误扩散并帮助用户安全恢复。

### 安全与隐私

- **NFR15：** 条件：配置、更新、使用和删除 API Key，并执行正常操作、错误诊断与诊断导出。测量方法：检查操作系统安全凭据存储状态，并搜索内容数据库、界面持久状态、日志、诊断导出和测试数据中的完整密钥及可还原片段。通过判据：密钥仅存在于操作系统提供的安全凭据存储中；其他检查位置命中数为 0。保护目标：防止凭据泄露和非预期持久化。
- **NFR16：** 条件：访问全部受支持外部来源和 AI 服务，并配置一个用户主动指定的本地服务地址。测量方法：记录每次连接的目标和传输协议。通过判据：除用户主动配置的本地服务地址外，外部连接未加密次数为 0；发生证书或加密校验失败时不得继续传输内容或凭据。保护目标：防止传输过程中的窃听和篡改。
- **NFR17：** 条件：来源内容包含指向本机地址、环回地址、内网地址、非允许协议及经重定向抵达这些目标的链接。测量方法：执行固定恶意样本并记录所有实际网络访问目标。通过判据：对上述目标和协议的实际访问次数为 0，且其他合法来源仍可继续处理。保护目标：防止不可信内容诱导应用探测或访问受保护网络资源。
- **NFR18：** 条件：外部来源分别返回超大响应、重定向链、慢速响应及其组合。测量方法：记录单次响应接收字节数、跟随重定向次数、处理持续时间和应用资源状态。通过判据：单个外部响应最多接收 10 MB、最多跟随 5 次重定向、单次处理最长 30 秒；达到任一上限后必须终止该请求并保留可诊断错误，且应用保持可操作。保护目标：防止单一恶意或异常来源耗尽本机资源。
- **NFR19：** 条件：对未收藏正文完成采集、临时处理、AI 分析、失败重试和应用重启。测量方法：处理完成后检查数据库、日志、崩溃信息及持久化临时文件中的完整正文或可复原正文。通过判据：未收藏完整正文的持久化残留数量为 0；仅允许保留需求明确要求的必要摘录和分析结果。保护目标：最小化用户未选择保留的内容及潜在敏感信息。
- **NFR20：** 条件：在包含密钥、授权头、完整正文和敏感提示内容的正常及故障场景中生成诊断信息。测量方法：导出并检查全部诊断字段。通过判据：完整密钥、可用授权头、完整正文和敏感提示内容的命中数均为 0；被移除内容以不泄露原值的标识替代。保护目标：使故障排查材料能够安全分享。
- **NFR21：** 条件：分别对来源授予或撤销第三方 AI 分析授权，并在关闭总开关时存在排队任务。测量方法：记录授权状态变化后的新外发请求及其来源。通过判据：未经用户确认或未获对应来源授权的内容外发次数为 0；关闭后不得发起新的内容请求，排队任务不得继续发送。保护目标：确保用户掌控内容是否交给第三方处理。
- **NFR22：** 条件：收藏正文已建立索引并可搜索，随后用户删除该正文及其索引。测量方法：重新启动应用后，通过关键词搜索、详情、收藏和历史入口尝试访问被删正文。通过判据：被删正文的搜索命中、展示和可访问残留均为 0；不含正文的必要收藏元数据仅在产品规则允许时保留。保护目标：落实用户删除意图并避免内容残留。

### 外部服务适配

- **NFR23：** 条件：分别向 RSS/Atom、GitHub Release 和 arXiv 来源连接注入连接失败、无效响应和解析错误，同时保持其他来源连接正常。测量方法：核对错误归属、诊断记录、可重试状态及其他来源连接结果。通过判据：每项错误均被准确归属于对应来源并可独立重试；其他来源连接成功率不受该错误影响。保护目标：实现来源级故障隔离和可诊断恢复。
- **NFR24：** 条件：来源分别返回带有效重试指示、无重试指示和连续限流响应。测量方法：记录限流后的每次请求时间及来源给出的重试时间。通过判据：存在有效重试指示时，在指定时间前请求次数为 0；无明确指示时首次重试间隔 ≥60 秒，连续重试间隔不得缩短，第三次间隔至少为首次的 4 倍，且不得持续高频请求。保护目标：尊重外部服务容量并避免扩大限流。
- **NFR25：** 条件：AI 服务分别返回超时、限流、无效结构和不完整结果。测量方法：检查用户界面、保存结果和后续流程中的状态标识。通过判据：上述结果被标记为有效 AI 分析的次数为 0；系统必须保留明确的失败或待重试状态，不得以推测性兜底文本伪装成功。保护目标：维护 AI 分析的可信边界。
- **NFR26：** 条件：每类来源使用缺失作者、缺失摘要、不同发布时间格式及同一内容更新的固定样本。测量方法：同步后核对有效内容是否入库、溯源是否保留、更新是否反映。通过判据：仍可溯源的有效样本因上述字段差异被丢弃的数量为 0；无法解析的字段必须留空或明确标识，不得伪造值。保护目标：提高真实世界来源差异下的数据覆盖与可信度。
- **NFR27：** 条件：外部来源或 AI 服务在任务处理过程中不可用，形成待处理任务后恢复服务。测量方法：观察任务是否自动继续，并核对入库、分析和通知结果。通过判据：所有仍有效的待处理任务均无需用户重新创建即可继续；每个逻辑任务最多产生一份有效入库结果、一份有效分析和一次通知。保护目标：在短暂外部故障后自动恢复且不产生重复副作用。

### 可用性与无障碍

- **NFR28：** 条件：在每类受支持设备上全新安装，用户不注册、不连接云端账户、不配置 AI Key 且不授予通知权限。测量方法：从首次启动开始执行示例情报浏览、详情查看和基础筛选。通过判据：上述首次体验任务完成率为 100%，过程中不得出现强制注册、强制云端连接、强制配置 AI Key 或强制通知授权。保护目标：降低首次使用门槛并兑现本地优先体验。
- **NFR29：** 条件：分别展示示例数据、原始事实、规则判断、AI 分析、离线状态和待分析状态，并在彩色、灰度和常见色觉差异模拟下检查。测量方法：核对每种状态是否具有可见文字、图标或形状标识。通过判据：六类状态的非颜色区分覆盖率为 100%，任意两类不得仅以颜色差异区分。保护目标：避免用户混淆事实、推断和系统状态，并支持色觉差异用户。
