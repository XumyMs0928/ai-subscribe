# ai-subscribe - Epic 与 Story 拆解

## 概述

本文档汇总 ai-subscribe 的完整需求库存，并将在后续步骤中把 PRD、UX 与架构要求拆分为可实施的 Epic 和 Story。

## 需求库存

### 功能需求

- FR1：用户无需注册或配置 AI 服务即可首次使用产品。
- FR2：首次启动可浏览明确标识的演示情报；演示记录不得触发真实通知或计入验证指标。
- FR3：首次启动可使用预置的 AI 技术赛道和默认来源。
- FR4：用户可添加、修改、启用或停用关注赛道。
- FR5：用户可配置关键词、排除词、关注来源和刷新周期。
- FR6：用户可配置来源可信度、提醒阈值、免打扰时段和提醒频率上限。
- FR7：用户可订阅公开 RSS/Atom 信息源。
- FR8：用户可监控指定 GitHub 项目的 Release 更新。
- FR9：用户可监控指定主题、关键词或分类的 arXiv 论文。
- FR10：各设备按本机来源配置增量同步；移动端受后台限制时在下次执行机会或前台触发后继续。
- FR11：用户可在当前设备手动触发全部或单个来源同步。
- FR12：系统分别显示各来源同步进度、最后成功时间、失败状态、待处理任务、数据新鲜度及后台限制，并提供最近一次同步的新增、更新、跳过与失败数量及同步结果入口。
- FR13：系统将不同来源内容转换为统一情报记录。
- FR14：每条情报保留来源类型、发布方、原始标题、有效原文链接、发布时间、采集时间、内容标识及可获得的作者；缺失作者须明确标识。
- FR15：用户可查看首次发现时间、最后更新时间和原文可用状态。
- FR16：系统区分原始事实、规则判断和 AI 分析。
- FR17：未收藏情报仅长期保存元数据、原文链接、必要摘录和 AI 分析，不得持久化完整或可还原全文。
- FR18：收藏时可保存合法获取的正文快照；取消收藏后可删除正文及派生索引。
- FR19：系统依据赛道、来源可信度、新鲜度、技术影响和用户规则判断情报价值，并向用户解释影响因素。
- FR20：系统给出重要程度，并展示赛道、来源、新鲜度、技术影响、规则命中及适用 AI 判断依据。
- FR21：系统按当前阈值区分高价值情报与普通候选；阈值变化不得删除或改写原始记录。
- FR22：用户可查看被过滤内容及过滤原因。
- FR23：Phase 1 仅依据确定性共享标识识别重复，不得仅凭语义相似自动合并。
- FR24：系统可依据确定性共享标识关联至少两个同事件来源，并保留各自完整溯源记录供展开核验。
- FR25：用户可在当前设备配置、更新或移除 OpenAI-compatible 第三方 AI 凭据，配置不自动传播到其他设备。
- FR26：每台设备首次向第三方 AI 发送内容前说明发送数据并取得确认。
- FR27：系统默认为新情报执行中文翻译、摘要、主题、重要度、置信度和理由生成，并在详情展示置信度。
- FR28：用户可按来源允许或禁止第三方 AI 内容发送，并可撤销授权。
- FR29：所有 AI 生成字段必须与事实和规则判断区分，并显示 AI 处理状态。
- FR30：AI 不可用、输出无效或无凭据时仍保留和展示原始情报，支持稍后重试。
- FR31：用户可浏览筛选和排序后的主情报流。
- FR32：用户可按赛道、来源、时间、重要度、用户处理状态和收藏状态筛选；用户处理状态与 AI 处理状态必须使用不同名称和筛选语义。
- FR33：用户可搜索元数据、必要摘录和可用收藏正文；不得暴露已删除或未获准持久化的全文。
- FR34：用户可查看内容提炼、评分依据、溯源和关联来源。
- FR35：用户可从详情打开原文核验。
- FR36：用户可收藏、取消收藏并离线阅读已保存正文；收藏变化及正文删除不得隐式改变用户处理状态。
- FR37：仅当当前设备本地完成判定且满足重大动态、完整溯源、阈值和通知授权时提交系统通知；MVP 不依赖远程推送。
- FR38：点击通知可直接打开对应情报详情。
- FR39：当前设备内防止同一情报或内容版本重复通知；MVP 不承诺跨设备去重。
- FR40：系统遵守免打扰、频率上限和系统授权；权限不足时显示不可送达状态。
- FR41：Windows 关闭主窗口后可继续在托盘运行和同步。
- FR42：Windows 用户可从托盘显示窗口、立即同步、显式退出并控制开机启动。
- FR43：用户可标记值得立即知道、有价值但不紧急、无价值、重复或分析错误。
- FR44：用户可记录已确认漏报及原因。
- FR45：系统汇总提醒有效率、主情报流有效率、漏报和每日使用情况，支持四周验证。
- FR46：系统按赛道、来源、规则和筛选结果汇总反馈，支持手动校准；Phase 1 不得自动改权重或规则。
- FR47：单个来源失败时继续其他来源并保留成功结果。
- FR48：用户可单独重试失败来源或 AI 任务；强制退避期间说明不可重试原因和时间。
- FR49：离线、挂起或恢复后仍可浏览、搜索、筛选、收藏、配置和反馈；重新获得机会后恢复有效任务。
- FR50：用户可查看可操作的来源级错误，并导出不含密钥、完整正文、敏感提示或凭据的脱敏诊断。
- FR51：iOS/iPadOS 与 Android 保存挂起、终止或回收前的完成数据和可恢复任务，恢复后续作或标记可重试。
- FR52：全平台显示最后成功同步、当前状态和后台限制，并支持前台手动同步。
- FR53：仅在确需重大通知时请求通知权限；拒绝或撤销不得阻断非通知能力，也不得反复强迫授权。
- FR54：通知深链在前台、后台和冷启动均打开目标；目标不可用时说明原因并提供主情报流入口。
- FR55：Windows、iPhone、iPad、Android 手机和平板均可独立完成全部核心旅程。
- FR56：系统适配设备、窗口、方向和输入方式，同时保持功能语义、筛选和任务上下文。
- FR57：配置、收藏、反馈、凭据和历史均保存在当前设备，并明确 MVP 无云备份或跨设备同步。
- FR58：卸载、清除或破坏性数据操作前说明保留后果，不暗示不存在的恢复或迁移能力。
- FR59：完成全部或单个来源同步后，用户可查看 RSS/Atom、GitHub Release、arXiv 各自的新增、更新、跳过、失败数量及本轮成功转换的最小结果列表；列表至少含来源类型、发布方、原始标题、可获得的发布时间、采集时间和原文链接，且不依赖 AI、评分、搜索或完整详情；零结果与部分失败必须明确，失败不得隐藏成功结果。
- FR60：用户可把每条情报显式设置为且仅设置为“未查看”“已判断”“待研究”之一并三态互转；新条目默认未查看，浏览或打开详情不自动改变；状态须跨重启、离线、生命周期恢复和升级保留，并与收藏及正文生命周期独立。
- FR61：主情报流可用后提供分步配置引导；所有可延后步骤可跳过且不阻断主流、同步、搜索和详情；设置根页保留固定名称“配置引导”的入口，从主流最多两次用户导航可达，恢复时已保存配置不丢失。
- FR62：保存赛道、关键词、排除词、来源或阈值前区分阻断性无效配置和过窄配置风险；无效配置禁止保存并指出字段、类别和修正方式，过窄风险解释影响及漏报后果并允许修改或明确确认，正常配置不得增加确认层。
- FR63：Windows 同一用户会话只允许一个可交互实例；已有实例运行（含隐藏至托盘）时再次启动须显示并聚焦现有窗口，不得创建第二实例。
- FR64：用户可保留手动建立的 GitHub Release 固定关注，并创建、修改、启用或停用 GitHub 项目发现订阅；订阅按赛道、主要语言、Topic、Star/Fork 当前门槛及有效增长条件发现公开仓库，区分新发现与新符合条件项目、展示命中依据并自动纳入 Release 监控。用户可按订阅忽略项目、停用自动关注或转为固定关注；系统须按规范仓库身份合并手动关注、多订阅及重命名/转移，保证单一项目和单一有效 Release 监控对象，保留合法历史，并隔离发现故障与既有 Release 同步。

### 非功能需求

- NFR1：各平台全新安装首启到演示情报可滚动并可打开详情，至少 100 次样本 P95 ≤5 秒。
- NFR2：50,000 条数据下，主流首屏、常用筛选、关键词搜索和结果首屏各至少 100 次样本 P95 <200ms。
- NFR3：同步、正文处理和 AI 分析并发时 UI 无响应事件为 0，用户操作 P95 ≤500ms，单次阻塞不超过 1 秒。
- NFR4：本地判定后 60 秒内进入主流；满足条件的通知 60 秒内提交；恢复后仍有效任务 60 秒内处理，过时即时通知补发为 0。
- NFR5：Windows 后台空闲 10 分钟平均 CPU <2%，且无持续 30 秒以上高于 5% 的占用。
- NFR6：Windows 在 50,000 条数据下工作集 P95 ≤250MB，10 分钟内不得持续增长超过 10%。
- NFR7：每类来源故障时其他来源全部正常完成，已保存结果不回退，错误只归属故障来源。
- NFR8：跨轮同步、重启和恢复后重复入库率与重复通知率均为 0。
- NFR9：崩溃、重启、断网、挂起、终止或回收后，已完成数据零损坏/丢失；未完成任务恢复、重执行或明确可重试且无重复结果。
- NFR10：离线、无 AI Key、AI 超时三种状态下缓存浏览、搜索、详情和收藏访问率均为 100%。
- NFR11：重大提醒的有效溯源完整率 100%；任何未达门槛样本触发提醒即失败。
- NFR12：各既有数据版本升级时配置、收藏、反馈和历史静默丢失或误改为 0；无法迁移则停止并提供恢复提示。
- NFR13：休眠、断网、挂起、回收和重启恢复后，每个逻辑任务最多产生一份入库、一份分析和一次通知，并发重复任务为 0。
- NFR14：数据库完整性异常时受影响写入成功为 0；所有场景提供恢复提示且未受影响数据可读。
- NFR15：密钥仅存在于平台安全凭据存储；数据库、UI 持久状态、日志、诊断和测试数据命中为 0。
- NFR16：除用户主动配置的本地服务外，外部未加密连接为 0；证书或加密失败时不得传输内容或凭据。
- NFR17：对本机、环回、内网、保留地址、禁用协议及重定向目标的实际访问为 0，合法来源不受影响。
- NFR18：单响应 ≤10MB、重定向 ≤5 次、单次处理 ≤30 秒；超限终止且应用保持可操作。
- NFR19：未收藏正文处理、失败、重试和重启后，数据库、日志、崩溃信息和持久临时文件中的完整或可还原正文残留为 0。
- NFR20：诊断导出中密钥、授权头、完整正文和敏感提示命中均为 0，移除项使用不泄露原值的标识。
- NFR21：未经确认或来源授权的 AI 内容外发为 0；关闭后不得发起新请求，排队任务不得继续发送。
- NFR22：删除收藏正文及索引并重启后，搜索命中、展示和可访问残留均为 0。
- NFR23：RSS/Atom、GitHub Release、arXiv 各类错误准确归属并可独立重试，其他来源成功率不受影响。
- NFR24：429 有有效指示时不得提前请求；无指示首次重试 ≥60 秒，间隔不缩短，第三次至少为首次 4 倍。
- NFR25：AI 超时、限流、无效结构和不完整结果不得标为成功，必须保留失败或待重试状态。
- NFR26：字段缺失、时间格式差异和内容更新样本不得造成可溯源有效内容丢弃；不可解析字段留空或明确标识，不得伪造。
- NFR27：服务恢复后所有仍有效任务无需重建即可继续，每个逻辑任务最多一份入库、分析和通知。
- NFR28：各设备全新安装时，无注册、云账户、AI Key 和通知授权也能 100% 完成演示浏览、详情和筛选。
- NFR29：演示、事实、规则、AI、离线和待分析六类状态的非颜色区分覆盖率 100%。
- NFR30：Windows 和带键盘平板仅用键盘可完成核心任务；每步焦点可见且无焦点陷阱。
- NFR31：Windows 100%–200% 缩放、浅深主题全部组合中，核心文字/操作可用，阻断裁切和重叠为 0。
- NFR32：所有可展示错误的对象、数据安全状态和恢复动作完整率 100%。
- NFR33：后续引导阻塞主流浏览为 0；所有可延后步骤可跳过；从主流到设置根页固定“配置引导”入口不超过两次用户导航，恢复后已保存配置丢失为 0。
- NFR34：Windows 10/11 x64 标准用户安装和运行成功，管理员权限请求为 0。
- NFR35：Windows 10/11 的托盘、通知、开机启动、关闭隐藏、单实例和显式退出通过率 100%；重复启动不得产生多个可交互实例，显式退出后不得继续后台运行。
- NFR36：关闭开机启动后，重启应用、系统和升级均保持关闭。
- NFR37：关闭窗口、关机或显式退出期间，已完成数据零损坏/丢失，任务安全完成/恢复/可重试，显式退出无残留进程。
- NFR38：Windows 必要运行环境缺失均在不可运行前检出，并准确说明缺失项和修复步骤。
- NFR39：Windows、iPhone、iPad、Android 手机和平板核心旅程适用步骤完成率 100%，跨设备绕行阻断为 0。
- NFR40：移动端各生命周期中完成数据零损坏/丢失，有效任务 100% 恢复/重试/标记，重复副作用为 0。
- NFR41：通知/后台权限各状态下非通知任务完成率 100%，未授权通知为 0，限制说明/最后同步/恢复入口完整率 100%，拒绝后自动重请为 0。
- NFR42：手机方向、iPad 分屏、Android 可变窗口/折叠态中核心内容和操作可达率 100%，阻断裁切/重叠/横向溢出为 0，上下文保留率 100%。
- NFR43：iPhone/iPad 使用 VoiceOver、最大动态字体、高对比度和减弱动画时核心任务完成率 100%，无名称控件、错误顺序、阻断裁切和仅颜色状态为 0。
- NFR44：Android 手机/平板使用 TalkBack、字体/显示缩放和减弱动画时核心任务完成率 100%，无名称控件、错误顺序、焦点陷阱、阻断裁切及小于 48×48dp 核心目标为 0。
- NFR45：通知前台、后台和冷启动有效目标到达率 100%，重复副作用为 0；无效目标错误信息和主流返回成功率 100%。
- NFR46：两设备之间自动变化和本地数据跨设备传输均为 0；“仅影响当前设备”说明覆盖率 100%。
- NFR47：各平台删除正文、缓存、配置、反馈或凭据后，明确删除数据残留为 0，被删凭据再次使用为 0，保留项事前说明完整率 100%。
- NFR48：移动端无任务后台 30 分钟主动网络和产品周期唤醒均为 0，不持续占用后台时间。
- NFR49：移动端 50,000 条数据和 20 次前后台循环中非预期终止为 0；满足 NFR2/3，内存不连续五轮增长且总增幅 ≤20%。
- NFR50：各平台所有既有版本升级/保留数据路径静默丢失或误改为 0；无法迁移则停止；数据后果说明覆盖率 100%。
- NFR51：有效签名且资格有效的移动构建安装率 100%，无效构建进入分发为 0；七类隐私披露完整率 100%，声明与行为不一致为 0。
- NFR52：三类来源分别使用覆盖新增、更新、跳过、解析失败和零结果的固定响应集，在无 AI Key 时执行单源与全部同步；数量与执行记录一致率、最小结果字段完整率、失败归属正确率均为 100%，零结果/部分成功误报和因其他来源失败而隐藏或回滚成功结果均为 0。
- NFR53：覆盖三种用户处理状态与收藏/未收藏的六种组合及三态互转、浏览、详情、收藏变化、正文删除、离线、重启、生命周期恢复和升级；显式转换成功率及组合保留率为 100%，所有隐式状态变化和与 AI 状态混用均为 0。
- NFR54：在五类受支持设备上使用固定 GitHub 仓库响应和带时间戳 Star/Fork 观测，验证手动/自动/多订阅、增长边界、分类、命中依据、忽略/停用/转固定、重命名/转移及故障注入；符合条件结果、分类、依据和控制行为正确率为 100%，不符合条件进入结果或监控、重复项目/监控/Release/通知、非法增长命中、历史意外丢失及发现故障阻断既有 Release 同步均为 0，并遵守 NFR24 退避。

### 架构附加要求

- ARCH-1：首个实现 Story 必须建立组合式官方脚手架：Cargo workspace、Tauri/React Windows、SwiftUI Apple、Compose Android、共享 `radar-core` 与 `radar-ffi`。
- ARCH-2：首个实现 Story 必须验证 UniFFI 0.32.0 绑定生成、DTO/AppError 往返、PlatformEffect outbox 幂等回报、临时密钥会话以及三端编译冒烟。
- ARCH-3：Rust 共享核心是数据库、确定性规则、迁移、任务和跨平台契约的唯一权威；三平台 UI 不重复实现领域规则。
- ARCH-4：每设备一个 SQLite；使用 bundled rusqlite 0.40.1、SQLite ≥3.53.4、单写执行器、WAL、外键、受控 checkpoint 和事务化迁移。
- ARCH-5：平台层不得直接访问数据库；UI 仅通过批准的 Command、Query、Task 和分页 DTO 使用核心。
- ARCH-6：数据库模型必须分离事实、正文、溯源、规则、AI、同步、任务、通知、收藏、反馈和非敏感设置；密钥不得入库。
- ARCH-7：身份优先使用 `(source_kind, external_id)`，否则规范化 URL hash；唯一约束是最终幂等防线，Phase 1 不进行语义自动合并。
- ARCH-8：检索采用 SQLite FTS5 trigram + B-tree + cursor 分页；列表不得加载完整正文，正文/索引事务一致。
- ARCH-9：演示数据使用独立 origin/namespace，禁止通知、AI 外发、指标和与真实记录去重。
- ARCH-10：迁移流程为验证、备份、事务迁移、完整性检查后开放写；失败进入可恢复只读诊断，禁止旧版本写新 schema。
- ARCH-11：Windows Credential Manager/当前用户 DPAPI、Apple Keychain、Android Keystore 分别持有密钥；共享核心只接收短生命周期 SecretLeaseInput。
- ARCH-12：WebView 使用最小 capability 和严格 CSP；禁止通用 SQL/URL/文件/命令接口，外链统一由系统浏览器打开。
- ARCH-13：共享 HTTP 层实施 scheme、DNS/IP、重定向、TLS、大小、超时和并发限制；来源与 AI provider 使用隔离网络策略。
- ARCH-14：应用 API 使用稳定版本化 DTO、Page、TaskRef、TaskSnapshot 和 AppError；ID 不透明，时间为 RFC3339 UTC，缺失值显式 optional/null。
- ARCH-15：长任务持久化并接受 ExecutionBudget；UI 只在活跃时自适应轮询，取消为协作式，已提交来源事务不回滚。
- ARCH-16：平台副作用通过持久 PlatformEffect outbox 执行并回报，通知、密钥、调度、深链均须可恢复且幂等，不注册长期 FFI callback。
- ARCH-17：Windows 使用 DesktopApi + TanStack Query，Zustand 只存纯 UI 状态；Apple 使用 RadarCoreClient actor + MainActor ViewModel；Android 使用 repository + ViewModel/StateFlow。
- ARCH-18：保存、删除、规则生效、来源配置、数据清理和 AI 发送设置不得乐观提交；核心负责最终字段验证。
- ARCH-19：三平台页面必须显式覆盖初载、带旧数据刷新、空、离线、部分失败、阻塞失败、迁移只读、权限、取消、成功和恢复状态。
- ARCH-20：锁定 Rust、Node 24 LTS、pnpm、Xcode 26.x、JDK 21、AGP/Kotlin/Compose 及依赖版本，并提交所有锁文件与 Gradle Wrapper。
- ARCH-21：CI 必须覆盖核心、绑定、三平台、安全、性能和发布；core/contracts/bindings/migrations 变更强制触发三端契约门禁。
- ARCH-22：Windows Phase 1 输出 x64 NSIS 当前用户包；授权受控手动测试可使用尚未取得 Windows 生产代码签名的候选构建，但须披露状态并提供 SHA-256，公共或生产分发前必须签名；Apple 使用 TestFlight，Android 使用 Google Play Internal Testing，移动受控测试签名要求保持不变；签名密钥仅在受保护发布环境。
- ARCH-23：正式构建禁止调试 capability、测试密钥、开发地址和宽松 CSP；CI 执行漏洞、许可证、secret 和契约生成差异检查。
- ARCH-24：结构化滚动日志使用 correlation ID 且默认脱敏；诊断采用 allowlist，禁止打包应用数据目录。
- ARCH-25：所有架构偏离必须先创建 ADR；整库加密、自动更新、公共商店、远程诊断、云同步和高级语义关联均延后。
- ARCH-26：同步执行必须以 `sync_runs`、`sync_source_results`、`sync_result_items` 保持整轮、来源级计数与成功条目的一致关系，并通过 `get_sync_result` 提供不依赖 AI、评分、FTS 或正文的最小只读结果。
- ARCH-27：`intel_items.user_processing_state` 采用 `unseen | judged | research_later` 三态、默认 `unseen`，仅由显式幂等命令修改，使用 revision 防并发覆盖，并与收藏、反馈及 AI 状态正交持久化。
- ARCH-28：配置校验返回稳定分类码、字段定位、风险影响与修正建议；风险确认回执绑定规范化配置 hash 和验证器版本，单次使用、短生命周期，保存时必须重新校验。
- ARCH-29：`setup_progress` 使用独立持久化表和 API，不与业务配置混存；设置根级固定路由 `/settings/setup`，核心进度是跨平台唯一事实源。
- ARCH-30：Windows 单实例插件锁定为 `tauri-plugin-single-instance 2.4.3` 并最先注册；重复启动参数按不可信输入验证后进入激活队列，禁止原始参数进入 WebView，恢复窗口时保留路由、查询、筛选、选择和草稿。
- ARCH-31：CI 增加 contracts、state-consistency、configuration-validation、sync-consumption、windows-lifecycle 门禁；发布元数据记录 API contract、验证器、fixture、签名状态和适用分发范围。
- ARCH-32：依赖基线锁定 Tauri core 2.11.5、CLI 2.11.4、UniFFI 0.32、SQLite 3.53.4、rusqlite 0.40.1、Navigation 3 1.1.4、Material 3 Adaptive 1.2.0、TanStack Query 5.101.4、Zustand 5.0.14、React Router 8.3.0，并按架构更新流程管理版本变化。
- ARCH-33：GitHub 项目发现与 GitHub Release 同步必须使用独立 Application Task、Adapter、运行状态和故障边界；发现失败、限流或部分分页不得阻断或覆盖既有 Release 同步结果。
- ARCH-34：共享核心以 GitHub 稳定仓库 ID 为首选规范身份，`owner/name` 仅作可变别名或降级键；身份解析与事务合并必须保证同一仓库只有一个本地项目及一个有效 Release 监控对象，并保留全部合法历史关联。
- ARCH-35：`GitHubDiscoveryConditionSet` 是发现条件唯一权威合同，不同维度按 AND、同维度多值按 OR；远端搜索仅缩小候选集，共享核心必须用规范化条件执行确定性复核，平台不得复制判定逻辑。
- ARCH-36：Star/Fork 增长只使用同一仓库至少两个成功且带时间戳的有效观测；首次观测、失败、限流、缺失值和零比例基数不得产生增长命中，时间与窗口边界由共享核心及固定 fixtures 判定。
- ARCH-37：发现订阅、运行、结果、忽略、撤销、自动关注启停及转固定均通过批准的 Command/Query API；写命令携带 revision 与幂等请求 ID，运行结果使用稳定枚举，事件只携带实体 ID 和 revision。
- ARCH-38：独立发现 Adapter 只访问 GitHub 官方公开仓库 API，按 Link header 分页并遵守 Retry-After、rate-limit reset、NFR24 与 ExecutionBudget；未完成分页必须标记部分完成或限流并保留已确认结果，不得伪装为成功零结果。
- ARCH-39：有效 Release 监控由共享核心按 `fixed > active_auto > inactive_auto` 计算；订阅级忽略只影响对应订阅，停用、条件失配、忽略或转固定不得级联删除项目、Release、收藏、反馈、观测或其他合法历史。
- ARCH-40：Phase 1 仅发现公开仓库，不新增 GitHub 登录、OAuth、GitHub App 或长期凭据；发现请求只允许官方 HTTPS 主机，诊断默认不记录完整搜索文本、项目描述或原始仓库响应。
- ARCH-41：三端实现独立的 `github-discovery` feature，覆盖订阅表单/列表、运行摘要、发现结果、命中依据和监控控制；分类、关注、发现运行和 Release 同步为正交展示状态，UI 只消费核心 DTO。
- ARCH-42：新增 `github-discovery-contracts`、`github-growth-observations`、`github-identity-deduplication`、`github-monitoring-controls` 和 `github-discovery-isolation` 门禁；核心、Adapter、三平台和 CI 共用 `contracts/fixtures/github-discovery/` 的单一固定样本。
- ARCH-43：GitHub 发现模块遵守 `domain → application → infrastructure → contracts` 依赖方向；只有专属数据库仓储访问新增表，Release 仅引用规范本地项目 ID，平台草稿不成为持久事实源。
- ARCH-44：自动关注容量上限、超限队列和淘汰策略尚未获产品批准；Story 不得自行加入容量上限、静默淘汰或“无限监控”承诺，未来决策须同步 PRD、UX、Architecture、fixtures 与 Epics。

### UX 设计要求

- UX-DR1：实现跨平台语义设计令牌，包括颜色、字体、4px 间距、布局、圆角、边界、焦点、运动和反馈；页面不得硬编码视觉值。
- UX-DR2：实现 IntelligenceFeedItem，覆盖来源/时间、标题、必要摘录、重要度、赛道、AI/离线状态、快捷操作及默认、焦点、选中、收藏、演示、等待和错误状态。
- UX-DR3：实现 EvidenceDetailPanel，按来源/标题、发生了什么、为何重要、影响、重要度、AI 置信度、依据、溯源和操作的渐进层级呈现，事实、规则和 AI 分区。
- UX-DR4：实现 SourceProvenanceGroup，展示发布方、作者、原始标题、链接、时间、可用状态及确定性关联依据；缺失字段明确写“未提供”。
- UX-DR5：实现 SyncHealthSummary，呈现总体状态、最后同步、各来源结果、AI 队列、数据安全和恢复动作；部分成功同时显示成功与失败范围。
- UX-DR6：实现 RuleImpactPreview，展示修改摘要、影响、风险、冲突、生效时间和历史数据说明；阻断错误不可保存，警告可明确确认。
- UX-DR7：实现 ProgressiveSetupGuide，配置赛道、来源、刷新周期和 AI 数据说明；每步独立保存、非阻塞并始终允许跳过/稍后继续。
- UX-DR8：实现 SourceDeliveryReadiness，逐项显示 RSS/Atom、GitHub Release、arXiv 的交付、配置、同步与阻塞状态；任一未达门禁不得显示 Phase 1 完成。
- UX-DR9：实现 DeviceScopeNotice，在首次使用、设置、诊断和数据管理中明确当前设备作用域、无云备份/跨设备同步以及适用的数据后果。
- UX-DR10：实现 DistributionDisclosureStatus，显示平台、版本、签名/安装资格、授权范围和七类隐私披露；缺失项阻塞受控分发且不得复用情报优先级视觉。
- UX-DR11：Windows ≥1280px 使用三栏，1024–1279px 压缩三栏，640–1023px 列表加独立详情，<640px 单栏；支持侧栏和列表宽度合同。
- UX-DR12：iPhone/紧凑 Android 使用底部导航和单栈详情；iPad 使用 NavigationSplitView；Android Medium+ 使用 Rail/Drawer 与 Adaptive 列表详情。
- UX-DR13：窗口、方向、分屏和折叠变化必须保留搜索、筛选、选择、未提交输入和滚动锚点，不得隐藏核心功能规避空间不足。
- UX-DR14：搜索作用域可见且防抖；筛选条件可移除并可恢复默认；后台新内容不得导致当前列表跳动。
- UX-DR15：通知深链在前台、后台和冷启动打开目标并提供安全回退；无后台机会时不承诺即时送达，过时内容仅入主流。
- UX-DR16：内容保留与删除确认必须逐项说明删除与保留内容；删除后的搜索、详情、诊断和请求不得暴露或使用残留正文、索引或凭据。
- UX-DR17：所有错误必须包含对象、阶段、时间（可得时）、影响范围、数据安全状态、系统下一步和用户动作；局部错误不得覆盖可用内容。
- UX-DR18：加载保留已有布局和内容，使用局部 Skeleton/Spinner；成功反馈克制，关键错误与数据后果不得仅用短暂 Toast。
- UX-DR19：每个组件覆盖默认、悬停（适用）、焦点、按下、选中、禁用、加载、错误、成功和破坏性状态，并具有非颜色提示。
- UX-DR20：Windows 全键盘可操作并具可见焦点；Apple 支持 VoiceOver、Dynamic Type 等；Android 支持 TalkBack、字体/显示缩放，核心触控目标 ≥48×48dp。
- UX-DR21：正文对比度 ≥4.5:1，大文本与非文本控件 ≥3:1；支持减弱动画，截断内容提供非悬停完整文本入口。
- UX-DR22：Windows 使用 shadcn/ui/Tailwind/Radix，Apple 使用 SwiftUI，Android 使用 Compose Material 3 Adaptive；共享语义和状态而非 DOM 或像素布局。
- UX-DR23：实现前必须为领域组件建立 Windows 场景、Xcode Preview 与 Compose Preview，覆盖主题、关键尺寸和完整状态；HTML 原型不得作为运行时验收证据。
- UX-DR24：平台手势、快捷键和图标按钮均须有可见等价入口、可访问名称和适用说明；不得以 Tooltip 承载关键事实。
- UX-DR25：实现 `SyncResultSummary`，同时呈现本轮完成、部分成功、零结果和失败状态、三类来源计数及最小结果条目；成功结果不得被局部错误覆盖，界面不得要求 AI、评分、搜索或详情先完成。
- UX-DR26：实现 `ProcessingStateControl`，只提供未查看、已判断、待研究三态及稳定可访问标签；与收藏、列表选择、价值反馈和 AI 状态分别呈现，浏览和打开详情不得触发状态转换。
- UX-DR27：设置根页必须提供名称固定为“配置引导”的 `ProgressiveSetupGuide` 入口并显示进度，从主流两次导航内可达；每步独立保存、可跳过、可恢复，恢复不得丢失已保存配置或重播已完成步骤。
- UX-DR28：所有适用配置保存使用两通道校验：四类阻断无效样本以字段错误阻止保存并聚焦首错，两类过窄风险以警告说明漏报影响并允许修改或确认；正常配置直接保存且无额外确认。
- UX-DR29：Windows 重复启动须恢复并聚焦现有窗口，保留当前页面、滚动、选择、筛选和未提交表单；默认不显示成功 Toast，无法恢复时提供可操作错误且仍不得产生第二实例。
- UX-DR30：跨平台验收矩阵必须覆盖三态×收藏/未收藏及 AI 等待/完成、三来源同步零结果/部分成功、四类阻断错误/两类过窄警告、配置引导恢复和 Windows 现有窗口获焦，并验证键盘及辅助技术等价路径。
- UX-DR31：在“来源”中将“固定关注的 GitHub 项目”与“GitHub 项目发现”作为可辨识的同级入口；订阅列表展示名称、启停、条件摘要、最近完成、结果数量和运行状态，发现结果不得伪装成 Release 或普通情报。
- UX-DR32：实现 `GitHubDiscoverySubscriptionForm`，依次覆盖名称/赛道、语言/Topic、Star/Fork 当前门槛、增长条件/观察窗口及可读组合摘要；复用 FR62 阻断错误与过窄风险通道，并解释首次基线和零基数边界。
- UX-DR33：实现 `GitHubDiscoveryResultItem` 与命中依据详情，明确区分新发现、新符合条件和增长基线，展示仓库身份、条件、实际值、观测时间、关注状态及独立 Release 状态；多订阅命中只显示一个项目主体。
- UX-DR34：实现 `GitHubMonitoringControl`，分别提供订阅级忽略/撤销、停用自动关注和转固定关注；动作前说明其他有效关注与历史保留，固定关注优先，任何控制不得暗示或造成历史删除。
- UX-DR35：GitHub 发现运行必须显式呈现执行中、成功有结果、成功零结果、部分完成、限流等待和失败可重试；错误附着于对应订阅并显示影响、数据安全与恢复动作，不能覆盖或阻断既有 Release 状态。
- UX-DR36：Windows、手机和平板分别使用列表—详情、单栈和多窗格原生布局，并在切换时保留订阅、筛选、选中项目、表单输入和滚动；分类、关注、发现及 Release 状态使用文字与平台语义，所有手势均有可见且可访问的等价入口。
- UX-DR37：GitHub 发现跨平台验收必须覆盖组合条件、新发现/新符合条件/增长基线、手动与多订阅重叠、重命名/转移、忽略/撤销/停用/转固定、成功零结果、部分分页、限流与发现失败但 Release 正常，并以 NFR24/NFR54 固定样本验证五类设备及辅助技术路径。

**Then** 结果展示仓库名称、所有者、主要语言、Topic、可获得的 Star/Fork 值、命中条件、实际观测值和观测时间
**And** 每个项目的依据字段完整率为 100%，状态和依据不只依靠颜色或图标。（FR64、NFR54、UX-DR33、UX-DR36）

**Given** 规范仓库身份首次进入当前设备的发现结果集
**When** 项目被分类
**Then** 显示“新发现项目”及“首次进入此设备的发现结果”的解释
**And** 不使用“GitHub 新建项目”等暗示仓库创建时间的文案。（FR64、UX-DR33）

**Given** 符合条件项目尚无固定或有效自动关注
**When** 发现事务成功提交
**Then** 共享核心将其自动纳入设备本地 Release 监控并返回合并后的关注状态
**And** 发现任务只更新监控投影，不直接抓取或保存 Release；Release Task 可独立运行。（FR64、ARCH-33、ARCH-39）

### Story 3.3：用有效观测识别增长与首次跨越门槛

作为追踪开源趋势的用户，
我希望平台只基于可靠的带时间戳观测判断 Star/Fork 增长和首次跨越门槛，
以便增长信号可复现且不会被失败数据或数学边界误导。

**验收标准：**

**Given** 某仓库只有首次成功且字段有效的 Star/Fork 观测
**When** 订阅包含增长条件
**Then** 系统保存带时间戳的基线并显示“增长基线已建立”
**And** 不将其分类为增长命中、新符合条件、增长失败或零增长。（FR64、NFR54、ARCH-36、UX-DR33）

**Given** 同一仓库在观察窗口内至少有两个成功有效观测
**When** 计算绝对增长或比例增长
**Then** 共享核心使用窗口内首个与末个有效值及 RFC3339 UTC 时间计算
**And** 命中依据展示首值、末值、时间范围、实际增长和订阅阈值。（FR64、NFR54、ARCH-36）

**Given** 请求失败、限流、字段缺失、时间无效或页面未获取
**When** 处理本轮观测
**Then** 系统不得写入零值或合成观测，也不得使用失败样本参与增长计算
**And** 不足两个有效值返回 `insufficient_baseline`。（NFR54、ARCH-36）

**Given** 比例增长窗口的首个有效值为零
**When** 评估比例条件
**Then** 系统返回 `zero_ratio_baseline` 且不得除零、改用 1 或静默降级为绝对增长
**And** 该项目不得因比例增长进入结果或自动监控。（NFR54、ARCH-36）

**Given** 当前设备已存在该仓库的有效观测但此前未满足订阅
**When** 本轮首次跨过当前门槛
**Then** 结果分类为“新符合条件项目”并解释“此前已有观测，本次首次达到当前订阅条件”
**And** 后续持续命中只更新依据和最近命中时间，不再次计为新符合条件。（FR64、NFR54、UX-DR33）

### Story 3.4：合并手动关注、多订阅及仓库身份变化

作为同时手动关注并使用多个发现订阅的用户，
我希望同一 GitHub 仓库始终保持单一项目与 Release 监控身份，
以便重叠规则、重命名或转移不会产生重复内容和提醒。

**验收标准：**

**Given** GitHub 响应提供稳定仓库数字 ID
**When** 系统解析或更新项目身份
**Then** 数字 ID 是规范身份，`owner/name` 作为可变别名，`node_id` 不建立第二套主键
**And** 所有取得与更新都通过共享核心的单一身份解析用例。（FR64、ARCH-34）

**Given** 同一仓库先被手动固定关注后又命中一个或多个发现订阅
**When** 发现事务提交
**Then** 只保留一个项目对象和一个有效 Release 监控对象，关注状态保持固定关注
**And** 每个订阅的命中依据分别保留，不生成第二开关、重复 Release 或重复通知。（FR64、NFR54、ARCH-34、UX-DR33）

**Given** 多个发现订阅命中同一规范仓库身份
**When** 用户查看项目详情
**Then** 只显示一个项目主体和合并后的有效监控状态
**And** “命中依据”按订阅分别展开，依据数量具有可访问名称。（FR64、NFR54、UX-DR33、UX-DR36）

**Given** 仓库发生大小写变化、重命名或组织转移
**When** 系统取得相同稳定仓库 ID 与新 `owner/name`
**Then** 在单一事务中更新别名并重定向订阅命中、观测、监控和 Release 外键
**And** 历史身份仍可追溯，不创建第二项目、第二有效监控、重复 Release 或重复通知。（FR64、NFR54、ARCH-34）

**Given** 初期只能使用规范化 `owner/name` 降级身份，后续取得稳定仓库 ID
**When** 核心发现两个记录属于同一仓库
**Then** 系统事务性合并记录并由唯一约束阻止并发重复
**And** 合并失败不得留下两个同时有效的 Release 监控对象。（FR64、NFR54、ARCH-34、ARCH-43）

### Story 3.5：控制自动关注并保留其他有效关注

作为审查自动发现结果的用户，
我希望忽略某订阅中的项目、停用自动关注或把项目转为固定关注，
以便控制后续 Release 监控而不误伤其他有效关注。

**验收标准：**

**Given** 某项目由当前订阅自动关注
**When** 用户选择“忽略此订阅中的项目”并确认
**Then** 当前订阅不再把它作为新发现并停止由该订阅建立自动关注
**And** 固定关注及其他有效订阅不受影响，用户可从同一上下文撤销忽略。（FR64、NFR54、ARCH-39、UX-DR34）

**Given** 项目仅由自动发现维持关注
**When** 用户停用自动关注
**Then** 系统保留项目、命中依据和历史，但暂停后续 Release 同步
**And** 若另有固定或其他有效自动关注，返回状态明确说明 `effective_monitoring = true` 及原因集合。（FR64、NFR54、ARCH-39）

**Given** 用户选择“转为固定关注”
**When** 核心命令成功提交
**Then** 系统在事务中设置固定关注并保持同一项目和 Release 监控身份
**And** 后续订阅停用、条件失配或订阅级忽略不得停止其 Release 同步。（FR64、NFR54、ARCH-39、UX-DR34）

**Given** 用户执行忽略、撤销、停用自动关注或转固定
**When** 命令正在提交
**Then** 平台显示局部进行状态且禁止重复提交，不乐观改写领域状态
**And** 成功后只使用核心返回的 `GitHubMonitoringStateView` 更新界面，revision 冲突时保留上下文并允许刷新重试。（ARCH-37、ARCH-39、UX-DR34）

**Given** 用户通过鼠标、键盘、触控或屏幕阅读器审查项目
**When** 使用关注控制
**Then** 三类操作均有可见、具可访问名称的入口，手势不是唯一入口
**And** 操作前说明其他有效关注和历史是否继续保留，停用或忽略不使用“已删除”的破坏性语义。（UX-DR34、UX-DR36）

### Story 3.6：在订阅和条件变化后保留合法历史

作为依赖历史 Release 与判断记录的用户，
我希望发现条件或关注状态变化时已保存数据仍然安全可用，
以便调整发现策略不会破坏过去的研究与决策证据。

**验收标准：**

**Given** 订阅被停用、条件修改后失配或项目在当前订阅中被忽略
**When** 监控投影重新计算
**Then** 系统不得删除项目、Release、收藏、反馈、命中依据、观测或其他合法历史
**And** 只在没有固定或其他有效自动关注时暂停未来 Release 同步。（FR64、NFR54、ARCH-39）

**Given** 已保存的项目后续不再满足当前条件
**When** 用户查看历史发现结果或项目详情
**Then** 历史分类、命中条件、实际值和观测时间仍可核验
**And** 界面说明当前条件状态，不把历史项目重新标记为新发现或静默移出历史。（FR64、UX-DR33、UX-DR35）

**Given** 用户编辑并保存新订阅条件
**When** 下一次发现执行
**Then** 新条件只影响后续判定和监控投影，不改写旧条件版本下的证据
**And** 历史命中记录保留其条件版本与依据版本。（FR64、ARCH-34、ARCH-39）

**Given** 项目已转为固定关注
**When** 原发现订阅被停用或项目在原订阅中被忽略
**Then** Release 同步继续使用同一监控对象
**And** 既有 Release、收藏、反馈和通知去重身份保持不变。（FR64、NFR54、UX-DR34）

**Given** NFR54 固定样本执行全部控制与身份变化组合
**When** 比较操作前后数据
**Then** 非用户主动删除造成的合法历史丢失数量为 0
**And** 迁移、唯一约束和控制命令测试共同证明不存在级联误删。（NFR54、ARCH-42、ARCH-43）

### Story 3.7：在限流和部分失败中继续发现与同步 Release

作为依赖持续 Release 情报的用户，
我希望 GitHub 发现受限或失败时仍能理解本轮结果并继续使用既有 Release 监控，
以便外部发现服务波动不会中断已建立的情报来源。

**验收标准：**

**Given** 发现运行完整执行且有符合条件项目、完整执行但无符合条件项目、部分分页失败、限流、失败或取消
**When** 运行进入终态
**Then** 结果分别映射为 `succeeded_with_results`、`succeeded_zero_results`、`partially_succeeded`、`rate_limited`、`failed` 或 `cancelled`
**And** UI 不得根据空数组自行推断成功零结果。（FR64、NFR54、ARCH-37、UX-DR35）

**Given** 已成功提交部分页面且仍存在下一页
**When** ExecutionBudget 用尽、后续页超时或响应无效
**Then** 系统保留已确认结果并标记部分完成，说明未完成范围和恢复动作
**And** 不回滚成功结果、不显示“没有符合条件的项目”、不重复自动关注。（NFR54、ARCH-38、UX-DR35）

**Given** GitHub 返回 Retry-After、rate-limit reset 或连续限流
**When** 调度发现重试
**Then** 有明确指示时指定时间前请求数为 0；无指示时首次重试不少于 60 秒且连续间隔不缩短，第三次至少为首次 4 倍
**And** 退避期间重复执行入口禁用并显示最早可重试时间。（NFR24、NFR54、ARCH-38）

**Given** 发现请求超时、限流、无效响应或部分分页失败，同时已有项目可同步 Release
**When** 发现任务失败或受限
**Then** 错误只归属于对应订阅和发现运行，既有 Release Task 继续执行并公开自己的结果
**And** Release 成功结果被阻断、隐藏或回滚的数量均为 0。（FR64、NFR54、ARCH-33、UX-DR35）

**Given** 发现服务恢复
**When** 用户重试或系统获得合法执行机会
**Then** 任务从持久状态安全继续或重新执行，已确认项目不重复创建
**And** 重复项目、有效监控对象、Release 记录和通知数量均为 0。（NFR27、NFR54、ARCH-42）

**Given** 在 Windows、iPhone、iPad、Android 手机和 Android 平板运行 NFR54 固定 fixtures
**When** 验证条件匹配、分类、依据、身份、控制、历史保留和故障隔离
**Then** 符合条件结果与固定预期集一致率、分类正确率、依据完整率和控制行为一致率均为 100%
**And** 不符合条件进入结果或自动监控、非法增长命中、重复副作用、历史意外丢失和发现阻断 Release 同步的数量均为 0。（NFR54、UX-DR37、ARCH-42）

**Given** Epic 3 的实现和验收
**When** 评审范围与正式测试证据
**Then** 不包含删除发现订阅、私有仓库、GitHub 登录、实时网络结果依赖或平台自有业务判定
**And** 不添加容量上限、静默淘汰或“无限监控”承诺。（FR64、ARCH-40、ARCH-44）

## Epic 4：获得可解释、可溯源的每日情报与离线资料库

用户可把多来源内容转化为统一、可溯源、确定性去重的情报，在主情报流、搜索、筛选、详情和被过滤视图中完成日常判断；用户可核验原文、关联来源、评分依据，并按内容生命周期安全地收藏和离线阅读正文。

### Story 4.1：将真实来源规范化为可溯源情报

作为情报阅读者，
我希望三类来源都转换为字段一致且保留原始证据的情报记录，
以便无论来源格式如何都能理解和核验内容。

**验收标准：**

**Given** RSS/Atom、GitHub Release 和 arXiv 返回合法但字段形态不同的内容
**When** 共享核心执行规范化
**Then** 每条内容转换为稳定情报身份、标题、来源类型、发布方、有效原文链接、发布时间、采集时间和内容标识
**And** 来源可提供作者时保存作者，否则明确记录为不可获得，不伪造字段。（FR13、FR14、NFR26）

**Given** 同一来源内容首次出现或内容版本发生变化
**When** 来源事务提交
**Then** 系统保存首次发现时间、最后更新时间和原文可用状态
**And** 原始事实、内容状态及来源溯源分别存储，后续规则或 AI 结果不得覆盖它们。（FR15、FR16、ARCH-6）

**Given** 外部字段包含无效 URL、超长值、未知枚举或不可解析时间
**When** 版本化 Rust DTO 进入领域构造函数
**Then** 系统按字段规则拒绝或显式标记无效值，并生成稳定可诊断错误
**And** 未经验证的第三方 payload 不进入持久化事实源。（ARCH-6、ARCH-14）

**Given** 一个来源批次包含多个有效条目和一个无效条目
**When** 执行规范化与持久化
**Then** 行为遵循明确的批次错误策略，已确认可保存的记录、游标和同步计数保持事务一致
**And** 错误可定位到来源和记录，不以 AI 或猜测值补全原始事实。（NFR7、NFR26）

**Given** GitHub Release 来自用户手动固定关注或 Epic 3 自动发现建立的有效监控
**When** Release 来源任务取得新版本
**Then** 两种关注来源使用相同的 Release 身份、规范化、溯源和内容生命周期管道
**And** GitHub 项目发现结果本身只存在于发现区域，不被伪装成 Release、论文或普通情报；发现失败不影响已取得 Release 的规范化。（FR8、FR13、FR64、ARCH-33、UX-DR31）

### Story 4.2：确定性识别重复并关联同一事件来源

作为技术决策者，
我希望系统可靠识别重复内容并保留同一事件的各条来源证据，
以便减少噪声而不丢失不同发布方的可核验记录。

**验收标准：**

**Given** 同一来源内容具有稳定外部 ID
**When** 内容跨轮次、应用重启或网络恢复后再次同步
**Then** 系统以 `(source_kind, external_id)` 保持同一情报身份并执行幂等更新
**And** 同一内容版本的重复入库数为 0。（FR23、NFR8、ARCH-7）

**Given** 来源没有可靠外部 ID 但提供有效原文 URL
**When** 系统计算身份
**Then** 使用规范化 URL hash 作为确定性身份依据
**And** 内容 hash 仅用于变化检测和分析缓存，不替代记录身份。（FR23、ARCH-7）

**Given** 两条来源记录共享规范化链接、内容标识、版本或其他可验证标识
**When** 系统判断它们指向同一事件
**Then** 建立可解释的关联关系，并保存关联类型和依据
**And** 每条记录各自的标题、链接、发布时间、发布方和其他溯源字段继续独立存在。（FR24）

**Given** 两条内容只在主题或语义上相似而无确定性共享标识
**When** 去重与关联流程运行
**Then** 系统不得自动合并或建立确定性同事件关系
**And** 可保留为独立候选供用户核验，高级语义聚类继续作为明确延后能力。（FR23、ARCH-25）

**Given** 并发任务尝试写入同一稳定身份或关联
**When** 数据库事务提交
**Then** `UNIQUE`、外键和事务约束作为最终幂等防线
**And** 不产生重复记录、悬空关联或重复副作用。（NFR8、NFR13、ARCH-4）

### Story 4.3：用透明规则判断价值并形成主流分流

作为 AI 开发者，
我希望理解每条情报为何被评为某个重要程度或被过滤，
以便信任并校准雷达，而不是面对黑盒排序。

**验收标准：**

**Given** 统一情报和当前设备规则配置已经存在
**When** 核心执行情报价值判断
**Then** 依据赛道匹配、来源可信度、新鲜度、技术影响和用户配置生成版本化规则结果
**And** 保存每项命中、分数或等级及可解释理由，不依赖 AI 才能工作。（FR19）

**Given** 情报完成规则评估
**When** 系统生成重要程度
**Then** 结果展示赛道、来源、新鲜度、技术影响和规则命中依据
**And** AI 判断依据在尚未分析时显示“未配置/等待分析/已禁用”等状态，不伪造结论。（FR16、FR20）

**Given** 当前设备设置主情报流阈值
**When** 系统应用阈值
**Then** 情报被明确分为高价值情报或普通候选，并保留过滤原因
**And** 修改阈值只重新计算投影或规则结果，不删除或改写原始情报。（FR21、FR22）

**Given** 用户打开被过滤内容
**When** 查看某条普通候选
**Then** 系统展示未进入主流的具体因素、适用规则版本和可执行的规则入口
**And** 事实、规则判断和 AI 状态以语义区块及非颜色提示区分。（FR16、FR22、UX-DR17、NFR29）

**Given** 同一固定输入、规则版本和时钟
**When** Windows、Apple 和 Android 通过共享核心获取规则结果
**Then** 三端得到相同的重要程度、分流和解释数据
**And** 平台 UI 不重新实现或修改领域评分逻辑。（ARCH-3）

### Story 4.4：显式管理每条情报的处理状态

作为每天处理情报的用户，
我希望明确把每条情报设为未查看、已判断或待研究，
以便可靠记录处理进度，而不让浏览、收藏或 AI 状态替我做决定。

**验收标准：**

**Given** 新情报首次成功入库
**When** 创建当前设备的处理状态

## Epic 5：在明确同意下获得可选 AI 中文分析

用户可在当前设备安全配置兼容 OpenAI 接口的 AI 服务，先了解数据接收方和发送范围，再按来源授权中文翻译、摘要、主题、重要度、置信度和理由；无 Key、撤销授权或 AI 失败时，可信的本地情报闭环仍完整可用。

### Story 5.1：在平台安全存储中管理 AI 凭据

作为希望使用自选 AI 服务的用户，
我希望在当前设备安全配置、更新和移除服务凭据，
以便启用 AI 能力而不把密钥暴露给内容数据库或其他设备。

**验收标准：**

**Given** 用户在 Windows、Apple 或 Android 设置中输入 AI 服务凭据
**When** 保存配置
**Then** Windows 使用当前用户 Credential Manager/DPAPI、Apple 使用仅当前设备 Keychain、Android 使用 Keystore 保护的应用私有加密 blob
**And** 共享核心和普通设置只收到稳定 secret ID、掩码及“已配置”状态，不持久化明文。（FR25、NFR15、ARCH-11）

**Given** 用户更新已配置的凭据
**When** 新凭据通过最小连接或格式校验
**Then** 平台原子替换当前设备上的旧 secret，并返回新的配置状态
**And** 保存失败保留可修改输入，不把新旧明文写入 SQLite、日志、崩溃报告、诊断或测试数据。（FR25、NFR15、NFR20）

**Given** 用户选择移除 AI 凭据
**When** 确认界面说明此设备上的影响并完成删除
**Then** 平台安全存储、相关临时缓存和允许清理的诊断引用中不再存在该 secret
**And** 重启后被删除凭据再次用于请求的次数为 0，历史情报和带原 provider 标识的既有分析不被伪装或静默删除。（FR25、NFR47）

**Given** 两台设备分别运行应用
**When** 用户只在其中一台配置、更新或移除凭据
**Then** 另一设备的凭据与配置不发生变化，跨设备传输次数为 0
**And** 设置页明确显示“仅影响当前设备”，不暗示账号同步或云端恢复。（FR25、FR57、NFR46、UX-DR9）

### Story 5.2：在首次外发前确认数据范围并按来源授权

作为重视数据控制的用户，
我希望在内容首次发送给第三方 AI 前了解接收方和字段，并能按来源授权或撤销，
以便明确决定哪些本地内容可以离开设备。

**验收标准：**

**Given** 当前设备尚未对所选 AI provider 完成数据发送确认
**When** 首个符合分析条件的任务准备外发
**Then** 系统阻止请求并展示 provider、目标地址、将发送的标题/必要片段/元数据及明确不发送的密钥、反馈历史、无关记录和诊断信息
**And** 用户可确认、取消或稍后处理，取消不阻断采集、规则筛选、浏览和溯源。（FR26、NFR21）

**Given** 用户已完成总体验证但某个来源未获 AI 内容授权
**When** 该来源产生待分析情报
**Then** 内容外发次数为 0，情报保留原始事实和“该来源未授权”状态
**And** 其他已授权来源仍可独立分析。（FR28、NFR21）

**Given** 用户允许某来源只发送标题和摘要，或允许必要正文片段
**When** 系统构造 AI 请求
**Then** 请求字段严格受当前来源授权范围和数据最小化策略约束
**And** 审计元数据只记录 provider、模型、输入 hash、策略版本和字段类别，不记录完整 prompt、正文或 secret。（FR26、FR28、NFR20）

**Given** 用户撤销来源授权或关闭 AI 总开关，同时存在排队任务
**When** 配置变更提交
**Then** 不再发起新的内容请求，尚未外发的排队任务不得继续发送
**And** 已完成原始情报保持可用，界面明确说明撤销只影响当前设备和后续外发。（FR28、NFR21）

**Given** 用户重新查看 AI 数据说明
**When** 从设置、来源详情或分析状态进入
**Then** 可再次查看接收方、发送字段、来源授权和撤销入口
**And** 文案与实际网络、权限和保留行为一致，属于受控分发七类隐私披露的一部分。（UX-DR10、NFR51）

### Story 5.3：生成并验证结构化中文情报分析

作为需要快速判断技术变化的用户，

**Given** provider 返回符合 schema 的完整结果
**When** 本地验证通过
**Then** 系统保存中文翻译、摘要、主题、重要度、置信度、理由、provider、模型、输入 hash 和策略版本
**And** AI 结果存储在独立分析记录中，不覆盖标题、发布方、时间、原文或规则判断。（FR16、FR27、ARCH-6）

**Given** 相同规范化输入、provider、模型和分析策略版本已有有效结果
**When** 后续任务请求同一分析
**Then** 系统可复用持久化分析结果而不重复外发
**And** 输入、provider、模型或策略版本变化时创建可追踪的新结果，不把旧结果冒充为新结果。（FR27、ARCH-6）

**Given** 未收藏正文被临时用于生成分析
**When** 分析成功、失败、超时或应用重启
**Then** 完整正文只存在于最短必要内存生命周期，持久化仅保留必要摘录与分析结果
**And** 数据库、日志、崩溃信息和持久临时文件中的完整或可还原正文残留为 0。（FR17、NFR19）

**Given** 分析任务与来源同步和用户浏览并发
**When** 用户滚动、搜索、查看详情或保存设置
**Then** UI 无响应事件为 0、用户操作 P95 ≤500ms，单次操作不被后台任务持续阻塞超过 1 秒
**And** AI 任务遵守 ExecutionBudget 与限并发，页面只观察持久任务状态。（NFR3、ARCH-15）

### Story 5.4：明确展示 AI 状态并在失败时可信降级

**And** AI 生成字段或连续区块明确标注“AI 生成”，与原始事实和规则判断使用语义标题分隔。（FR29、UX-DR3、NFR29）

**Given** AI 已完成有效分析
**When** 用户查看详情
**Then** 展示中文提炼、主题、重要度、置信度及理由，并保留 provider/模型的适当来源说明
**And** 用户始终可以展开原始事实、规则依据和溯源并打开原文核验。（FR27、FR29、FR34）

**Given** provider 返回超时、限流、无效结构或不完整结果
**When** 分析任务结束
**Then** 这些结果被标记为有效 AI 分析的次数为 0，并保留明确失败或待重试状态
**And** 原始标题、来源、必要摘录、规则判断、浏览、搜索和收藏继续可用，不生成推测性兜底结论。（FR30、NFR10、NFR25）

**Given** 用户未配置有效凭据、撤销授权或设备离线
**When** 打开主情报流或详情
**Then** 系统显示准确的降级状态和适用下一步，不弹出阻塞配置墙
**And** 缓存浏览、搜索、详情和收藏访问率为 100%。（FR30、NFR10、UX-DR17）

**Given** AI 错误可由用户稍后处理
**When** 展示失败信息
**Then** 错误包含对象、阶段、影响范围、数据安全状态、重试条件和 correlation ID
**And** 退避期间不允许提前请求；关键错误保持可见，不仅依赖短暂 Toast。（UX-DR17、UX-DR18、NFR24、NFR32）

**Given** Story 5.1–5.4 全部完成
**When** 分别测试有效 Key、无 Key、未授权、撤销、离线、超时、限流和无效输出
**Then** FR25–FR30 的配置、同意、来源授权、分析、标识和降级路径全部可完成
**And** Epic 5 只增强 Epic 4 的判断效率，任何 AI 状态都不破坏本地优先、事实可溯源或无 AI 可用原则。

## Epic 6：在真正重要时收到可控的设备本地提醒

用户可在当前设备本地完成重大动态判断后收到稀少、可解释且不重复的系统通知，并从前台、后台或冷启动直达证据详情；用户能控制通知授权、免打扰和频率，Windows 用户还能通过托盘维持与管理后台运行。

### Story 6.1：仅为符合门槛的重大动态生成本地通知效果

作为关注重大技术变化的用户，
我希望只有当前设备已完成可信判断的重大动态才进入通知流程，
以便提醒稀少、可解释且不会由不可核验内容触发。

**验收标准：**

**Given** 当前设备已完成一条情报的本地采集、规范化和规则判定
**When** 情报同时达到高价值条件、用户提醒阈值并具有有效原文链接、明确发布方和可解析发布时间
**Then** 核心生成版本化 `NotificationEffect`，包含稳定情报 ID、内容版本、幂等键、过期时间和安全深链目标
**And** 通知判定不要求远程推送，也不要求 AI 已成功分析。（FR37、NFR11、ARCH-16）

**Given** 情报缺少任一溯源门槛、未达到用户阈值或只是普通候选
**When** 通知判定运行
**Then** 系统不生成“重大动态”通知效果
**And** 情报仍按适用规则保留在主情报流、普通候选或被过滤视图供用户核验。（FR37、NFR11）

**Given** 同一设备对同一情报内容版本跨轮次同步、重启或任务恢复
**When** 通知判定重复运行
**Then** `notification_log` 与 outbox 幂等键确保最多生成并提交一次有效通知
**And** MVP 不尝试跨设备通知去重，也不传播通知状态。（FR39、NFR8、NFR13）

**Given** 同一 GitHub 仓库同时被手动固定关注、多个发现订阅命中，或后续发生重命名或转移
**When** 相同 Release 内容版本进入通知判定
**Then** 通知幂等键引用规范本地项目与稳定 Release 身份，不引用可变 `owner/name` 或发现订阅 ID
**And** 由关注重叠或身份变化产生的重复通知数量为 0。（FR39、FR64、NFR54、ARCH-34）

**Given** 情报在后台不可执行期间产生并已失去即时提醒价值
**When** 应用下次获得执行机会
**Then** 内容可以进入主情报流，但补发带即时含义通知的次数为 0
**And** 仍在有效时限内的任务在恢复执行后 60 秒内完成主流更新及适用通知效果生成。（FR37、NFR4）

### Story 6.2：渐进请求通知权限并遵守提醒治理

作为希望掌控打扰程度的用户，
我希望只在确有重大提醒价值时被请求通知权限，并让系统遵守免打扰和频率限制，
以便拒绝通知也不影响产品核心价值。

**验收标准：**

**Given** 通知权限尚未请求且没有符合门槛的重大动态
**When** 用户首启、浏览、搜索、配置来源或执行同步
**Then** 系统不请求通知权限
**And** 所有非通知核心任务保持可用。（FR53、NFR41）

**Given** 首次出现符合门槛且准备发送的重大动态
**When** 系统需要提交通知但权限未决定
**Then** 先用上下文说明提醒价值、可能内容和拒绝后果，再由用户主动触发系统权限请求
**And** 拒绝或取消后本条不提交，采集、浏览、搜索、溯源、反馈和前台同步不受阻断。（FR53、UX-DR17）

**Given** 通知权限为允许、拒绝或已撤销
**When** 用户查看设置或同步状态
**Then** 界面显示准确权限状态、提醒是否可送达以及适用的系统设置入口
**And** 拒绝后每次启动自动再次请求权限的次数为 0。（FR40、FR53、NFR41）

**Given** 当前时间处于免打扰时段、已达到频率上限或通知授权不足
**When** 有重大动态满足内容门槛
**Then** 系统遵守当前设备规则，不提交不允许的系统通知，并记录确定性原因
**And** 内容仍进入主情报流，界面显示提醒不可送达或延后条件。（FR40）

**Given** 当前设备已允许通知且所有治理条件满足
**When** 平台消费 `NotificationEffect`
**Then** 在本地判定完成后 60 秒内向操作系统提交，并回报 delivered、denied、expired 或 failed
**And** 回报通过幂等 Application Command 持久化，重复消费不产生第二次通知。（NFR4、ARCH-16）

### Story 6.3：从通知安全直达证据详情并处理无效目标

作为收到重大提醒的用户，
我希望点击通知后直接到达对应证据详情，
以便立即核验来源和影响，而不是重新查找内容。

**验收标准：**

**Given** 应用正在前台且用户点击有效通知
**When** 平台解析 `radar://intel/<id>`
**Then** 应用打开对应情报详情，并保留返回原先视图或主情报流的路径
**And** 不重复创建详情实例、情报、分析或通知。（FR38、FR54、NFR45）

**Given** 应用在后台或尚未运行
**When** 用户点击有效通知
**Then** 应用恢复或冷启动后解析稳定目标并打开正确详情
**And** 启动、迁移和任务恢复不会导致目标丢失或重复副作用。（FR38、FR54、NFR45）

**Given** 通知目标已删除、不可用或深链版本不受支持
**When** 应用尝试导航
**Then** 显示包含目标、原因和数据安全状态的可操作错误，并提供返回主情报流入口
**And** 不展示其他记录、猜测相邻目标或进入无法返回的空页面。（FR54、NFR45、UX-DR17）

**Given** 深链 payload 或外部输入包含密钥、正文、prompt、敏感查询参数或无效 ID
**When** 平台解析目标
**Then** 输入被拒绝或安全降级，敏感值不进入日志、导航状态或错误界面
**And** ID 始终作为不透明字符串处理，平台不推断其格式。（ARCH-12、ARCH-14）

**Given** 前台、后台、冷启动和无效目标 fixture
**When** 在五类目标设备执行通知入口测试
**Then** 有效目标详情到达率 100%，重复详情/通知为 0，无效目标错误信息完整率和返回主流成功率均为 100%
**And** 测试同时验证无后台机会时不承诺即时送达、过时内容只入主流，并使用原生运行时而非 HTML 原型作为证据。（NFR39、NFR45、UX-DR15、UX-DR23）

### Story 6.4：通过 Windows 托盘安全管理后台运行

作为 Windows 用户，
我希望关闭主窗口后可继续在托盘运行，并能明确显示、同步或退出应用，
以便获得桌面常驻价值且始终掌控进程生命周期。

**验收标准：**

**Given** Windows 用户关闭主窗口且设置允许关闭后隐藏
**When** 关闭操作发生
**Then** 主窗口隐藏，应用保持单实例并可继续执行已允许的同步任务
**And** 已完成数据不丢失，进行中任务安全完成、持久化为可恢复或明确可重试。（FR41、NFR35、NFR37）

**Given** 应用正在托盘运行
**When** 用户选择“显示主窗口”“立即同步”或“退出”
**Then** 分别恢复并聚焦现有窗口、启动一次幂等同步任务或安全收敛并终止进程
**And** 重复启动不产生多个可交互实例，显式退出后残留应用进程为 0。（FR42、NFR35、NFR37）

**Given** 同一 Windows 用户会话中的现有窗口分别处于可见、最小化或托盘隐藏状态
**When** 用户再次启动应用
**Then** 系统显示、恢复并聚焦同一个现有窗口，进程与窗口层面始终只有一个可交互实例
**And** 当前路由、滚动位置、选择、筛选和未提交表单输入保持不变。（FR63、NFR35、ARCH-30、UX-DR29）

**Given** Windows 因前台激活策略拒绝应用直接抢占焦点
**When** 重复启动请求到达现有实例
**Then** 应用使用标准任务栏注意反馈并保持现有窗口可恢复
**And** 不创建第二实例、不重置会话，也不把未经验证的启动参数传入 WebView。（FR63、ARCH-30、UX-DR29）

**Given** 用户启用或关闭开机启动
**When** 重启应用、重启 Windows 或升级候选构建
**Then** 系统尊重并保持用户明确选择
**And** 用户关闭后应用自动恢复开机启动的次数为 0。（FR42、NFR36）

**Given** Windows 候选构建处于后台空闲且没有任务
**When** 按统一基线连续采样 10 分钟
**Then** 平均 CPU <2%，且不存在持续 30 秒以上高于 5% 的占用
**And** 托盘状态不通过固定高频轮询维持。（NFR5）

**Given** Windows 10/11 x64 标准用户安装环境
**When** 验证托盘、桌面通知、开机启动、关闭隐藏、单实例和显式退出
**Then** 六项规定行为在两个系统版本上的通过率均为 100%，无需管理员权限
**And** 缺少必要运行环境时在应用不可运行前准确说明缺失项和修复步骤。（NFR34、NFR35、NFR38）

**Given** Story 6.1–6.4 全部完成
**When** 分别验证通知门槛、权限状态、免打扰、频率上限、重复任务、前后台深链和 Windows 托盘生命周期
**Then** FR37–FR42、FR53–FR54、FR63 的用户路径均可完成
**And** Epic 6 不使用远程推送，不削弱无通知可用原则，并能在没有 AI 分析结果时基于可信规则与溯源独立工作。

## Epic 7：用反馈验证并持续校准雷达质量

用户可评价情报和分析、记录漏报、查看提醒有效率与主流有效率，并按赛道、来源和规则理解误报/漏报原因，在四周个人验证期内手动校准雷达而不被系统静默改变规则。

### Story 7.1：记录可解释的情报价值与分析反馈

作为日常使用者，
我希望对情报价值、紧急程度、重复关系和 AI 分析准确性分别反馈，
以便积累可用于判断雷达质量的本地证据。

**验收标准：**

**Given** 用户正在查看真实情报列表或详情
**When** 选择“值得立即知道”“有价值但不紧急”“无价值”“重复”或“分析错误”
**Then** 系统将反馈与稳定情报 ID、当前内容版本、时间和当前设备关联保存
**And** 各反馈类别语义独立，不把“当前不感兴趣”自动等同于内容低质量。（FR43）

**Given** 用户对同一情报更新反馈
**When** 新反馈提交成功
**Then** 当前有效反馈原位更新并保留必要的审计时间
**And** 可逆操作提供撤销；提交失败时恢复原状态、保留上下文并允许重试。（FR43、UX-DR18）

**Given** 记录为演示数据的情报
**When** 用户尝试提交价值反馈
**Then** 可将操作用于演示交互，但不得进入真实验证指标
**And** 演示反馈使用独立 namespace，不与真实反馈汇总。（FR2、ARCH-9）

**Given** 用户离线或 AI 服务不可用
**When** 提交情报反馈
**Then** 反馈保存到当前设备并立即可见，不依赖网络或 AI
**And** 反馈、收藏和选择保持独立状态，反馈不自动修改规则。（FR43、FR46）

**Given** 用户仅使用键盘或屏幕阅读器
**When** 打开反馈入口、选择类别、提交和撤销
**Then** 每个选项具有稳定名称、状态和可见焦点，快捷键有可见等价入口
**And** 成功或错误有非颜色反馈，关键失败不只依赖短暂 Toast。（UX-DR20、UX-DR24）

### Story 7.2：登记已确认漏报及其原因

作为校准雷达的用户，
我希望记录系统未提醒或未进入主流的已确认重大事件及原因，
以便同时衡量准确率和漏报，防止系统靠少展示制造表面质量。

**验收标准：**

**Given** 用户发现一条已存在于普通候选或被过滤视图的漏报
**When** 选择“记录漏报”
**Then** 系统关联该情报、当时的规则版本、筛选结果和可获得的来源证据
**And** 用户可选择或说明未采集、去重错误、赛道不匹配、来源权重过低、AI 判断错误、溯源不足或其他原因。（FR44）

**Given** 重大事件尚不存在于本地数据库
**When** 用户登记外部已知漏报
**Then** 系统允许保存最小可核验记录，包括标题、公开原文链接、发现时间、原因和备注
**And** 该记录明确标识为用户登记的验证证据，不伪装成已采集情报。（FR44）

**Given** 用户提交的漏报链接无效、指向禁用地址或缺少最小证据
**When** 核心校验记录
**Then** 阻止不安全或不可识别的输入并给出字段级错误
**And** 不自动抓取本机、内网或禁用协议目标，未提交输入保持可修改。（NFR17、UX-DR17）

**Given** 用户修改或撤销漏报记录
**When** 操作完成
**Then** 验证汇总使用最新有效状态，同时保留必要的本地审计时间
**And** 不删除或改写原始情报、来源记录或历史规则结果。（FR44）

### Story 7.3：汇总四周个人验证指标

作为产品验证者，
我希望查看提醒有效率、主流有效率、漏报和每日使用情况，
以便判断雷达在连续四周内是否真正减少时间并提高信号质量。

**验收标准：**

**Given** 当前设备已积累真实反馈、提醒记录、漏报记录和使用会话
**When** 用户打开验证概览
**Then** 系统按明确分母展示“值得立即知道”提醒占比、主流“有价值”占比、已确认漏报数和每日使用情况
**And** 指标说明目标值：提醒有效率 ≥80%、主流有效率 ≥70%、每日使用 ≤15 分钟、已确认关键漏报为 0。（FR45）

**Given** 样本包含演示数据、撤销反馈、普通候选或未实际提交的通知
**When** 计算指标
**Then** 演示数据和无效/撤销记录被排除，分子与分母定义可查看
**And** 系统不以减少采集或隐藏普通候选的方式提高表面准确率。（FR45、ARCH-9）

**Given** 验证周期不足四周或样本量过小
**When** 展示指标
**Then** 系统明确显示当前周期、样本数和“不足以得出稳定结论”的状态
**And** 不把校准期结果宣传为模型精度或产品成功结论。（FR45）

**Given** 用户查看按天、周、赛道或来源的指标切片
**When** 切换范围
**Then** 所有切片使用相同可解释统计口径，保持当前筛选和时间范围
**And** 图表或数字均有文字等价、可访问名称和非颜色区分。（UX-DR20、UX-DR21）

**Given** 当前设备离线
**When** 用户查看验证指标
**Then** 使用本地事实源完整计算并展示已保存数据
**And** 明确说明数据只代表当前设备，不暗示跨设备汇总。（FR45、FR57、UX-DR9）

### Story 7.4：从透明证据手动校准筛选规则

作为希望降低误报和漏报的用户，
我希望按赛道、来源、规则命中和筛选结果查看反馈汇总，并在预览影响后手动调整规则，
以便改善雷达而不让系统替我静默决策。

**验收标准：**

**Given** 当前设备存在价值反馈和漏报记录
**When** 用户查看校准分析
**Then** 系统按赛道、来源、规则命中、重要程度和筛选结果汇总误报与漏报证据
**And** 每个汇总可下钻到对应情报、反馈、规则版本或用户登记证据。（FR46）

**Given** 用户从情报详情、漏报或汇总进入规则编辑
**When** 修改关键词、排除词、来源可信度或阈值
**Then** `RuleImpactPreview` 显示修改摘要、影响范围、冲突、漏报风险、生效时间和历史数据说明
**And** 阻断错误不可保存；警告只有经用户明确确认后才可继续。（FR46、UX-DR6）

**Given** 用户确认有效规则变更
**When** 保存完成
**Then** 系统明确说明“下一轮同步/评估生效”，保留历史情报、反馈和旧规则结果的可追踪关系
**And** 保存、规则生效和配置更新不采用乐观提交，失败时保留输入。（FR46、ARCH-18）

**Given** 新反馈或统计趋势出现
**When** 系统更新校准分析

**And** 保存仍经过 FR62 的阻断错误与过窄风险分流，不建立绕过验证的快捷路径。（FR46、FR62、FR64、UX-DR32）

**And** Epic 7 在当前设备形成透明、可审计、用户掌控的质量闭环，不自动学习权重或依赖云端分析。

## Epic 8：在离线、故障和移动生命周期中继续工作

用户可在单源失败、AI 失败、离线、后台受限、挂起、终止或进程回收后继续使用安全缓存，查看具体影响与数据安全状态，独立重试可恢复任务并导出脱敏诊断；系统恢复时不产生重复入库、分析或通知。

### Story 8.1：在单源故障中保留部分成功结果

作为依赖多个信息源的用户，
我希望一个来源失败时其他来源仍完成并保留结果，
以便局部故障不会让整个情报雷达失去价值。

**验收标准：**

**Given** RSS/Atom、GitHub Release 和 arXiv 同时同步且其中一个来源超时、连接失败或解析错误
**When** 同步任务结束
**Then** 未故障来源正常完成并提交各自记录、游标和同步计数
**And** 故障仅归属于对应来源，不回滚其他来源已保存结果。（FR47、NFR7、NFR23）

**Given** 整轮同步包含成功和失败来源
**When** 核心生成任务与应用状态
**Then** 任务状态为 `partially_succeeded`，同时返回成功计数与来源级问题列表
**And** 不伪装为全部成功，也不折叠成使成功结果不可用的整体失败。（FR47、ARCH-14、ARCH-19）

**Given** 用户查看主情报流或 `SyncHealthSummary`
**When** 最近同步为部分成功
**Then** 已成功内容继续可浏览，界面显示失败对象、阶段、时间、影响范围、数据安全状态和下一步
**And** 错误附着在相关来源或状态区域，不以全屏错误覆盖可用内容。（UX-DR5、UX-DR17、NFR32）

**Given** 数据库检测到完整性异常
**When** 受影响来源尝试继续写入
**Then** 相关写入成功次数为 0，未受影响的已保存数据继续可读
**And** 应用进入适当的阻塞或只读诊断状态，并提供可操作恢复说明。（NFR14、ARCH-19）

**Given** GitHub 项目发现与 GitHub Release 同时存在，且某个发现订阅超时、限流、响应无效或部分分页失败
**When** 本轮任务状态提交
**Then** 故障只归属于对应发现订阅和发现运行，GitHub Release 继续使用独立任务与状态
**And** 既有 Release 成功结果不得被阻断、隐藏或回滚，发现部分完成不得显示为成功零结果。（FR47、FR64、NFR54、ARCH-33、UX-DR35）

### Story 8.2：按退避规则独立重试来源和 AI 任务

作为遇到外部服务故障的用户，
我希望只重试失败来源或待处理 AI 分析，并了解何时可以重试，
以便恢复工作而不重复已成功任务或扩大限流。

**验收标准：**

**Given** 某来源失败且 `AppError.retryability` 为 manual
**When** 用户选择该来源的独立重试
**Then** 系统只为目标来源创建新的持久任务，不重新同步已成功来源
**And** 任务使用稳定来源 ID、前次游标和明确 ExecutionBudget。（FR48、ARCH-15）

**Given** AI 分析任务失败且仍满足当前凭据与来源授权
**When** 用户选择重试
**Then** 系统只重试对应分析输入，并保留原始情报和既有有效分析版本
**And** 不保存明文密钥、不重复入库，也不影响其他 AI 任务。（FR48、NFR25）

**Given** 来源或 provider 处于 `retry_wait` 且有明确恢复时间
**When** 用户查看或尝试重试
**Then** 重试入口保持可发现但禁用，并显示暂不可重试的原因和时间
**And** 指定时间前外部请求次数为 0。（FR48、NFR24）

**Given** 服务没有提供 Retry-After 且连续失败
**When** 系统执行自动退避
**Then** 首次重试间隔不少于 60 秒，后续间隔不缩短，第三次至少为首次的 4 倍
**And** UI 不自行实现无限重试或固定间隔轮询。（NFR24、ARCH-19）

**Given** 用户重复点击重试或相同任务被晚到事件再次触发
**When** 核心处理请求
**Then** 幂等键与任务状态确保最多一个有效重试任务
**And** 事件只触发重新查询，不直接修改领域事实或产生重复副作用。（NFR13、ARCH-16）

**Given** GitHub 发现运行失败、限流或部分完成并允许重试
**When** 用户或系统在合法时间触发发现重试
**Then** 系统只重试目标发现订阅并沿用 NFR24、rate-limit reset 与 ExecutionBudget
**And** 不重新同步已成功的 GitHub Release，不回滚已确认发现结果，也不创建重复监控对象。（FR48、FR64、NFR24、NFR54、ARCH-38）

### Story 8.3：在离线模式继续使用本地资料和配置

作为网络不稳定或暂时离线的用户，
我希望继续浏览、搜索、筛选、收藏、配置和反馈，
以便外部服务不可用时仍能完成本地研究工作。

**验收标准：**

**Given** 当前设备离线且已有缓存数据
**When** 用户浏览主流、搜索、筛选、查看详情和读取已保存收藏正文
**Then** 所有本地任务保持可用，缓存访问率为 100%
**And** 界面显示“离线可用”、最后成功同步和当前数据新鲜度，不使用全屏错误。（FR49、NFR10）

**Given** 用户离线时修改来源配置、规则或提交反馈
**When** 保存操作只需本地事务
**Then** 有效配置和反馈保存到当前设备并在重启后保持
**And** 需要外部验证或获取的动作明确标记为等待联网，不伪造远程成功。（FR49）

**Given** 用户离线时尝试同步、打开未缓存原文、获取未缓存正文或执行 AI 分析
**When** 操作需要网络
**Then** 系统不发起失败风暴，明确说明受影响动作和联网后恢复条件
**And** 已缓存内容和当前输入保持可用。（FR49、UX-DR17）

**Given** 网络恢复且存在仍有效的待处理任务
**When** 应用获得执行机会
**Then** 任务无需用户重新创建即可按预算恢复或明确标记为可重试
**And** 每个逻辑任务最多产生一份有效入库、一份分析和一次通知。（FR49、NFR27）

**Given** 网络状态在浏览期间变化
**When** UI 更新离线、恢复中或已恢复状态
**Then** 只更新相关状态和可用动作，不清空列表、搜索、筛选、选择或未提交输入
**And** 高频状态变化不会反复打断屏幕阅读器。（UX-DR13、UX-DR18）

### Story 8.4：在移动生命周期中安全恢复持久任务

作为移动设备用户，
我希望应用在挂起、终止、进程回收、重启或网络切换后保留数据并恢复有效任务，
以便不可控的系统生命周期不会造成数据损坏或重复副作用。

**验收标准：**

**Given** iOS/iPadOS 或 Android 正在同步、分析、收藏、保存配置或处理通知
**When** 应用进入后台、挂起、被终止或进程被回收
**Then** 已完成事务保持完整，未完成任务状态持久化为可恢复或明确可重试
**And** 系统不依赖退出回调一定执行，也不持有长期 FFI callback。（FR51、NFR40、ARCH-16）

**Given** 应用重新获得前台或系统授予的后台执行机会

**Then** 使用有限 `ExecutionBudget` 继续仍有效工作，并通过 PlatformEffect outbox 执行适用平台副作用
**And** 无法继续的任务标记为可重试并说明原因，不静默丢弃。（FR51、NFR9）

**Given** 在同步、分析和通知不同阶段触发挂起、回收、设备重启和网络恢复
**When** 恢复完成
**Then** 已完成数据损坏或丢失为 0，每个有效任务均恢复、重试或明确标记
**And** 重复入库、重复分析、重复通知和并发重复任务均为 0。（NFR13、NFR40）

**Given** 移动应用在后台或挂起且无待处理任务
**When** 持续观察 30 分钟
**Then** 产品主动网络请求和自行周期唤醒均为 0，不持续占用后台执行时间
**And** 系统授予的明确后台任务在预算或任务完成后结束。（NFR48）

**Given** 移动基线设备加载 50,000 条数据并完成 20 次前后台循环
**When** 执行主流、搜索、详情、收藏和设置操作
**Then** 非预期终止为 0，核心时延满足 NFR2/NFR3
**And** 相同操作后的内存不连续 5 轮增长且总增幅不超过首轮稳定值的 20%。（NFR49）

**Given** GitHub 发现任务在移动后台执行期间被挂起、终止或回收
**When** 应用再次获得执行机会并恢复任务
**Then** 系统保留原 ExecutionBudget、分页完成度、已确认结果、错误与退避状态，并从安全边界继续或明确标记可重试
**And** 未完成分页不得误报为成功零结果，已确认项目不得再次标记为新发现或创建重复 Release 监控。（FR51、FR64、NFR40、NFR54、ARCH-38）

### Story 8.5：查看全平台状态并导出安全诊断

**验收标准：**

**Given** 用户在任一受支持平台打开同步与诊断
**When** 页面加载
**Then** 显示最后成功同步时间、当前同步状态、各来源结果、待处理任务、数据新鲜度和影响时效性的后台限制

**Given** 当前设备配置了 GitHub 项目发现和 GitHub Release 监控
**When** 用户打开同步与诊断
**Then** 两类任务分别展示进度、最后成功时间、运行结果、错误、退避与重试动作
**And** 发现状态不得覆盖或替代 Release 状态，任一方成功或失败均独立可见。（FR50、FR52、FR64、NFR54、UX-DR35）

**Given** 系统存在来源、AI、存储、迁移、权限或后台限制错误
**When** 用户查看问题
**Then** 每项错误包含对象、阶段、时间（可得时）、影响范围、数据安全状态、retryability、用户动作和 correlation ID
**And** 无用户动作时明确说明等待条件或无需操作。（FR50、NFR32）

**Given** 用户选择导出诊断
**When** 系统使用明确 allowlist 构建导出
**Then** 仅包含允许的版本、平台、操作、来源 ID、状态、计数、耗时、错误码和 correlation ID
**And** 不直接打包应用数据目录。（FR50、ARCH-24）

**When** 系统构建发现诊断字段
**Then** 只记录订阅 ID、运行 ID、页码、计数、状态码、错误分类、限流和退避元数据
**And** 完整搜索条件、项目描述、仓库响应、命中项目正文及用户控制内容均不得进入默认诊断。（FR50、FR64、ARCH-40）

**Given** 正常或故障状态中存在 API Key、Authorization、Cookie、完整正文、完整 prompt、敏感提示或带敏感查询参数的 URL
**When** 生成并检查诊断输出
**Then** 上述敏感内容命中均为 0，移除项以不泄露原值的标识替代
**And** URL 默认移除 query 和 fragment。（FR50、NFR20）

**Given** 用户删除 secret、来源或正文后重新导出诊断
**When** 检查缓存、索引和诊断引用
**Then** 已要求删除的数据残留为 0，被删 secret 不再出现或被请求使用
**And** 允许保留的信息已在删除确认前逐项说明。（NFR47、ARCH-24）

**Given** Story 8.1–8.5 全部完成
**When** 执行单源故障、AI 故障、离线、限流、挂起、终止、回收、重启、恢复和诊断导出矩阵
**Then** FR47–FR52 的部分成功、独立重试、本地工作、移动恢复、状态可见和安全诊断路径全部可完成
**And** Epic 8 在外部环境不可靠时仍保护已完成数据、用户控制和幂等副作用。

**And** Apple 支持动态字体等门禁，Android 核心触控目标 ≥48×48dp，平台手势均有可见等价操作。（NFR30、NFR43、NFR44、UX-DR20、UX-DR24）

**Given** 用户在 Windows、iPhone、iPad、Android 手机或 Android 平板进入 GitHub 项目发现
**When** 创建、修改、启用或停用订阅，审查结果与命中依据，并执行忽略/撤销、停用自动关注或转固定关注
**Then** 每个平台都提供完整原生路径且使用相同的分类、关注和运行状态语义
**And** 五类设备适用步骤完成率为 100%，不得要求转到另一平台完成控制。（FR55、FR64、NFR39、NFR54、UX-DR36、UX-DR37）

**When** 窗口宽度、方向、分屏、折叠姿态或列表—详情模式变化
**Then** 当前订阅、结果筛选、选中项目、未提交表单输入、命中依据展开状态和滚动锚点全部保留
**And** 新布局恢复等价目的地与安全返回路径，不隐藏任何关注控制。（FR56、NFR42、UX-DR36）

### Story 9.3：明确当前设备数据边界并安全执行删除

作为重视本地数据控制的用户，
我希望始终知道数据只在当前设备，并在清理前理解删除与保留范围，
以便不会误以为存在云备份、跨设备同步或未配置的恢复能力。

**验收标准：**

**Given** 用户首次使用或打开设置、诊断与数据管理
**When** 查看数据作用域说明
**Then** `DeviceScopeNotice` 明确列出配置、收藏、反馈、凭据和历史情报只保存在当前设备
**And** 明确说明 MVP 无云备份、跨设备同步或自动迁移。（FR57、UX-DR9）

**Given** 两台设备分别修改来源、规则、收藏、反馈、正文或凭据
**When** 比较另一设备的数据与网络传输
**Then** 未经明确同步能力自动出现变化的次数为 0，跨设备传输次数为 0
**And** “仅影响当前设备”说明覆盖率为 100%。（FR57、NFR46）

**Given** 用户准备删除正文、缓存、配置、反馈、凭据或执行应用内清除数据
**When** 破坏性确认出现
**Then** 逐项说明将删除、允许保留、作用设备和可恢复性，并提供取消入口
**And** 不可逆操作不由手势独占，保存/删除不采用乐观提交。（FR58、UX-DR16、ARCH-18）

**Given** 用户确认删除并重新启动应用
**When** 检查本地数据、派生索引、安全凭据、诊断和网络请求
**Then** 用户明确要求删除的数据残留为 0，被删除凭据再次使用为 0
**And** 成功反馈说明实际清理范围，失败提供数据安全状态和恢复动作。（NFR47、UX-DR17）

**Given** 用户从操作系统直接卸载应用
**When** 应用无法拦截该系统行为
**Then** 数据后果通过设置、隐私说明和平台标准分发披露预先表达
**And** 产品不承诺虚假的应用内卸载确认、云恢复或自动迁移。（FR58）

**Given** 用户查看或修改 GitHub 发现订阅、发现结果和关注控制
**When** 界面说明数据与动作作用域
**Then** 明确这些配置、结果、依据和状态只影响当前设备，不暗示云端或跨设备同步
**And** 停用订阅、条件失配、忽略项目或停用自动关注不得使用删除语义，也不得触发历史删除确认。（FR57、FR58、FR64、NFR46、UX-DR34）

### Story 9.4：保护安装、升级和数据迁移路径

作为长期使用本地资料的用户，
我希望安装和升级不会静默损坏配置、收藏、反馈或历史情报，
以便版本演进期间仍能信任设备上的长期数据。

**验收标准：**

**Given** 候选构建在全新设备安装
**When** 应用首次启动
**Then** 按验证数据库、必要备份、事务化迁移、完整性检查的顺序开放写操作
**And** 创建的数据目录、SQLite 版本、外键和安全设置符合架构约束，并向用户提供与安装/本地数据后果一致的说明。（FR58、ARCH-4、ARCH-10）

**Given** 任一声明支持的既有数据版本包含配置、收藏、反馈和历史情报
**When** 升级到候选构建
**Then** 静默丢失、清空或错误改写记录数为 0，关键关系保持一致
**And** 升级前后数据后果说明覆盖率为 100%。（NFR12、NFR50）

**Given** 迁移无法安全完成或完整性检查失败
**When** 候选构建启动
**Then** 停止升级写入并进入可恢复的只读诊断状态，旧数据库保持可恢复
**And** 提供具体失败、数据安全状态和恢复路径，不允许旧版本继续写已升级 schema。（NFR12、ARCH-10）

**Given** 用户关闭开机启动、撤销权限或保留特定本地设置
**When** 升级应用
**Then** 这些明确选择保持不变，不被候选构建重置
**And** 权限和数据保留变化必须由用户可见操作或平台要求触发。（NFR36、NFR50）

**Given** 既有版本包含 GitHub 发现订阅、规范项目身份、仓库别名、带时间戳观测、命中依据、忽略和监控状态
**When** 升级到候选构建并执行迁移
**Then** 上述记录、版本关系及其关联 Release 历史均被保留，身份合并与唯一约束继续成立
**And** 静默丢失、错误改写、重复项目、重复有效监控、重复 Release 和重复通知数量均为 0。（FR64、NFR50、NFR54、ARCH-34、ARCH-43）

**Given** 候选构建准备进入发布门禁
**When** 在干净和升级设备上执行验证
**Then** 覆盖安装、启动、卸载披露、数据库创建/迁移、三来源、AI 有/无 Key/失败、离线恢复、后台机会、通知深链、无障碍、数据保留和诊断导出
**And** 每项保留构建、系统、硬件、数据集、前置条件、实际结果和结论。（NFR50、ARCH-22）

### Story 9.5：通过移动受控测试分发与隐私披露门禁

作为受控测试参与者和发布负责人，
我希望只有具备有效签名、安装资格和完整隐私说明的移动构建才能分发，
以便候选构建可安装、可追责且声明与实际行为一致。

**验收标准：**

**Given** iOS/iPadOS 候选构建准备归档
**When** 受保护发布任务执行
**Then** 生成有效签名归档并仅通过 TestFlight 分发给授权测试账户或设备
**And** PR/fork 构建无法访问签名密钥，首版不进入公开 App Store。（NFR51、ARCH-22、ARCH-23）

**Given** Android 候选构建准备发布
**When** 受保护发布任务执行
**Then** 生成有效签名 AAB 并仅通过 Google Play Internal Testing 分发给授权测试对象
**And** debug APK 仅供开发，PR/fork 构建无法访问发布签名密钥。（NFR51、ARCH-22、ARCH-23）

**Given** 构建签名缺失/失效或安装资格无效
**When** `DistributionDisclosureStatus` 评估候选构建
**Then** 该构建进入受控测试分发的次数为 0，并显示具体平台、版本、阻塞原因和修复路径
**And** 分发状态位于构建/关于/诊断上下文，不使用重大情报的颜色或图标语义。（UX-DR10、NFR51）

**Given** 移动候选构建准备分发
**When** 检查隐私与数据处理说明
**Then** 设备本地数据、系统权限、公开来源、第三方 AI 外发数据、正文保留与删除、诊断范围、无云备份/跨设备同步七类披露完整率为 100%
**And** 用户可从首次 AI 授权、设置和分发说明再次访问适用内容。（UX-DR10、NFR51）

**Given** 候选构建的实际权限、网络请求、内容保留、删除或诊断行为与披露不一致
**When** 发布门禁核验
**Then** 声明与行为不一致项必须为 0，否则阻止分发
**And** 分发签名前已证明数据库迁移、任务恢复和隐私边界在三端一致。（NFR51、ARCH-22）

**Given** 候选构建包含 GitHub 项目发现能力
**When** 在 Windows、iPhone、iPad、Android 手机和 Android 平板执行发布验收
**Then** 使用同一版本的 NFR54 固定仓库响应、观测快照和预期结果验证条件、分类、依据、身份、控制、历史保留与故障隔离
**And** 正式验收不依赖 GitHub 当前在线结果，实时网络波动不得改变发布结论。（NFR54、ARCH-42、UX-DR37）

**Given** Story 9.1–9.5 全部完成
**When** 在 Windows、iPhone、iPad、Android 手机和平板执行四条核心用户旅程、布局/辅助技术矩阵、升级删除矩阵和移动分发门禁
**Then** FR55–FR58 全部可验证，适用核心步骤完成率为 100%，跨平台绕行阻断为 0
**And** ai-subscribe 具备平台原生、设备本地、可升级且可受控分发的完整 MVP 交付边界。
