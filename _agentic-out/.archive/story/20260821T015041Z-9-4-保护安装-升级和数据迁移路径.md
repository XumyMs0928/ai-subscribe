# Story 9.4：保护安装、升级和数据迁移路径

状态：ready-for-dev

## Story

作为长期使用本地数据的用户，  
我希望安装和升级过程不会静默损坏我的配置、来源、同步历史和情报证据，  
以便我能安全采用新的 Windows 内部候选版本，并在失败时知道数据是否安全以及如何恢复。

## 当前阶段交付覆盖层

- 本 Story 是 Phase 1 的最后一个闭环 Story，只验收 Windows 10/11 x64、标准当前用户、real RSS/Atom minimum-loop 的受控内部候选。安装器采用 NSIS current-user 模式，不请求管理员提升；不交付 MSI、公共商店、自动更新或公开分发。
- 当前数据库 tip 固定为 schema v10。声明支持的升级起点必须冻结为 **v1–v10**，并由可独立复用、版本明确的文件型 SQLite fixture 逐版本证明；schema 0 只代表全新安装，不得当作含用户数据的旧版本。若代码审计证明某历史版本无法构造真实合同 fixture，必须先收窄并记录支持清单，禁止模糊宣称“所有旧版本”。
- 数据保护只覆盖当前已经存在的持久实体：应用/引导元数据、配置版本与当前选择、RSS/Atom 来源及启停/刷新状态、增量 checkpoint、任务和同步结果、real intelligence facts/content/provenance、association 与 current rule evidence。收藏、反馈、处理状态、GitHub discovery、通知权限、开机启动等未实现模型不得为迁移测试而提前建表或生成假数据。
- “迁移前备份”是同一设备上的受控 rollback artifact，不是云备份、跨设备同步或卸载后恢复承诺。全新空库无需伪造备份；已有 v1–v9 文件必须先生成经校验的一致快照，再进入迁移事务。
- 内部候选允许未使用 Windows 生产代码签名，但必须明确显示“受控测试构建，未使用 Windows 生产代码签名”、构建来源、版本、schema tip、SHA-256 和适用范围；不得称为已签名、适合公开发布或商店就绪。
- 风险信号 `security + high-nfr + cross-artifact` 推荐 assured；为延续已批准的 Phase 1 快速闭环显式采用 standard。readiness 旧快照和系统级 test design 缺失是已知建议项，但不能降低迁移零静默损失、失败关闭、候选身份与真实设备证据门禁。

## 验收标准

### AC1 — Windows 内部候选身份与当前用户安装边界

**Given** 构建目标是 Phase 1 Windows 10/11 x64 受控内部候选  
**When** 生成、检查或安装 NSIS candidate  
**Then** Tauri bundle 只生成 `x86_64-pc-windows-msvc` NSIS current-user installer，默认写入当前用户目录且不请求管理员权限；bundle/release 配置不包含 MSI、updater、store upload、dev URL、debug/test command、宽松 CSP 或额外 WebView capability  
**And** 与安装器一起生成机器可校验 release manifest，至少记录 product/app version、platform/target、database schema tip `10`、API/contract version、validator/core commit、fixture family/version、构建时间、签名状态与适用范围、SBOM reference、installer filename/size/SHA-256；未签名时在发布说明和安装指引中使用准确受控构建披露，不把 SmartScreen 绕过描述成安全证明。（ARCH-22–ARCH-25、NFR34、NFR38）

### AC2 — 全新安装的数据库启动门

**Given** 当前用户 app-data 目录中不存在产品数据库  
**When** 首次启动内部候选  
**Then** radar-core 的唯一 SQLite owner 按固定顺序执行：解析并验证 app-data/数据库目标 → 验证 bundled SQLite 版本 → 创建/初始化事务 → 设置并回读 `foreign_keys=ON`、WAL、有限 busy timeout 等当前安全配置 → 将 schema 初始化到 v10 → 执行 bounded `integrity_check` 与 `foreign_key_check`/当前 schema contract → 最后才开放业务写入与 seed  
**And** fresh install 明确记录 backup 为 `not_applicable`，不得制造空备份；任一步骤失败都不 seed demo、不写用户配置/来源/任务/情报，并进入 AC4 的安全状态。安装/关于或发布说明明确数据只保存在当前设备、没有云备份或跨设备同步，并说明升级与 OS 卸载的实际后果。（ARCH-4、ARCH-10、FR57–FR58、NFR12、NFR14）

### AC3 — schema v1–v10 的语义零损失升级

**Given** 每个已声明支持起点 v1–v10 的权威文件型 fixture 都包含该版本实际存在的最大合法数据集、稳定 identity、边界值及关系  
**When** 当前候选首次打开数据库  
**Then** v1–v9 均先用 SQLite backup API 或等价一致快照机制创建 versioned rollback artifact 并校验其可打开、schema version 与 checksum/metadata，再通过 core-owned、单写者、逐版本事务迁移到 v10；v10 只验证且不产生迁移备份或 schema 写  
**And** 每个起点迁移前后进行语义比较：所有该版本原有记录数、稳定 IDs、配置当前版本与 revision、来源 enabled/状态/checkpoint、任务与同步结果、facts/content/provenance、association/rule evidence 及 FK/unique 关系零静默丢失、清空、重复或误改；只允许迁移合同明确列出的 deterministic transform。重复启动不得重跑迁移、复制数据或替换成功备份。（NFR12、NFR50）

### AC4 — 备份、迁移与完整性失败时安全关闭并可诊断

**Given** 文件打开、备份创建/校验、任一 vN→vN+1 步骤、commit、schema contract、`integrity_check` 或 `foreign_key_check` 被确定性故障注入  
**When** 启动门检测到失败或检测到高于 v10 的未知 future schema  
**Then** 所有未完成迁移回滚，业务写入口保持关闭，原数据库及最后一个已验证 rollback artifact 可恢复；future schema 和已升级 schema 被旧二进制打开时必须 fail closed，禁止 downgrade write、自动重建或覆盖  
**And** Windows 仍可展示有界的 `read_only_migration_failure` 诊断视图/状态，说明失败阶段、受影响对象、数据是否仍安全、当前 schema/候选版本、correlation ID、合法的退出/查看恢复指引/稍后重试动作；不得泄露绝对用户路径、SQL、正文、URL query、secret 或底层错误。若不能安全读取业务数据，就准确显示阻断状态，不以空列表冒充“无数据”。（ARCH-10、NFR12、NFR14、UX-DR17）

### AC5 — 当前已实现用户选择和关系保持

**Given** 旧数据库含当前已实现的配置、引导进度、RSS/Atom 来源启停与刷新选择、同步 checkpoint/result、情报事实/溯源/关联/规则记录  
**When** 安装新候选并完成升级  
**Then** 用户选择、revision、stable IDs、来源—结果—事实—证据关系及最后已知状态保持；迁移不得启用已禁用来源、重置当前配置、重新 seed 覆盖 real 数据、恢复已删除记录、改写历史时间或把 AI unavailable 变成模拟结论  
**And** 打开/验证/升级本身不触发 RSS 网络请求、AI、系统浏览器、通知或其他平台 effect。开机启动、通知权限、收藏/反馈/处理状态和 GitHub discovery 因当前未实现而明确 Deferred，不得以缺字段默认值伪造“已保持”。（canonical AC4–AC5 的 Phase 1 覆盖）

### AC6 — 本地数据、升级与卸载后果的可信披露

**Given** 用户查看候选安装指引、应用内数据边界入口或升级/卸载说明  
**When** 决定安装、升级、清除数据或通过 Windows 卸载应用  
**Then** 各入口使用同一权威 disclosure，明确列出当前设备保存的数据类别、迁移前 rollback artifact 的用途/位置策略与保留上限、无云备份/无跨设备同步、升级通常保留什么、应用内清除与 OS 卸载各自实际保留或删除什么以及不可恢复条件  
**And** 不声称应用能拦截 Windows 卸载流程；若 NSIS 默认保留 app-data，就明确“卸载应用不等于删除本地数据”及手动清除路径/动作，若实现显式卸载数据选项则必须默认不选、清晰确认且单独验证。披露不能只存在于临时 Toast 或测试文案。（FR57–FR58、UX-DR10）

### AC7 — 隔离 Windows 候选矩阵与可审计证据

**Given** clean fixture、v1–v10 supported-upgrade fixtures、每类迁移/完整性失败 fixture 与 Story 1.6–4.6 的 real RSS 最小闭环数据  
**When** 在隔离的 Windows 10/11 x64 标准用户候选环境运行正式 gate  
**Then** 证据覆盖安装/首启/重复启动、逐版本升级、失败保护、future-schema/old-binary lockout、已实现数据可读、RSS minimum-loop smoke、卸载披露与实际数据保留行为，并为每次运行记录 build/OS/hardware、installer SHA-256、dataset/fixture、前置条件、步骤、实际结果、结论和 artifact 路径  
**And** 自动化的 core/contract/transport/UI/release-surface gates 与隔离 VM/设备 smoke 分层；测试不得修改开发机全局 PATH、主题、缩放、权限或真实用户 app-data，不访问公网、不真实触发系统浏览器。最终结论只能是 `Windows RSS minimum-loop PASS/FAIL`；公开签名、商店、自动更新、移动、三来源、AI、后台/托盘/通知、GitHub discovery 与完整跨平台矩阵必须标 `Deferred/N/A`，不得计 PASS。（canonical AC6 的 Phase 1 覆盖）

## 完整产品 Canonical AC（Deferred 部分保留）

Epics 中 Story 9.4 的六条 canonical AC 继续作为长期产品目标：所有声明支持的数据版本、收藏/反馈/处理历史、开机启动与已撤销权限、GitHub discovery identity/alias/observations/monitor/release history，以及干净/升级设备上的三来源、AI、离线、后台、通知、无障碍和诊断完整发布矩阵。当前 Phase 1 仅验收 Windows RSS minimum-loop 的内部候选、当前 schema v1–v10、失败保护和设备本地/卸载披露；所有未激活能力不得通过占位表、模拟 fixture 或 responsive/browser mock 冒充完成。

## Dev Notes

### 已有实现必须复用

- 当前唯一数据库入口是 `DemoStore::open -> from_connection`，已验证 bundled SQLite 最低版本、设置 FK/WAL/busy timeout、按 v1→v10 事务迁移并运行 `verify_database_contract`。Story 9.4 应在此基础上拆出 startup/migration coordinator，不创建第二 SQLite owner。[Source: `crates/radar-core/src/application/demo.rs`]
- 现有迁移已经覆盖 v1→v2 evidence、v2→v3 setup、v3→v4 configuration、v4→v5 sources、v5→v6 jobs、v6→v7 sync results、v7→v8 real intel、v8→v9 associations、v9→v10 rules；当前测试含若干 rollback/contract failure，但没有统一的文件型 v1–v10 fixture matrix、迁移前一致备份和可恢复只读 startup state。[Source: `crates/radar-core/src/application/demo.rs`; `crates/radar-core/tests/`]
- 当前 `DemoState` 延迟打开 `Mutex<Option<DemoStore>>`，失败只在业务 command 上返回错误；应演进为一次性、可观察 startup state，不能让 React 通过空列表猜测迁移失败。[Source: `apps/windows/src-tauri/src/commands/mod.rs`]
- 当前 Tauri 配置 `bundle.active=false`，release tests 已精确验证本地 CSP、单一 handler 和 `core:default` capability。Story 9.4 只增加 NSIS current-user 候选面，必须继续复用并加强这些 exact gates。[Source: `apps/windows/src-tauri/tauri.conf.json`; `apps/windows/src-tauri/tests/release_surface.rs`]
- 当前 `README.md` 仍描述 Story 1.2 健康壳且 Tauri build 使用硬编码绝对 runner、`--no-bundle`；本 Story 必须更新为当前 product/candidate reality，并使用可移动的项目内 wrapper。[Source: `README.md`; `package.json`]

### Architecture Compliance

- 顺序固定为：验证数据库/版本 → 必要时一致备份 → 单写者事务迁移 → schema/integrity/FK 验证 → 开放业务写。任何 bootstrap、sync recovery 或 fixture seed 都不能越过写门。[Source: `_agentic-out/planning/architecture.md#数据架构`; `#数据库与迁移`]
- SQLite 备份必须使用 online backup API 或受控 checkpoint 后的一致快照，不能用文件复制读取活跃 WAL 数据库。官方 SQLite 文档说明 backup API 产生源数据库一致 snapshot，并需处理 busy/locked。[Source: https://www.sqlite.org/backup.html]
- 主 WebView 继续只加载打包资源；无通用 SQL/file/shell/http command。诊断只返回 allowlisted fields，绝对路径、SQL、正文、URL query、secret 需要脱敏。[Source: `_agentic-out/planning/architecture.md#FFI-与进程边界`; `#日志与诊断`]
- unknown future schema 与 downgrade 均 fail closed；Phase 1 不创建不存在的未来 schema 或伪造其迁移证据。[Source: `_agentic-out/planning/architecture.md#第一阶段激活架构`]

### Library / Framework Requirements

- 保持锁定版本，不以本 Story 顺带升级：Tauri core `2.11.5`、CLI `2.11.4`、rusqlite `0.40.1` bundled、React `19.2.8`、Vitest `4.1.10`、Playwright `1.62.1`。[Source: `apps/windows/src-tauri/Cargo.toml`; `apps/windows/package.json`; `crates/radar-core/Cargo.toml`; `package.json`]
- Tauri v2 官方 Windows installer 文档确认 NSIS 支持 current-user 安装且默认无需管理员权限；本 Story仍显式写出 `installMode: currentUser`，避免配置漂移。[Source: https://v2.tauri.app/distribute/windows-installer/; https://v2.tauri.app/reference/config/]
- Tauri 官方说明 Windows 未签名应用可执行但可能出现 SmartScreen 警告；内部候选必须准确披露，不将“可运行”视为生产信任。[Source: https://v2.tauri.app/distribute/sign/windows/]
- SQLite `integrity_check` 不替代 `foreign_key_check`；二者都必须纳入成功写门，且结果必须精确验证而不是仅检查命令未报错。[Source: https://www.sqlite.org/pragma.html#pragma_integrity_check]
