# Story 1.1：建立共享核心与版本化契约基线

状态：ready-for-dev

## Story

作为产品验证者，
我希望先建立可测试的共享领域核心与稳定跨平台契约，
以便三个原生平台可以逐一接入同一业务权威而不复制规则。

## 验收标准

### AC1：共享核心工程基线

**Given** 工作区尚未建立正式应用工程  
**When** 按架构初始化 Cargo workspace、`radar-core`、`radar-ffi`、`contracts` 和 `xtask`  
**Then** 共享核心可独立构建并通过健康检查与纯 Rust 契约测试  
**And** 本 Story 只建立最小契约与工程边界，不提前创建未来业务表或平台 UI。（FR1、ARCH-1、ARCH-3）

### AC2：最小版本化跨平台契约

**Given** 已定义最小版本化 DTO、`AppError`、`PlatformEffect` 和 `SecretLeaseInput`  
**When** 分别执行成功、字段验证失败、未知错误、重复 effect 回报和 secret lease 生命周期测试  
**Then** 字段语义、稳定错误码、幂等结果和密钥生命周期符合契约  
**And** Rust panic 不跨越 FFI，ID 不透明，时间使用 RFC3339 UTC，缺失值显式 `optional/null`，明文不进入持久化或日志。（ARCH-11、ARCH-14、ARCH-16）

## Tasks / Subtasks

- [ ] 1. 建立最小 Rust workspace 和仓库基线（AC1）
  - [ ] 创建根 `Cargo.toml` 虚拟 workspace，成员仅包含 `crates/radar-core`、`crates/radar-ffi`、`crates/xtask`；显式设置 Cargo resolver，并共享 edition、license 和版本元数据。
  - [ ] 创建 `rust-toolchain.toml`，精确锁定经本 Story 验证的 Rust stable，并包含 `rustfmt`、`clippy`；提交根 `Cargo.lock`，禁止浮动工具链。
  - [ ] 创建 `crates/radar-core`、`crates/radar-ffi`、`crates/xtask` 及 `contracts/{schemas,fixtures/golden,snapshots}` 的最小目录和清晰职责说明。
  - [ ] 配置根级 `rustfmt.toml`、`.editorconfig`、`.gitignore` 和最小 README；忽略 `target/`、真实 secret、用户数据、数据库及生成物临时目录。当前项目根不是 Git 仓库，本 Story 不擅自初始化 Git；锁文件须生成并保留在工作区，待仓库初始化后纳入版本控制。
  - [ ] 不创建 `apps/windows`、`apps/apple`、`apps/android`、业务数据库、迁移、来源适配器或任何平台 UI。

- [ ] 2. 建立共享核心健康检查和单一权威边界（AC1）
  - [ ] 在 `radar-core` 定义无平台依赖的最小健康检查用例及版本化返回 DTO，可由纯 Rust 测试直接调用。
  - [ ] 保持依赖方向为 `radar-ffi -> radar-core`；`radar-core` 不依赖 UniFFI、React、SwiftUI、Compose、Tauri 或平台 SDK。
  - [ ] `radar-ffi` 只提供版本化用例/DTO/错误的薄映射与 panic 防护入口，不承载业务判断，不暴露 SQL、文件、URL、HTTP client 或任意命令能力。
  - [ ] `xtask` 提供可扩展的 `contracts` 校验入口，通过 `cargo run -p xtask -- contracts` 调用；成功返回 0，schema/snapshot/fixture 不一致返回非 0。本 Story 不安装全局 `cargo-xtask`，也不承担 Story 1.5 的 Swift/Kotlin 绑定生成与三端编译门禁。

- [ ] 3. 定义最小、稳定、版本化合同（AC2）
  - [ ] Rust 类型是运行时权威；建立 `contract_version: 1` 的最小 contract manifest，列出所有 public DTO 字段、JSON `snake_case` 名称、枚举全集和兼容性规则（同版本只允许兼容新增；删除字段、改变枚举/错误语义需显式迁移 ADR）。在 `contracts/schemas` 与 `contracts/snapshots` 保存可读镜像和稳定枚举/错误码快照。
  - [ ] 定义不透明 ID 新类型；序列化边界不得暴露数据库 rowid、内部整数或可推断结构。
  - [ ] 时间字段只接受/输出带时区的 RFC3339 UTC；缺失值使用 `Option<T>` 并在 JSON 镜像中显式表现为 `null`，不得用空字符串、零或 `unknown` 代替缺失。
  - [ ] 定义 `AppError`：至少包含 `code`、`category`、`message_key`、`retryability`、`source_id?`、`task_id?`、`details_allowlisted`、`correlation_id`；稳定 category 与 retryability 必须使用架构规定值。
  - [ ] 未知底层错误统一映射为 `internal` 并生成 correlation ID；底层错误文本不得进入面向平台的 DTO。
  - [ ] 定义 `PlatformEffect`：至少包含稳定 effect ID、幂等键、effect 类型、payload version、过期时间和执行状态；contract manifest 必须列出初始/终态、合法转换矩阵、相同重复回报的固定幂等结果，以及不同终态重复回报产生的固定 `conflict` `AppError`。最小 effect 类型可使用不执行真实副作用的合同测试类型，不提前实现通知等业务 effect。
  - [ ] 定义短生命周期 `SecretLeaseInput`，禁止派生或实现会输出明文的 `Debug`/`Display`/序列化行为；明文不得成为 task payload、持久 DTO 或日志字段。

- [ ] 4. 建立纯 Rust 合同测试与固定样本（AC1、AC2）
  - [ ] 健康检查成功：验证独立构建、合同版本和确定性返回。
  - [ ] 字段校验失败：覆盖非法/空 ID、非法 RFC3339 UTC、未知受限枚举、超限字段及不合法状态转换，并断言稳定 `validation` 错误码。
  - [ ] 未知错误与 panic：通过 `radar-ffi` 的纯 Rust 可测试适配入口和 `catch_unwind` 验证二者被转换为 `internal` `AppError`，panic 不逃逸该适配边界，错误中含 correlation ID 且不泄露底层文本；不得声称已完成 Swift/Kotlin 绑定往返。
  - [ ] effect 幂等：同一 effect ID/幂等键首次回报生效，完全相同的重复回报返回稳定幂等结果且不产生第二次状态变化；冲突回报返回稳定 `conflict`。
  - [ ] secret lease 生命周期：golden fixture 只保存不含明文的 `secret_ref`、场景和预期元数据；运行时由进程内 fake provider 生成 canary 字节并注入一次受控调用，调用后不可重用。`SecretLeaseInput` 不实现会输出明文的 `Debug`、`Display` 或 serde 序列化；扫描捕获日志、JSON、snapshot、错误文本及测试输出并断言 canary 零命中，失败信息也不得回显原字节。
  - [ ] 为成功、校验失败、未知错误、effect 回报和 secret lease 建立唯一的 `contracts/fixtures/golden/{health_success_v1,validation_failure_v1,internal_error_v1,effect_report_v1,secret_lease_v1}` 样本；每个样本在 manifest 标明输入、期望输出和禁止字段，禁止在 crate 或未来平台目录复制 fixture。
  - [ ] 增加 schema-conformance 测试：枚举所有 public DTO 并校验 `contract_version`、字段名、显式 `null`、枚举全集、`AppError` category/retryability 和 error-code snapshot，而非只抽测单一样例。

- [ ] 5. 建立本 Story 的纯 Rust 基线门禁与交接证据（AC1、AC2）
  - [ ] 运行 `cargo fmt --all --check`、`cargo clippy --workspace --all-targets --all-features -- -D warnings`、`cargo test --workspace --all-targets` 和 `cargo run -p xtask -- contracts`。
  - [ ] 验证工作区可在无注册、无云账户、无 AI Key、无平台 SDK 和无数据库的环境中完成 core 构建与测试。
  - [ ] 在当前非 Git 工作区执行确定性的目录/内容扫描：允许 `contracts/schemas/**`，但禁止 `apps/**`、`migrations/**`、SQL DDL、`rusqlite` 依赖、真实 secret、Authorization header、数据库文件和未来业务表名；同时扫描测试输出和捕获日志。该边界检查应纳入 `xtask contracts` 或独立 `xtask boundaries` 子命令。
  - [ ] 在本 Story 的 Dev Agent Record 中记录命令、结果、锁定版本和文件清单，为 Stories 1.2–1.5 提供可复用基线。

- 本 Story 只交付 Cargo workspace、`radar-core`、`radar-ffi`、`contracts`、`xtask`、最小合同和纯 Rust 测试。
- Windows/Tauri/React 壳与 `DesktopApi` 属于 Story 1.2；SwiftUI 与 `RadarCoreClient` actor 属于 1.3；Compose 与 repository/ViewModel/StateFlow 属于 1.4；生成绑定、三端合同往返、三端编译和完整 CI 门禁属于 1.5。
- 演示数据属于 1.6；原生列表/详情、视觉令牌落地和辅助技术验收属于 1.7；默认赛道与配置引导属于 1.8。
- 不得借“预留”之名创建空平台壳、未来业务表、通用 `utils/helpers/services`、云 API、账户体系、SQLCipher、自动更新、公共商店、远程诊断或云同步。

### 架构约束

- `radar-core` 是确定性规则、未来数据库/迁移/任务和跨平台运行时合同的唯一权威。平台不得复制领域规则；`radar-ffi` 只做稳定类型和错误映射。
- Application API 使用类型化 DTO 和 Rust 结果类型，不增加 `{data,error}` 包装。Rust/JSON 使用 `snake_case`；未来 Swift/Kotlin/TypeScript wrapper 可映射为惯用 `camelCase`，但不能改变语义。
- `AppError.category` 固定集合：`validation`、`not_found`、`conflict`、`permission`、`network`、`rate_limited`、`source_format`、`provider`、`storage`、`migration`、`cancelled`、`internal`。
- `AppError.retryability` 固定集合：`never`、`manual`、`automatic`、`after`。`message_key` 用于未来平台本地化，不能返回拼接的用户长文。
- `PlatformEffect` 的最终架构是持久 outbox，但本 Story 禁止提前创建数据库表；只建立纯领域合同、状态转换和内存 fake，以便后续持久化实现复用同一语义。
- `SecretLeaseInput` 只是一次执行会话的短生命周期输入。本 Story 用 fake provider 验证合同，不接入 Windows Credential Manager、Keychain 或 Android Keystore。
- FFI 输入一律视为不可信；输入长度、枚举和嵌套深度应有显式边界。不得跨 FFI 暴露数据库连接、Future、Stream、长生命周期 callback 或可变共享对象。

### 技术版本与最新官方核验

- 架构锁定 UniFFI `0.32.0`。该版本包含破坏性变化：旧式 `--config` 覆盖文件会被忽略、`[ByRef] bytes` 在 Rust 侧映射为 `&[u8]`、Kotlin/Python 对 async primary constructor 直接拒绝生成。本 Story 不使用 async constructor、旧式 config 或实验性 Kotlin JNI 管线。
- UniFFI 官方建议在多 crate workspace 尽可能使用 library mode 生成绑定；实际 Swift/Kotlin 生成与漂移校验归 Story 1.5。本 Story 仅保证 `radar-ffi` 的合同可由该模式消费。
- UniFFI 对 Swift 6 的支持仍有边界，尤其 async/`Sendable`；因此合同保持同步、窄 DTO、显式错误，不在边界暴露复杂异步对象。
- 创建 Story 时官方最新 Rust stable 为 `1.97.1`。实现时应将实际验证通过的稳定版本精确写入 `rust-toolchain.toml`，而不是只写浮动 `stable`；若选择不同版本，须记录验证依据，不得静默漂移。
- 根虚拟 Cargo workspace 应显式指定 resolver；Rust 2024 workspace 可使用 `resolver = "3"`。所有 workspace package 共享根 `Cargo.lock`。

### 测试与完成判据

- Test Design 产物当前缺失；standard profile 允许继续，但本 Story 必须把 AC2 的五类合同测试作为阻断性完成条件，不得以“后续测试”替代。
- 测试必须断言语义和稳定输出，不只断言函数未报错。golden snapshot 的变化必须能区分兼容新增和破坏性修改。
- NFR15 是派生安全约束：完整密钥不得命中数据库、持久 UI 状态、日志、诊断或测试数据。平台安全存储的端到端验收归 Stories 1.2–1.4/5.1，本 Story 只验证 core 合同和输出无明文。
- Story 完成前不得声称三端可构建、UniFFI 绑定无漂移、语言侧合同往返或平台密钥安全存储已验证；这些证据分别由 1.2–1.5 提供。

### UX 兼容边界

- 本 Story 不创建 UI、导航、主题或设计 token 实现。只需保证合同不会迫使未来三端共享 DOM/UI，且不会阻碍平台原生状态、无障碍和本地化映射。
- UX 的视觉权威是 `ux/DESIGN.md`，行为/状态权威是 `ux/EXPERIENCE.md`；从 Story 1.2 起按平台原生方式消费，不得在 1.1 创建伪共享 UI 层。

### Planning Gate

- 解析 profile：`standard`；来源：schema-v2 compatibility fallback。
- 风险建议：`assured`，原因是基础合同跨越多个权威产物并影响重要 NFR；未显式覆盖当前 profile。
- PRD、UX、Architecture、Epics、Readiness 均为 complete；Readiness 结论为 READY。
- Test Design 缺失。用户已指示继续，视为接受 standard profile 下的该项风险；上述合同测试仍为 Story 内强制项。
