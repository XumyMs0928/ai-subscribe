# Story 4.2：确定性识别重复并关联同一事件来源

状态：review

## Story

作为技术决策者，
我希望系统可靠识别重复内容并保留同一事件的各条来源证据，
以便减少噪声而不丢失不同发布方的可核验记录。

## 当前阶段交付覆盖层

- 当前只实现 shared core + 单一 SQLite owner 的 Windows RSS/Atom 切片；不新增 Windows 页面、路由、Tauri command、DesktopApi method 或 capability。
- 本阶段必须用至少两个 RSS/Atom 来源实例完成真实确定性关联；不能以“只有一种 source_kind”为由延期 FR24。
- Canonical Story 的 GitHub Release、arXiv、移动端、完整三来源和完整 NFR8/NFR13 通知/AI 矩阵继续 Deferred；只能声明 `Windows RSS minimum-loop PASS/FAIL`。
- 风险信号建议 assured；为遵守用户批准的快速 Phase 1，显式沿用 standard。readiness 旧快照与缺少系统级 test design 作为已知建议项，不降低上述 non-waivable gates。

## 验收标准

### AC1 — 稳定外部身份跨运行幂等

**Given** RSS/Atom 条目具有 adapter 已验证的 GUID/Atom ID，或 Story 4.1 已建立的 source-scoped canonical external ID  
**When** 条目跨同步轮次、应用重启或网络恢复后再次提交  
**Then** 继续使用 Story 4.1 固定的 `(source_kind, canonical_external_id)` 解析同一 `intel_item_id`，同一内容版本不产生第二条事实、provenance 或 result link  
**And** 内容变化只更新同一事实的 revision/lifecycle；不得重算、迁移或替换既有 IntelItemId。（FR23、NFR8、ARCH-7）

### AC2 — 无可靠外部 ID 时复用 URL fallback 身份

**Given** RSS item/Atom entry 没有可靠 GUID/ID，但有已验证的公网 HTTPS 原文 URL  
**When** adapter 生成 fallback identity 并由 core 持久化  
**Then** 复用现有 parser 的 `url:` + canonical URL SHA-256 结果；默认 443 与 fragment 的等价 URL 产生同一 fallback identity，path/query 差异保持不同  
**And** `content_hash` 只用于版本变化与缓存，不替代记录身份或 URL fallback；不得新增第二套 URL canonicalizer/hash。（FR23、ARCH-7）

### AC3 — 跨 RSS 来源建立可解释的确定性关联

**Given** 两个不同 RSS/Atom 来源实例的两条独立 real intel records 具有完全相同的、已 canonicalize 的公网 HTTPS `original_url`  
**When** 当前来源事务提交规范化事实  
**Then** 建立唯一的 `same_event` association group，依据固定为 `normalized_original_url`，只持久化 allowlisted basis、basis version 与 URL SHA-256 evidence digest；两条记录各作为独立 member  
**And** 两条记录各自的 IntelItemId、标题、链接、发布时间、发布方、作者、生命周期和 provenance 均保持独立；不得物理合并、删除记录或选“主记录”覆盖事实。（FR24）

### AC4 — 不做传递推断或语义相似自动关联

**Given** 两条记录只有相似标题、摘要、publisher、发布时间或 content hash，或者 A–B 与 B–C 分别由不同证据匹配  
**When** 去重与关联流程运行  
**Then** 没有相同 canonical URL 的记录不进入同一 association group；不同 evidence group 之间不做传递闭包，A–C 不因 B 的另一条证据自动关联  
**And** 记录继续作为独立候选保留；标题/摘要规则、embedding、LLM、模糊 URL 或高级事件聚类均明确 Deferred。（FR23、ARCH-25）

### AC5 — 关联生命周期、事务和并发约束确定

**Given** 多个来源以不同顺序、并发任务、重放或应用恢复写入同一 evidence group，或后续内容更新改变当前 URL  
**When** 数据库事务提交  
**Then** association ID 由版本化 domain separator + relation type + basis + basis version + evidence digest 生成；association UNIQUE key 与 `(association_id,item_id)` member PK/FK 保证一个 evidence group 和一个 membership  
**And** URL 改变时在同一事务撤销旧 current membership 并加入新 group，零成员 group 清理；只有 member 数≥2 才表示当前“已关联”，重复观察只单调更新 first/last observed，时钟回拨不得倒退。（NFR8、NFR13、ARCH-4）

### AC6 — v9 迁移、来源事务与数据域隔离

**Given** fresh database、v1–v8 database、既有多个 RSS facts、demo rows 或注入的关联写入故障  
**When** v9 migration/backfill 或新的来源事务运行  
**Then** migration 仅为非 legacy real RSS rows 按完全相同 canonical URL 确定性回填 group/member；member 的 `first_observed_at`/`last_observed_at` 分别取其 provenance 的 `first_discovered_at`/`last_updated_at`，group 的 observation envelope 分别取全部 members 的最小 first 与最大 last（不冒充“关系开始时间”），相同输入得到相同 association/member 数量，重复、悬空或非规范历史整笔 fail closed  
**And** 新关系在当前 `commit_sync_source_success` 的既有 `BEGIN IMMEDIATE` 来源事务内写入；失败回滚当前来源的 checkpoint/fact/provenance/result/count/association，但不回滚其他已提交来源；demo 不参与 real 关联，run retention 不删除事实、provenance 或 association。（NFR8、NFR13、ARCH-4、ARCH-9）

## 完整产品 Canonical AC（Deferred 部分保留）

Epics 中 Story 4.2 的五组 canonical AC 继续有效：稳定外部 ID 幂等、URL hash fallback、共享规范化链接/内容标识/版本的确定性关联、禁止仅凭语义相似合并、并发 UNIQUE/FK/事务防线。当前 Phase 1 仅注册 `rss_atom` adapter，并只激活 `normalized_original_url` 跨来源 evidence basis；GitHub Release、arXiv 的 source content/version evidence、移动恢复矩阵、AI/通知副作用矩阵和高级语义聚类不得用占位实现或假 PASS 证据替代。

## Dev Notes

### 权威数据流

RSS/Atom adapter → RawSourceCandidate → Story 4.1 normalization → 同一来源 `BEGIN IMMEDIATE` → fact/provenance upsert → normalized URL association key → group/member reconcile → checkpoint/result/count/cursor/task projection。

### 必须复用

- `RawSourceCandidate`、RSS parser 的 GUID/Atom ID 与 `url:` fallback、现有 HTTPS canonicalization/public-IP policy。
- Story 4.1 的 `canonical_external_id`、`derive_intel_item_id`、完整 `intel:` SHA-256 ID、fact/provenance schema 和 transaction plumbing。
- `DemoStore::open` 唯一 migration/verifier、`commit_sync_source_success` 唯一写编排、`intel_repository` 窄 SQL seam。
- PID+atomic scoped DB、Drop cleanup、固定时间/ID、fault injection、无公网/无 sleep 的测试模式。

### 关联模型的规范性裁决

- 模型是 evidence-keyed association group + independent members，不是“主记录”、物理 merge、event winner 或跨 evidence 的传递 group。
- Phase 1 跨来源 evidence allowlist 只有 `normalized_original_url`；RSS GUID/Atom ID 默认只在来源实例命名空间内作为 identity，不因字符串相同跨 feed 自动关联。
- content hash 仍只做版本变化/缓存；即使相同也不单独触发 association。
- 当前 membership 必须与当前可核验 provenance URL 一致；URL 改变时事务化移动 membership。完整历史关联审计若以后需要，必须通过新 Story/ADR 引入显式 observation history，不能让失效证据继续冒充当前关系。
- 关联结果是 domain fact；UI、Tauri、TS、规则或 AI 不得重算。

### 禁止项

- 禁止语义相似、embedding、LLM、标题规则、编辑距离或模糊 URL 自动关联。
- 禁止删除/覆盖独立 facts/provenance、重写 Story 4.1 IntelItemId、把关联塞进 `deterministic_association_basis` 字符串冒充关系表。
- 禁止新增第二 SQLite、post-commit backfill、platform SQL、generic command、UI placeholder、外联或全局安装。
- 禁止顺手修复 Story 2.5 已登记的 retry_wait/budget/idempotency deferred 项。
