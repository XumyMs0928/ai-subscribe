# Story 4.1：将真实来源规范化为可溯源情报

状态：ready-for-dev

## Story

作为情报阅读者，
我希望 RSS/Atom 内容转换为字段一致且保留原始证据的情报记录，
以便在后续主情报流和详情中理解并核验真实内容。

## 当前阶段交付覆盖层

- 本 Story 只完成 shared core + 单一 SQLite owner 的 RSS/Atom 规范化与溯源持久化；Windows 只做既有同步结果回归，不新增 UI 页面、路由或 IPC。
- Epic 中 RSS/Atom、GitHub Release、arXiv 的完整三来源 canonical AC 原样保留；GitHub Release、arXiv 及 Epic 3 discovery integration 本阶段 Deferred，不计入 Windows RSS milestone gate。
- 当前完成结论只能写 Windows RSS minimum-loop slice PASS/FAIL，不得写三来源、跨平台或完整 MVP 完成。
- 风险模型因跨产物、安全输入和事务 NFR 推荐 assured；根据用户已批准的快速 Phase 1 策略，显式采用 standard，但上述 non-waivable gates 不降级。

## 验收标准

### AC1 — 合法 RSS/Atom 候选形成稳定事实与溯源

**Given** 已通过 Story 2.2 adapter 安全解析的 RSS 2.0 或 Atom 候选  
**When** shared core 在来源成功提交中执行规范化  
**Then** 为每条合格候选生成稳定、无业务语义的 intel_item_id，并保存 source_id、source_kind=rss_atom、stable_external_id、publisher、original title、经验证 HTTPS original URL、可选 published time、collected time 和 64 位小写十六进制 content hash  
**And** 作者存在时原样保存，缺失时以 author=null 与 author_availability=unavailable 明示，不用空串、publisher 或其他猜测值代替。（FR13、FR14、NFR26）

### AC2 — 生命周期更新不覆盖原始事实

**Given** 同一 (source_id, stable_external_id) 首次出现、相同版本重放或 content hash 变化  
**When** 来源事务提交  
**Then** 首次出现保存 first_discovered_at，相同版本不创建第二条事实记录，变化版本在同一 intel_item_id 上单调增加 revision、更新当前来源事实和 last_updated_at，且保留首次发现时间  
**And** facts/content state、provenance、rule evaluation、AI analysis 分离；本 Story 不写规则、AI 或 FTS，后续结果不得覆盖来源事实。（FR15、FR16、ARCH-6）

### AC3 — 第三方字段 fail closed 且不伪造

**Given** adapter 收到畸形 XML/不安全 URL，或 normalized candidate 存在空标题/原文链接、超长字段、非法 content hash、不可解析可选时间  
**When** versioned Rust input/领域构造函数验证  
**Then** adapter 的结构性 feed/identity/unsafe-URL 错误按现有 source_format.rss_atom 使该来源批次失败且零写入；领域层的记录级必填字段错误只拒绝该记录；非法可选时间保存为 null 并只保留 allowlisted field/code warning  
**And** 错误稳定、脱敏并可归属到 source 与 hash 化 candidate reference，原始第三方 payload、无效 URL 和超长文本不进入数据库、日志或诊断。（ARCH-6、ARCH-14）

### AC4 — 混合批次与来源事务一致

**Given** 一个 RSS 来源批次包含多个合格候选和至少一个记录级无效候选  
**When** 执行 checkpoint、规范化、结果投影和持久化  
**Then** 合格候选的 checkpoint、intel、provenance、run snapshot/link、cursor、source/job revision 与 inserted/updated/skipped/failed counts 在同一 BEGIN IMMEDIATE 来源事务提交  
**And** 无效候选不推进 checkpoint；任一 intel/provenance/link 写入失败使该来源全部回滚，但不得回滚其他已提交来源；不得用 AI 或猜测值补全。（NFR7、NFR26）

### AC5 — 重启、保留清理和数据域隔离

**Given** v1–v7 数据库、已有 demo 数据、既有 v7 sync results 或完成后的 v8 数据库  
**When** 应用迁移、重启、离线读取或清理有界 sync run/result 历史  
**Then** v8 迁移事务化回填真实 result→intel 关系，demo/FTS/规则/AI 现有数据保持等价，重启后 FK/UNIQUE/CHECK/verifier 全部成立  
**And** 删除 run/result/failure 只删除运行历史，不删除 intel、provenance 或 checkpoint；demo 与 real namespace 不互相去重、关联或触发副作用。

### AC6 — 当前阶段来源隔离与稳定身份

**Given** 至少两个 RSS/Atom 来源实例，或同一候选跨运行/重试/重启再次出现  
**When** 一个来源失败或同一 external ID 出现在不同 source instance  
**Then** 其他来源的事实不回滚；adapter 先把 source identity 与 raw stable_external_id 规范化为 source-scoped canonical external_id，再按架构固定的 (source_kind, canonical external_id) 解析同一 intel_item_id；不同 source instance 在 Story 4.1 保持不同身份  
**And** raw stable_external_id 继续只用于 checkpoint/result 关系，content hash 只用于版本变化；跨来源 URL/event 关联和确定性去重留给 Story 4.2。

## 完整产品 Canonical AC（本阶段 Deferred 部分）

Epics 中 Story 4.1 的五组 canonical AC 继续有效：三类来源统一规范化、首次发现/最后更新/可用性、版本化 DTO 拒绝非法字段、混合批次策略，以及手动/自动发现 GitHub Release 进入同一 Release 管道。本 Story 只实现其中 RSS/Atom 可执行切片；GitHub Release、arXiv 和 discovery→Release 映射不得以占位 adapter、fixture 或假 PASS 证据提前实现。

### 必须复用

- domain/sources 的 RawSourceCandidate、warning、disposition。
- rss_atom parser 的 HTTPS URL canonicalization、stable external ID 与 content hash。
- application/sources 的 checkpoint/CAS；application/sync 的 task/run/result/count/retention；application/demo 的唯一连接和 migration verifier。

### 数据与错误合同

- IntelItemId、TaskId、SyncRunId、ResultItemId 必须强类型区分。4.1 identity scope 是一个来源实例内；4.2 才做跨来源关联。
- URL 生产输入只接受 parser 已 canonicalize 的 public HTTPS item URL；这是 Story 2.2 已批准的 NFR16 收紧策略（公网 HTTP 配置可保留但不可生成可运行 source），不得重新联网探测、静默升级 HTTP 或记录 query secrets。Story 2.6 较宽的 HTTP/HTTPS 读取 guard 不是新数据写入许可。
- invalid optional time 只保存 null + allowlisted warning；缺失 published time 不得替换为 collected time。
- 优先复用 source_format.rss_atom、storage.source、migration.source、conflict.source_revision；不得用 internal 掩盖已知错误，也不得为 intel 建平行错误类别。
- facts、provenance、rule evaluation、AI analysis、sync result 正交；4.1 不写 rule_evaluations、analysis_results 或真实 FTS 内容。
